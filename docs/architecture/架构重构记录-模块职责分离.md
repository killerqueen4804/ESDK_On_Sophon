# 架构重构记录 - Vision 模块职责分离

> 📅 **重构日期**: 2025-10-28  
> 🎯 **目标**: 解决 vision 模块职责混乱问题，实现清晰的模块划分  
> ✅ **状态**: 已完成

---

## 🔍 问题发现

在实现 TaskConfig 和 EventMessage 时，发现它们被错误地放置在`vision/`模块中，导致以下问题：

### ❌ 重构前的架构问题

```
vision/
├── CompletionDetector.h     ✅ 视觉任务完成检测
├── MediaFileFilter.h        ✅ 媒体文件过滤
├── PerformanceMonitor.h     ✅ 性能监控
├── TaskManager.h            ❌ 任务管理（不是视觉处理）
├── TaskConfig.h             ❌ 配置数据（不是视觉相关）
└── EventMessage.h           ❌ 消息格式（不是视觉相关）
```

**核心问题**：

1. **职责混乱**: vision 模块既做视觉处理，又管理任务，又定义数据结构
2. **依赖混乱**: TaskManager 需要依赖 TaskConfig，导致奇怪的模块依赖关系
3. **难以复用**: TaskConfig 绑定在 vision 模块，未来非视觉任务无法使用
4. **违反 SRP**: 单一职责原则被严重破坏

---

## ✅ 重构方案

采用**方案一：按职责分层**

### 新的目录结构

```
include/esdk_sophon/
├── types/                   # 📦 通用数据类型（新增）
│   ├── TaskConfig.h         ✅ 任务配置
│   └── EventMessage.h       ✅ 事件消息
│
├── task/                    # 📋 任务管理（新增）
│   └── TaskManager.h        ✅ 任务生命周期管理
│
└── vision/                  # 👁️ 视觉处理（专注）
    ├── CompletionDetector.h ✅ 完成检测
    ├── MediaFileFilter.h    ✅ 文件过滤
    └── PerformanceMonitor.h ✅ 性能监控
```

### 设计原理

1. **types/** - 纯数据结构，无业务逻辑

   - 可被多个模块复用
   - 不依赖任何业务模块

2. **task/** - 任务管理逻辑

   - 依赖 types 模块
   - 协调 vision、device 等模块

3. **vision/** - 专注视觉算法
   - 提供视觉处理辅助功能
   - 被 task 模块调用

**修改前**:

```cpp

    struct TaskConfig { ... };
}
}
```

**修改后**:

```cpp
namespace esdk_sophon {

    struct TaskConfig { ... };
}
}
```

### 4. 更新头文件保护符

```cpp
// 修改前

// 修改后

#define ESDK_SOPHON_TYPES_TASK_CONFIG_H_
```

### 5. 更新 include 路径

**test_task_config.cpp 修改前**:


```cpp

#include "esdk_sophon/types/EventMessage.h"

```

## 📊 重构效果对比

### 模块职责

| 模块   | 重构前                     | 重构后          |
| ------ | -------------------------- | --------------- |
| vision | 视觉处理+任务管理+数据定义 | 专注视觉处理 ✅ |
| task   | 不存在                     | 任务管理 ✅     |
| types  | 不存在                     | 通用数据类型 ✅ |

### 依赖关系

**重构前** (混乱):

```
TaskManager (在vision) → TaskConfig (在vision)
  ↓ 奇怪的依赖
Application → vision (为了用TaskManager)
  ↓ 不合理的耦合
难以扩展非视觉任务
```

**重构后** (清晰):

```
types (独立)
  ↑
  ├─ task (依赖types)
  ↑     ↓
  │  vision (独立，被task调用)
  │     ↓
  └─ mqtt (依赖types)
```

### 可复用性

| 组件         | 重构前                  | 重构后                     |
| ------------ | ----------------------- | -------------------------- |
| TaskConfig   | 绑定在 vision，难以复用 | 独立 types 模块，可复用 ✅ |
| EventMessage | 绑定在 vision，难以复用 | 独立 types 模块，可复用 ✅ |
| vision 模块  | 职责混乱，难以理解      | 职责单一，易于维护 ✅      |

## 📚 知识点总结

### 1. 单一职责原则 (SRP)

**定义**: 一个类或模块应该只有一个引起它变化的原因

**应用**:

- types 模块：只管理数据结构定义
- task 模块：只管理任务生命周期
- vision 模块：只提供视觉算法辅助

### 2. 依赖倒置原则 (DIP)

**定义**: 高层模块不应依赖低层模块，都应依赖抽象

**应用**:

- task 和 vision 都依赖 types（抽象的数据定义）
- 而不是 task 依赖 vision（具体实现）

### 3. 开闭原则 (OCP)

**定义**: 对扩展开放，对修改关闭

**应用**:

- 新增音频任务？直接使用 types 模块的 TaskConfig
- 新增存储模块？直接使用 types 模块的 EventMessage
- 无需修改原有模块代码

### 4. 接口隔离原则 (ISP)

**定义**: 客户端不应被迫依赖它不使用的接口

**应用**:

- mqtt 模块只需要 EventMessage，不需要引入整个 vision 模块
- task 模块需要 TaskConfig，不需要关心 vision 的实现细节

## 🎯 面试回答模板

**Q: 你在项目中如何进行架构重构？以一个具体例子说明。**

**A**: 在 DJI ESDK 项目中，我发现 TaskConfig、EventMessage 等数据结构被错误放置在 vision 模块，导致职责混乱。我进行了以下重构：

1. **问题识别**:

   - vision 模块既做视觉处理，又管理任务，又定义数据
   - 违反单一职责原则，难以扩展

2. **方案设计**:

   - 创建 types 模块存放通用数据类型
   - 创建 task 模块管理任务逻辑
   - vision 模块专注视觉算法

3. **实施步骤**:

   - 创建新目录结构
   - 移动文件并更新命名空间
   - 修改所有引用路径
   - 重新编译测试验证

4. **重构收益**:

   - 模块职责清晰，易于理解和维护
   - 降低耦合度，提高可复用性
   - 符合 SOLID 原则，便于扩展

5. **验证方法**:
   - 所有单元测试通过
   - 编译无警告
   - 代码审查确认

这次重构体现了我对架构设计原则的理解和实践能力。
