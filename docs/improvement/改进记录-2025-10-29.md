### 问题1: switch语句中的变量初始化错误

**错误信息**:
```
error: jump to case label crosses initialization
```

**原因分析**:
- switch是基于goto实现的跳转语句
- case标签只是跳转目标，不是作用域边界
- C++不允许"跳过"变量初始化

**解决方案**:
```cpp
// ❌ 错误写法
case TaskConflictAction::STOP_OLD:
    bool isNewTaskLiveview = (newConfig.source == 0);
    // ...

// ✅ 正确写法
case TaskConflictAction::STOP_OLD: {  // 用花括号创建作用域
    bool isNewTaskLiveview = (newConfig.source == 0);
    // ...
    break;
}
```

**知识点**:
- switch中的case需要花括号创建独立作用域
- 避免变量初始化被跳过

### 问题2: map的operator[]与默认构造函数

**错误信息**:
```
error: no matching function for call to 'TaskState::TaskState()'
```

**原因分析**:
```cpp
runningTasks_.emplace(taskIdStr, std::move(taskState));
runningTasks_[taskIdStr].status = PROCESSING;  // ❌ 需要默认构造!
```

- `map::operator[]`会在key不存在时调用默认构造函数
- TaskState没有默认构造函数

**解决方案**:
```cpp
// ✅ 正确：在插入前修改
taskState.status = PROCESSING;
runningTasks_.emplace(taskIdStr, std::move(taskState));
```

**知识点**:
- 优先使用emplace/insert而非operator[]
- 在对象构造时就设置正确状态

### 问题3: processWaitingQueue崩溃

**错误信息**:
```
basic_string::_M_create
```

**原因分析**:
```cpp
// ❌ 错误：先pop()再访问config
types::TaskConfig config = waitingQueue_.front();
waitingQueue_.pop();  // config被销毁!
std::string taskIdStr = std::to_string(config.taskID);  // 未定义行为!
```

**解决方案**:
```cpp
// ✅ 正确：在pop()前复制所有需要的数据
types::TaskConfig config = waitingQueue_.front();
std::string taskIdStr = std::to_string(config.taskID);
TaskState taskState(taskIdStr, config);
waitingQueue_.pop();  // 现在可以安全pop了
```

**知识点**:
- **关键原则**: 在调用`pop()`之前完成所有数据访问
- `queue::pop()`会销毁队首元素
- 先复制，后删除

### 问题4: 测试用例相互影响

**问题描述**:
- TaskManager是单例，所有测试共享同一实例
- 前一个测试的任务影响后续测试

**测试失败原因**:

| 测试 | 失败原因 | 解决方案 |
|------|---------|---------|
| 测试4 | 测试3的视频流任务2001未清理 | 测试3结束时停止任务 |
| 测试6 | 任务5001在等待队列中，stopTask无法删除 | 增强stopTask支持队列删除 |
| 测试7 | 任务6001在等待队列中 | 同上 |

**解决方案1**: 每个测试结束后清理
```cpp
void test_start_liveview_task() {
    // ... 测试代码 ...
    
    printTestResult("启动视频流任务", passed);
    
    // 清理：停止任务，避免影响后续测试
    manager.stopTask(std::to_string(config.taskID));
}
```

**解决方案2**: 增强stopTask()支持等待队列
```cpp
bool TaskManager::stopTask(const std::string& taskId) {
    std::lock_guard<std::mutex> lock(mutex_);
    
    // 1. 先从运行列表删除
    auto it = runningTasks_.find(taskId);
    if (it != runningTasks_.end()) {
        // ... 删除运行中的任务 ...
        return true;
    }
    
    // 2. 从等待队列删除
    std::queue<types::TaskConfig> newQueue;
    bool found = false;
    
    while (!waitingQueue_.empty()) {
        types::TaskConfig config = waitingQueue_.front();
        waitingQueue_.pop();
        
        if (std::to_string(config.taskID) == taskId) {
            found = true;
            logger_.info("从等待队列删除任务: taskID=" + taskId);
        } else {
            newQueue.push(config);
        }
    }
    
    waitingQueue_ = newQueue;
    return found;
}
```

**知识点**:
- 单例模式下测试需要注意状态清理
- 测试之间应该相互独立
- 队列操作需要重建队列来删除元素

## 📚 知识点总结

### 1. C++ switch语句的坑

**面试题**: 为什么switch的case里不能直接声明变量？

**答案**:
- switch是基于goto实现的跳转
- case标签不是作用域边界
- 如果直接声明变量，从其他case跳过来时变量未初始化
- 解决：用花括号`{}`创建独立作用域

### 2. std::queue的正确用法

**关键原则**: **先复制，后删除**

```cpp
// ❌ 错误
auto data = queue.front();
queue.pop();
useData(data);  // data可能已失效!

// ✅ 正确
auto data = queue.front();  // 复制数据
auto copy = data;           // 或者这样
queue.pop();                // 再删除
useData(copy);              // 使用副本
```

**原因**:
- `front()`返回的是引用
- `pop()`会销毁队首元素
- 引用可能指向已销毁的对象

### 3. map::operator[] vs emplace

| 操作 | 行为 | 要求 |
|------|------|------|
| `map[key]` | key不存在时默认构造value | value必须可默认构造 |
| `map.at(key)` | key不存在时抛异常 | 无要求 |
| `map.emplace(key, val)` | 原位构造，避免拷贝 | 无要求 |

**最佳实践**:
- 插入时用emplace
- 修改已存在元素时用at()或迭代器
- 避免使用operator[]

### 4. 单元测试的隔离性

**原则**: 测试之间应该相互独立

**单例模式下的挑战**:
- 所有测试共享同一个实例
- 需要在每个测试后清理状态

**解决方案**:
```cpp
void test_something() {
    // 1. 设置
    auto& instance = Singleton::getInstance();
    
    // 2. 测试
    bool result = instance.doSomething();
    
    // 3. 断言
    assert(result == expected);
    
    // 4. 清理 ⭐ 关键!
    instance.cleanup();
}
```
