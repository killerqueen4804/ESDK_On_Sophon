## 2025-10-30 (下午): 修正 MQTT 指令理解错误

### 📌 问题发现

集成测试时发现程序报错：

```
[ERROR] 解析算法同步数据失败: [json.exception.out_of_range.403] key 'taskID' not found
```

用户提醒：**算法同步是没有 taskID 的**

### 🔍 根本原因

**错误理解接口文档**：

- ❌ 我们认为 `device_algorithm_sync` = 启动任务（包含 taskID）
- ✅ 实际上 `device_algorithm_sync` = **同步算法包**（无 taskID）

**正确的工作流程**：

```
1. device_algorithm_sync     → 同步/下载算法包（❌ 无taskID）
2. device_algorithm_enable   → 启动任务分析（✅ 有taskID）
3. [运行中] 推送检测结果     → drone/{device_sn}/info/event
4. device_algorithm_disable  → 停止任务（✅ 有taskID）
5. device_task_end           → 任务结束通知（✅ 有taskID）
```

```cpp
void MqttHandler::handleAlgorithmSync(const nlohmann::json& data) {
    /**
     * 📖 算法同步 (device_algorithm_sync)
     *
     * 功能: 下载并安装算法包到设备
     *
     * 请求格式: {
     *   "algorithm_list": [
     *     {
     *       "id": 1234,          // 算法仓ID
     *       "name": "算法名称",
     *       "version": "v1.0",
     *       "url": "下载地址",
     *       "type": [...]        // 算法类型列表
     *     }
     *   ]
     * }
     *
     * 注意: ❌ 没有 taskID 字段！这个指令只是同步算法包，不启动任务
     */
    logger_.info("处理算法同步指令...");
    logger_.debug("算法同步数据: " + data.dump());

    try {
        // 1. 验证algorithm_list字段
        if (!data.contains("algorithm_list")) {
            logger_.error("算法同步指令缺少algorithm_list字段");
            sendServiceReply("device_algorithm_sync", 1, 0);
            return;
        }

        const auto& algorithmList = data.at("algorithm_list");
        if (!algorithmList.is_array() || algorithmList.empty()) {
            logger_.error("algorithm_list字段格式错误或为空");
            sendServiceReply("device_algorithm_sync", 1, 0);
            return;
        }

        // 2. 遍历算法包列表
        logger_.info("收到 " + std::to_string(algorithmList.size()) + " 个算法包");

        for (const auto& algorithm : algorithmList) {
            int algorithmId = algorithm.value("id", 0);
            std::string name = algorithm.value("name", "");
            std::string version = algorithm.value("version", "");
            std::string url = algorithm.value("url", "");

            logger_.info("算法包: id=" + std::to_string(algorithmId) +
                        " name=" + name + " version=" + version);
            logger_.debug("下载地址: " + url);

            // TODO: 实现算法包下载和安装逻辑
        }

        // 3. 发送成功应答
        logger_.info("算法同步完成（占位实现）");
        sendServiceReply("device_algorithm_sync", 0, 0);

    } catch (const nlohmann::json::exception& e) {
        logger_.error("解析算法同步数据失败: " + std::string(e.what()));
        logger_.error("数据内容: " + data.dump());
        sendServiceReply("device_algorithm_sync", 1, 0);
    }
}
```

```cpp
void MqttHandler::handleAlgorithmEnable(const nlohmann::json& data) {
    /**
     * 📖 算法启用 (device_algorithm_enable)
     *
     * 功能: 启动任务，开始算法分析
     *
     * 请求格式: {
     *   "id": 1234,              // 算法仓ID
     *   "taskID": 1234,          // ✅ 任务ID（这里才有！）
     *   "source": 0,             // 0=视频流, 1=图片
     *   "display": 0,
     *   "airtransfer": 0
     * }
     */
    logger_.info("处理启用算法指令...");
    logger_.debug("启用算法数据: " + data.dump());

    try {
        // 1. 验证taskID字段
        if (!data.contains("taskID")) {
            logger_.error("启用算法指令缺少taskID字段");
            sendServiceReply("device_algorithm_enable", 1, 0);
            return;
        }

        // 2. 解析为TaskConfig
        types::TaskConfig config = types::TaskConfig::fromJson(data);

        // 3. 验证配置有效性
        if (!config.isValid()) {
            logger_.error("任务配置无效: taskID=" + std::to_string(config.taskID));
            sendServiceReply("device_algorithm_enable", 1, config.taskID);
            return;
        }

        // 4. 调用TaskManager启动任务
        bool success = taskManager_.startTask(config);

        // 5. 发送应答
        if (success) {
            logger_.info("任务启动成功: taskID=" + std::to_string(config.taskID));
            sendServiceReply("device_algorithm_enable", 0, config.taskID);
        } else {
            logger_.error("任务启动失败: taskID=" + std::to_string(config.taskID));
            sendServiceReply("device_algorithm_enable", 3, config.taskID);
        }

    } catch (const nlohmann::json::exception& e) {
        logger_.error("解析启用算法数据失败: " + std::string(e.what()));
        logger_.error("数据内容: " + data.dump());
        sendServiceReply("device_algorithm_enable", 1, 0);
    }
}
```

## 2025-10-30 (下午): 优化算法同步应答性能

### 📌 问题发现

用户反馈测试日志：

```
[INFO] 算法同步完成（占位实现）
[WARN] 等待消息确认超时, token: 2
```

用户说明：**算法同步完成，发送完消息后就不用管了，不用等待消息确认了**

### 🔍 根本原因

**MQTT QoS 级别导致的阻塞**:

在 `MqttClient::Impl::publish()` 中：

```cpp
// QoS > 0 时等待确认
if (actualQos > 0) {
    rc = MQTTClient_waitForCompletion(pahoClient_, token, timeoutMs_);
    if (rc != MQTTCLIENT_SUCCESS) {
        logger_.warning("等待消息确认超时, token: " + std::to_string(token));
    }
}
```

**问题分析**:

- `device_algorithm_sync` 是占位实现，不需要保证消息送达
- 使用 QoS 1 会阻塞等待 broker 确认（10 秒超时）
- 如果网络慢或 broker 繁忙，会出现超时警告
- 占位实现没必要等待，应该"发完就走"

### ✅ 修复方案

**方案选择**: 针对 `device_algorithm_sync` 使用 QoS 0

**为什么选择 QoS 0?**

1. **无需保证送达**: 占位实现，功能不完整
2. **性能更好**: 不阻塞，立即返回
3. **避免超时**: 不等待确认，无超时警告
4. **减少资源**: 降低网络和 broker 负担

**其他指令仍用 QoS 1**:

- `device_algorithm_enable`: 启动任务，必须保证送达 ✅ QoS 1
- `device_algorithm_disable`: 停止任务，必须保证送达 ✅ QoS 1
- `device_task_end`: 任务结束，必须保证送达 ✅ QoS 1

### 📚 知识点总结

#### 1. **MQTT QoS 级别详解** ⭐⭐⭐⭐⭐

**QoS 0 - At most once (最多一次)**

```
发送者                      Broker                     接收者
   |                          |                           |
   |------- PUBLISH -------->|                           |
   |                          |------- PUBLISH -------->|
   |                          |                           |
   完成（不等待）              完成                        完成
```

**特点**:

- ✅ 最快：无需等待确认
- ✅ 最省资源：无需存储、重传
- ❌ 可能丢失：网络故障时消息会丢
- 💡 **适用场景**: 传感器数据、日志、占位实现

**QoS 1 - At least once (至少一次)**

```
发送者                      Broker                     接收者
   |                          |                           |
   |------- PUBLISH -------->|                           |
   |                          |------- PUBLISH -------->|
   |                          |                           |
   |<------ PUBACK ---------|                           |
   |                          |<------ PUBACK ---------|
   完成                        完成                        完成
```

**特点**:

- ✅ 保证送达：必须收到 PUBACK 确认
- ✅ 可靠性高：失败会自动重传
- ❌ 可能重复：网络抖动时可能收到多次
- ❌ 性能开销：需要等待确认
- 💡 **适用场景**: 指令下发、任务启停、重要通知

**QoS 2 - Exactly once (恰好一次)**

```
发送者                      Broker                     接收者
   |                          |                           |
   |------- PUBLISH -------->|                           |
   |                          |------- PUBLISH -------->|
   |<------ PUBREC ---------|                           |
   |                          |<------ PUBREC ---------|
   |------- PUBREL -------->|                           |
   |                          |------- PUBREL -------->|
   |<------ PUBCOMP ---------|                           |
   |                          |<------ PUBCOMP ---------|
   完成                        完成                        完成
```

**特点**:

- ✅ 严格一次：保证不重复、不丢失
- ❌ 最慢：4 次握手，延迟高
- ❌ 最耗资源：需要存储事务状态
- 💡 **适用场景**: 金融交易、支付、库存扣减

**面试高频问题**:
Q: 如何选择 MQTT QoS 级别？
A:

```
场景分析矩阵:

┌─────────────┬───────────┬───────────┬───────────┐
│             │  QoS 0    │  QoS 1    │  QoS 2    │
├─────────────┼───────────┼───────────┼───────────┤
│ 延迟        │  最低     │  中等     │  最高     │
│ 资源消耗    │  最低     │  中等     │  最高     │
│ 可靠性      │  低       │  高       │  最高     │
│ 重复性      │  无       │  可能重复 │  不重复   │
└─────────────┴───────────┴───────────┴───────────┘

选择依据:
1. 数据重要性: 越重要越高QoS
2. 幂等性: 可重复执行的操作用QoS 1即可
3. 性能要求: 实时性要求高用QoS 0
4. 网络质量: 网络不稳定时提高QoS
```

#### 2. **异步 vs 同步发布** ⭐⭐⭐⭐

**同步发布** (当前实现):

```cpp
bool publish(const std::string& topic,
             const std::string& message,
             int qos) {
    // 发送
    MQTTClient_publishMessage(client, topic, &msg, &token);

    // 等待确认（阻塞）
    if (qos > 0) {
        MQTTClient_waitForCompletion(client, token, timeout);
    }

    return true;
}
```

**优点**:

- ✅ 实现简单
- ✅ 立即知道结果
- ✅ 调试方便

**缺点**:

- ❌ 阻塞线程
- ❌ 性能差（等待 IO）
- ❌ 超时会卡住

**异步发布** (高级实现):

```cpp
bool publishAsync(const std::string& topic,
                  const std::string& message,
                  int qos,
                  std::function<void(bool)> callback) {
    // 发送
    MQTTClient_publishMessage(client, topic, &msg, &token);

    // 不等待，注册回调
    deliveryCallbacks_[token] = callback;

    return true;
}

// 在 onDeliveryComplete 回调中
void onDeliveryComplete(MQTTClient_deliveryToken token) {
    auto it = deliveryCallbacks_.find(token);
    if (it != deliveryCallbacks_.end()) {
        it->second(true);  // 调用回调
        deliveryCallbacks_.erase(it);
    }
}
```

**优点**:

- ✅ 非阻塞
- ✅ 性能高
- ✅ 可批量发送

**缺点**:

- ❌ 实现复杂
- ❌ 需要管理回调
- ❌ 调试困难

#### 3. **性能优化策略** ⭐⭐⭐⭐

#### 1. Header-Only 库的优缺点

**优点**:

- ✅ 无需编译，直接包含头文件即可使用
- ✅ 编译器可以看到完整实现，优化空间大
- ✅ 模板类必须 header-only
- ✅ 便于分发（只需复制头文件）

**缺点**:

- ❌ 编译时间长（每个使用者都要编译一遍）
- ❌ 增大二进制体积（可能有代码重复）
- ❌ 修改后需要重新编译所有使用者

**何时使用 Header-Only**:

1. 模板类（必须）
2. 内联函数（推荐）
3. 工具类库（如我们的 Vision 模块）

#### 2. RAII 在性能监控中的应用

**RAII 原则**: Resource Acquisition Is Initialization（资源获取即初始化）

**核心思想**:

- 构造函数获取资源（启动计时器）
- 析构函数释放资源（记录结果）
- 利用 C++的栈自动管理生命周期

**PerformanceMonitor 的 RAII 设计**:

```cpp
class PerformanceMonitor {
public:
    class InferenceHandle {
    public:
        InferenceHandle(PerformanceMonitor* monitor, ...)
            : monitor_(monitor),
              startTime_(std::chrono::high_resolution_clock::now()) {
            // 构造时：记录开始时间
        }

        ~InferenceHandle() {
            // 析构时：如果用户忘记调用finish()，自动记录
            if (monitor_ && metrics_.totalTime == 0) {
                auto now = std::chrono::high_resolution_clock::now();
                metrics_.totalTime = duration(now - startTime_);
                monitor_->recordMetrics(metrics_);
            }
        }

        void finish() {
            // 手动完成（推荐）
            monitor_->recordMetrics(metrics_);
            monitor_ = nullptr;  // 防止析构时重复记录
        }
    };
};
```

**为什么这样设计？**

1. **防止遗漏**: 即使忘记调用`finish()`，析构时也会自动记录
2. **异常安全**: 抛出异常时，析构函数仍会执行，不会丢失数据
3. **代码简洁**: 不需要 try-catch 包裹

**对比手动管理**:

```cpp
// ❌ 手动管理（容易遗漏）
auto startTime = now();
try {
    process();
} catch (...) {
    // 容易忘记记录！
    throw;
}
auto endTime = now();
recordMetrics(endTime - startTime);

// ✅ RAII自动管理
{
    auto handle = monitor.startInference(...);
    process();
    handle.finish();
}  // 离开作用域自动析构，确保记录
```

**面试问答**:

Q: 什么是 RAII？举个项目中的例子。  
A: RAII 是 Resource Acquisition Is Initialization，资源获取即初始化。在我的性能监控模块中，我设计了`InferenceHandle`类：构造时启动计时器，析构时自动记录结果。这样即使用户忘记调用`finish()`或中途抛出异常，析构函数也会确保性能数据被记录，避免数据丢失。

### 🎯 优化方案设计

#### 优化 1: 自适应定时器完成检测

**文件**: `include/esdk_sophon/Vision/CompletionDetector.h`

**核心思路**:

1. **首次触发机制**: 首张图片到达后才启动定时器 (避免空等待)
2. **滑动窗口**: 每收到新图片重置定时器 (延长等待时间)
3. **自适应超时**: 根据文件到达速率动态调整超时时间

**自适应算法**:

```cpp
// 计算平均文件到达间隔
double avgInterval = totalElapsed / (filesReceived - 1);

// 超时时间 = 平均间隔 * 3 (留足缓冲)
timeout = clamp(avgInterval * 3, 30s, 120s);

// 例如:
// 100张图片,300秒 → 平均3秒/张 → 超时9秒
// 100张图片,1000秒 → 平均10秒/张 → 超时30秒
```

**工作流程**:

```
任务开始 → 等待首张图片 (不计时)
              ↓ 首张到达
         启动定时器 (T=60s)
              ↓
         收到新图片 → 重置定时器 ←┐
              │                   │
              └───────────────────┘
              ↓ 超过T秒无新图片
         任务完成
```

**使用示例**:

```cpp
CompletionDetector detector;
detector.setCompletionCallback([](const string& reason) {
    INFO("Task completed: %s", reason.c_str());
});

detector.start();  // 启动,但不计时

// 媒体文件回调
detector.onFileReceived();  // 首次启动定时器,后续重置
detector.onFileProcessed();
```

**优势**:

- ✅ 不依赖预期文件数量

#### 1. 自适应算法设计

**知识点**: 如何在参数不确定的情况下做出决策?

**答案**: 自适应策略

- 根据运行时数据动态调整参数
- 例如: 文件到达速率 → 超时时间

**面试模板**:

> "在我的项目中,遇到了无法预知文件数量的问题。我设计了自适应定时器:根据文件到达速率动态调整超时时间。如果文件传输快(平均 3 秒/张),超时设为 9 秒;如果传输慢(平均 10 秒/张),超时设为 30 秒。这样既避免了误判,又能快速响应。"

#### 2. EXIF 时间戳的应用

**知识点**: 如何区分新旧数据?

**答案**: 时间戳过滤

- EXIF DateTimeOriginal (相机生成,不可伪造)
- 文件系统时间 (兜底方案)
- 时间缓冲 (避免边界误判)

**面试模板**:

> "在分布式系统中,时间戳是判断数据新旧的可靠手段。我的项目需要区分'本次任务的图片'和'旧任务的图片',由于文件名无规律,我采用 EXIF 时间戳过滤:记录任务开始时间,只处理此后拍摄的图片。为避免时钟误差,时间戳往前推 5 秒缓冲。"

#### 3. 百分位数 vs 平均值

**知识点**: 为什么用 P95/P99 而不是平均值?

**答案**: 百分位数更能反映真实性能

- 平均值会被极端值拉偏
- P95 表示"95%的请求都在此时间内完成"
- P99 表示"只有 1%的请求超过此时间"

**示例**:

```
100次推理:
- 95次: 40ms
- 4次: 50ms
- 1次: 200ms (异常)

平均值: (95*40 + 4*50 + 1*200) / 100 = 42ms
P95: 50ms
P99: 200ms

结论:
- 平均值42ms看起来不错,但隐藏了1%的异常情况
- P99=200ms暴露了问题,需要优化
```

**面试模板**:

> "我在性能监控中使用 P95/P99 百分位数而不是平均值,因为平均值会被极端值拉偏。例如 100 次推理,99 次 40ms,1 次 200ms,平均值 42ms 看似正常,但 P99=200ms 暴露了问题。百分位数能更准确反映用户体验。"

#### Q1: MQTT 连接和设备连接的区别?

**A**:

#### Q2: Edge-SDK 的 Liveview 如何使用?

**A**: 基于回调机制:

```cpp
// 1. 创建Liveview实例
auto liveview = edge_sdk::CreateLiveview();

// 2. 定义H264流回调
edge_sdk::Liveview::H264Callback callback =
    [](const uint8_t* buf, uint32_t len) -> ErrorCode {
        // buf: H264编码的视频帧
        // 需要用FFmpeg解码为cv::Mat
        cv::Mat frame = decodeH264(buf, len);
        // 传给Vision模块检测
        VisionModule::detect(frame);
        return kOk;
    };

// 3. 初始化Liveview
Liveview::Options option = {
    .camera = Liveview::kCameraTypePayload,   // 负载相机
    .quality = Liveview::kStreamQuality720p,  // 720p
    .callback = callback
};
liveview->Init(option);

// 4. 启动视频流
liveview->StartH264Stream();

// 5. 停止视频流
liveview->StopH264Stream();
liveview->DeInit();
```

**关键点**:

- H264 流是压缩格式,需要 FFmpeg 解码
- 回调函数在 SDK 内部线程执行,注意线程安全
- Vision 模块通过 Callback 接收`cv::Mat`

#### Q3: MediaManager 如何读取图片?

**A**: 三步流程:

```cpp
// 1. 获取MediaManager单例
auto* mediaManager = MediaManager::Instance();

// 2. 创建MediaFilesReader
auto reader = mediaManager->CreateMediaFilesReader();
reader->Init();

// 3. 获取文件列表
MediaFilesReader::MediaFileList fileList;
reader->FileList(fileList);

// 4. 打开并读取图片文件
for (auto& file : fileList) {
    if (file->file_type == MediaFile::kFileTypeJpeg) {
        // 打开文件
        auto fd = reader->Open(file->file_path);

        // 读取文件内容到内存
        std::vector<uint8_t> buffer(file->file_size);
        reader->Read(fd, buffer.data(), file->file_size);
        reader->Close(fd);

        // 用OpenCV解码为Mat
        cv::Mat image = cv::imdecode(buffer, cv::IMREAD_COLOR);

        // 传给Vision模块
        VisionModule::detect(image);
    }
}

// 5. 清理
reader->DeInit();
```

**为什么需要`DataSource`参数?**

虽然输入都是`cv::Mat`,但不同来源需要不同处理:

- **Liveview**: 实时处理,优先速度,可以降低精度
- **MediaFile**: 离线处理,优先精度,保持高分辨率
- **ZoomCapture**: 超高分辨率,需要特殊预处理

**代码示例**:

```cpp
ProcessResult YOLOv10Detector::process(
    std::shared_ptr<cv::Mat> image,
    DataSource source,
    const std::string& sourceId
) {
    if (source == DataSource::kLiveview) {
        // 实时流:快速推理
        cv::resize(*image, resized, cv::Size(640, 640));
        auto result = fastInfer(resized);
        result.visualizedImage = drawBoxes(resized, result.detections);

    } else if (source == DataSource::kMediaFile) {
        // 离线图片:高精度推理
        auto result = highPrecisionInfer(*image);
    }

    return result;
}
```

```cpp
bool TaskManager::checkTaskCompletion(const std::string& taskId) {
    auto& state = tasks_[taskId];

    // 策略1: 超过60秒无新文件 (避免卡死)
    auto elapsed = now() - state.lastMediaFileTime;
    bool timerOk = (elapsed > 60s && state.mediaFilesProcessed > 0);

    // 策略2: 处理数量==预期数量 (精确判断)
    bool countOk = (state.expectedMediaFiles > 0 &&
                   state.mediaFilesProcessed >= state.expectedMediaFiles);

    if (timerOk || countOk) {

        return true;
    }

    return false;
}
```

#### 核心设计 3: 时间戳过滤解决媒体文件混淆

**核心思路**: 主动过滤,而非被动删除

**文件**: `include/esdk_sophon/Vision/TaskManager.h`

**过滤策略**:

```cpp
bool TaskManager::shouldProcessMediaFile(
    const std::string& taskId,
    const std::string& fileId,
    int64_t fileTimestamp  // 从EXIF提取
) {
    auto& state = tasks_[taskId];

    // 策略1: 时间戳过滤(核心!)
    // 只处理taskStartTime之后拍摄的图片
    if (fileTimestamp < toMillis(state.taskStartTimestamp)) {
        INFO("Skip old file: %s", fileId.c_str());
        return false;  // 这是旧任务的图片!
    }

    // 策略2: 任务ID过滤
    if (fileId.find(taskId) == std::string::npos) {
        INFO("Skip file from different task: %s", fileId.c_str());
        return false;
    }

    // 策略3: 去重过滤
    if (alreadyProcessed(fileId)) {
        return false;
    }

    // 通过所有检查
    state.receivedFileIds.push_back(fileId);
    state.lastMediaFileTime = now();
    return true;
}
```

**EXIF 时间戳提取**:

```cpp
#include <exiv2/exiv2.hpp>

int64_t extractExifTimestamp(const std::string& filePath) {
    auto image = Exiv2::ImageFactory::open(filePath);
    image->readMetadata();

    auto& exifData = image->exifData();
    auto iter = exifData.findKey(
        Exiv2::ExifKey("Exif.Photo.DateTimeOriginal"));

    if (iter != exifData.end()) {
        std::string timeStr = iter->toString();
        return parseExifTime(timeStr);  // "2025:10:27 14:30:15"
    }

    // 如果EXIF失败,使用文件修改时间
    struct stat st;
    stat(filePath.c_str(), &st);
    return st.st_mtime * 1000;
}
```

**使用示例**:

```cpp
ErrorCode MediaFilesUpdateCallback(const MediaFile& file) {
    // 1. 提取时间戳
    int64_t timestamp = extractExifTimestamp(file.file_path);

    // 2. 询问是否应该处理
    if (TaskManager::Instance().shouldProcessMediaFile(
            currentTaskId, file.file_path, timestamp)) {

        // 3. 处理此文件
        media_file_queue.push(file);

    } else {
        INFO("Skip old file: %s", file.file_name.c_str());
    }

    return kOk;
}
```

### 🎓 关键知识点

#### 1. 策略模式的正确应用

**问题**: 虽然输入都是`cv::Mat`,为什么还需要`DataSource`参数?

**答案**:

- 策略模式不仅仅是"算法替换",还包括"算法适配"
- 同一个算法(如 YOLOv10),对不同数据源可能需要不同的前处理、后处理策略
- `DataSource`参数使算法能够**根据上下文调整行为**

**面试回答模板**:

> "在我的项目中,我使用策略模式设计了算法处理器。虽然所有算法都接收`cv::Mat`,但我额外传递了`DataSource`参数,这样算法可以根据数据来源(实时流 vs 离线图片)采用不同的处理策略。比如实时流优先速度,会降低分辨率快速推理;而离线图片优先精度,保持原分辨率高质量推理。这体现了策略模式的灵活性。"

#### 2. 异步任务的完成检测

**问题**: 如何可靠地检测异步任务完成?

**答案**: 混合策略

- **定时器**: 作为兜底方案,避免无限等待
- **计数器**: 精确判断,但需要知道预期数量
- **状态机**: 明确任务处于哪个阶段
- **时间戳**: 过滤无关数据,提高判断准确性

**面试回答模板**:

> "在我的项目中,遇到了'如何判断媒体文件全部接收完成'的问题。单纯用定时器不可靠,因为网络延迟可能导致误判。我设计了混合策略:首先通过任务状态机明确任务阶段,然后结合定时器(60 秒无新文件)和计数器(如果知道预期数量)进行双重检测,同时用 EXIF 时间戳过滤旧任务的图片。这样既避免了卡死,又提高了判断准确性。"

#### 3. 时间戳过滤 vs 自动删除

**问题**: 为什么时间戳过滤比自动删除更好?

**答案**:

- **自动删除**: 被动机制,依赖外部系统(机场),时序不确定
- **时间戳过滤**: 主动机制,自己控制,确定性强,无副作用

**对比表**:

| 方案            | 优点                     | 缺点                              | 可靠性 |
| --------------- | ------------------------ | --------------------------------- | ------ |
| `SetAutoDelete` | 简单                     | 时序不确定,可能删除正在传输的文件 | ❌ 低  |
| 时间戳过滤      | 确定性强,无副作用,可追溯 | 需要解析 EXIF                     | ✅ 高  |

**面试回答模板**:

> "旧项目用`SetDroneNestAutoDelete`控制机场图片删除,但效果不好,因为删除时机不确定,可能误删正在传输的文件。我改用时间戳过滤:记录任务开始时间,从图片 EXIF 提取拍摄时间,只处理任务开始后拍摄的图片。这是主动过滤,不依赖外部系统,确定性强,而且保留了所有图片便于事后审查。"

#### 4. 状态机设计

**问题**: 如何设计清晰的任务状态机?

**原则**:

1. **状态互斥**: 每个时刻只能处于一个状态
2. **转移明确**: 每个转移都有明确的触发条件
3. **可观测**: 状态变化可追溯,便于调试

**状态机示例**:

```cpp
enum class TaskState {
    kIdle,                  // 初始状态
    kLiveviewRunning,       // 视频流处理中
    kLiveviewEnded,         // 视频流结束,等待媒体文件
    kMediaFileProcessing,   // 媒体文件处理中
    kCompleted,             // 任务完成
    kError                  // 错误状态
};

// 状态转移
void TaskManager::onLiveviewEnded(const std::string& taskId) {
    auto& state = tasks_[taskId];

    if (state.state == TaskState::kLiveviewRunning) {
        state.state = TaskState::kLiveviewEnded;
        state.liveviewEndTime = now();

        // 如果配置包含MediaFile,进入等待状态
        if (state.config.enableMediaFile) {
            state.state = TaskState::kMediaFileProcessing;
        } else {
            // 否则直接完成
            completeTask(taskId, true);
        }
    }
}
```
