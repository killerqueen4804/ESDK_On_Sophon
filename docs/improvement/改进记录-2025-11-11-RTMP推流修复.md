# 改进记录 - RTMP 推流修复

**日期**: 2025-11-11  
**问题**: RTMP 推流器虽然推送了数据，但播放器显示 0 KB/s，无法播放视频  
**影响模块**: `rtmp::RtmpStreamer`, `task::LiveStreamTask`

## 问题分析

### 1. 日志乱码问题

**现象**:

````
[2025-11-11 15:38:13] [INFO ] 鉁?閲嶈繛绾跨▼宸插惎鍔?```

**原因**:
- SE7 设备使用 UTF-8 编码
- Logger 可能使用了其他编码（如 GB2312）

**解决方案**:
- 确保 Logger 以 UTF-8 编码写入日志
- 在查看日志时指定正确编码

---

### 2. RTMP 推流无法播放

**现象**:
````

关闭 RTMP 推流器...
总推送帧数: 4464 ✅ 数据确实推送了
✅ RTMP 推流器已关闭

````

但播放器显示 **0 KB/s**，一直加载。

**根本原因**:

#### ❌ 问题1: 缺少 SPS/PPS 头信息

H.264 流必须包含 **SPS (Sequence Parameter Set)** 和 **PPS (Picture Parameter Set)**，否则解码器无法初始化。

**什么是 SPS/PPS？**
- **SPS**: 描述视频序列的全局参数（分辨率、帧率、色彩空间等）
- **PPS**: 描述图像参数（编码模式、量化参数等）
- **位置**: 通常在 IDR 帧（I 帧）之前发送

**DJI SDK 的行为**:
- `onH264Data()` 回调会返回完整的 NAL 单元，包括 SPS/PPS
- 但我们没有识别和提取它们

**NAL 类型**:
```cpp
0x67 (103) = SPS
0x68 (104) = PPS
0x65 (101) = IDR 帧 (I 帧)
0x61 (97)  = P 帧
````

#### ❌ 问题 2: 起始码解析错误

**代码问题**:

```cpp
uint8_t nalType = h264Data[4] & 0x1F;  // 假设起始码是 4 字节
```

**实际情况**:

- 4 字节起始码: `0x00 0x00 0x00 0x01` (常用于 SPS/PPS/IDR)
- 3 字节起始码: `0x00 0x00 0x01` (常用于 P/B 帧)

如果起始码是 3 字节，`h264Data[4]` 不是 NAL 类型字节！

#### ❌ 问题 3: 缺少 extradata（编码器参数）

FFmpeg 的 `codecParams_` 需要设置 `extradata`，包含 SPS/PPS:

```cpp
codecParams_->extradata = ...; // SPS + PPS 数据
codecParams_->extradata_size = ...;
```

这样 RTMP 接收端才能初始化解码器。

## 解决方案

### 方案 1: 使用 GStreamer（旧项目方案）

**优点**:

- `h264parse` 自动处理 SPS/PPS
- 代码简单，不需要手动解析 NAL

**管道示例**:

```bash
appsrc ! h264parse ! flvmux ! rtmpsink location="rtmp://..."
```

**缺点**:

- 依赖 GStreamer（已有）
- 与当前 FFmpeg 架构不一致

### 方案 2: 手动解析 H.264 NAL 单元（推荐）

**步骤**:

1. 解析每个 NAL 单元，识别 SPS/PPS/IDR/P 帧
2. 提取 SPS 和 PPS，设置到 `codecParams_->extradata`
3. 只在 IDR 帧前发送 SPS/PPS（或首次发送）
4. 正确计算 PTS/DTS

**实现**:

```cpp
class H264Parser {
public:
    struct NALUnit {
        enum Type {
            UNKNOWN = 0,
            P_FRAME = 1,
            IDR_FRAME = 5,
            SEI = 6,
            SPS = 7,
            PPS = 8
        };

        Type type;
        std::vector<uint8_t> data;
        int startCodeLength;  // 3 or 4
    };

    static std::vector<NALUnit> parseH264(const std::vector<uint8_t>& h264Data);
    static std::vector<uint8_t> buildExtradata(const std::vector<uint8_t>& sps,
                                                const std::vector<uint8_t>& pps);
};
```

## 技术细节

### H.264 NAL 单元结构

```
起始码 (3/4 字节)  NAL 头 (1 字节)  NAL 数据 (可变长度)
│                  │                │
0x00 0x00 0x01    0x67 (SPS)       ...数据...
0x00 0x00 0x00 0x01 0x68 (PPS)    ...数据...
0x00 0x00 0x00 0x01 0x65 (IDR)    ...帧数据...
0x00 0x00 0x01    0x61 (P帧)      ...帧数据...
```

**NAL 头结构** (1 字节):

```
7 6 5 4 3 2 1 0
│ │   │       │
│ │   │       └─ nal_unit_type (5 bits)
│ │   └───────── nal_ref_idc (2 bits)
│ └─────────────── forbidden_zero_bit (1 bit, must be 0)
```

### AVCC vs Annex B 格式

**Annex B** (DJI SDK 输出):

```
起始码 + NAL 单元 + 起始码 + NAL 单元 + ...
```

**AVCC** (MP4/FLV 内部):

```
长度 (4字节) + NAL 数据 + 长度 + NAL 数据 + ...
```

**RTMP 需要 AVCC 格式！** FFmpeg 的 `flvmux` 会自动转换，但需要正确的 `extradata`。

## 参考资料

### 八股文知识点

**Q: H.264 的 SPS 和 PPS 是什么？为什么必须发送？**

A:

- **SPS (Sequence Parameter Set)**: 序列参数集，描述视频序列的全局参数
  - 包含：图像宽高、色彩格式、参考帧数量、时序信息等
  - 作用：解码器初始化的必需信息
- **PPS (Picture Parameter Set)**: 图像参数集，描述图像的编码参数

  - 包含：熵编码模式、slice 分组、量化参数等
  - 作用：解码每个图像的必需信息

- **为什么必须发送？**

  - 解码器需要 SPS/PPS 才能正确解析 IDR 帧
  - 缺少 SPS/PPS 会导致解码器无法初始化
  - 播放器收到数据但无法解码，表现为 "0 KB/s" 或黑屏

- **何时发送？**
  - 流开始时（首个 IDR 帧之前）
  - 分辨率/帧率变化时
  - 解码器复位时
  - 某些编码器在每个 IDR 帧前都发送（冗余但安全）

**Q: RTMP 推流为什么需要 extradata？**

A:

- **extradata**: 编码器的额外参数数据，存储在容器头部
- **作用**: 让解码端在接收第一个帧前就能初始化解码器
- **内容**: 对于 H.264，包含 SPS 和 PPS (AVCC 格式)
- **格式**: AVCDecoderConfigurationRecord (ISO/IEC 14496-15)
  ```
  [0]    configurationVersion = 1
  [1]    AVCProfileIndication (从 SPS 提取)
  [2]    profile_compatibility
  [3]    AVCLevelIndication
  [4]    lengthSizeMinusOne (通常 = 3, 即 4 字节长度)
  [5]    numOfSequenceParameterSets (SPS 数量)
  [6-7]  SPS 长度
  [8...] SPS 数据
  [...]  numOfPictureParameterSets (PPS 数量)
  [...]  PPS 长度
  [...]  PPS 数据
  ```
