# 修复 RTMP 推流段错误 - 2025-11-18

## 📋 问题描述

### 现象

程序在 RTMP 推流 5160 帧（约 172 秒）后出现段错误:

```log
[INFO] RTMP 推流中: 已推送 5160 帧
Segmentation fault
```

同时伴随 GStreamer 警告:

```log
WARN h264parse broken/invalid nal Type: 1 Slice, Size: 9394 will be dropped
WARN flvmux Codec data for video stream not found, output might not be playable
ERROR GST_BUS Tried to add new watch while one was already there
```

---

## 🔍 诊断过程

### 步骤 1: 隔离变量 - 禁用 RTMP

**实验**: 设置 `video.rtmp.enabled=false`

**结果**:

- ✅ 无段错误 (运行正常)
- ✅ 数据接收正常 (60 帧,FPS=60)
- ✅ 队列管理正常
- ✅ 内存稳定

**结论**: **100% 确认问题在 RTMP 推流器**

---

### 步骤 2: 代码审查

通过详细分析 `RtmpStreamer.cpp`,发现两个 Bug:

#### Bug 1: GstBuffer 内存泄漏 ⚠️⚠️⚠️

**位置**: `RtmpStreamer::pushH264Frame()` (Line ~240)

**问题代码**:

```cpp
GstFlowReturn ret = gst_app_src_push_buffer(GST_APP_SRC(appsrc_), buffer);
if (ret != GST_FLOW_OK) {
    logger_.error("推送失败");
    return false;  // 🔴 BUG: buffer 未释放!
}
```

**GStreamer 内存管理规则**:

- `gst_app_src_push_buffer()` **成功** → GStreamer 接管 buffer 所有权
- `gst_app_src_push_buffer()` **失败** → 调用者必须释放 buffer

**问题链**:

```
DJI H.264 数据缺少 SPS/PPS
  ↓
GStreamer h264parse 拒绝所有帧
  ↓
gst_app_src_push_buffer() 返回 GST_FLOW_ERROR
  ↓
每次失败都泄漏一个 GstBuffer (~9KB)
  ↓
累积 6-7 帧后,野指针访问
  ↓
Segmentation fault 💥
```

---

#### Bug 2: 重复添加总线监听 ⚠️

**位置**:

- `RtmpStreamer::initialize()` (Line 137) - Lambda 版本
- `RtmpStreamer::createPipeline()` (Line 380) - onBusMessage 版本

**问题**: 同一个总线被添加了两次监听器

**后果**:

```log
ERROR GST_BUS Tried to add new watch while one was already there
```

每条 GStreamer 消息被处理两次,可能导致:

- 日志重复
- 回调中访问已释放对象
- 不确定的行为

---

## 🔧 修复方案

### 修复 Bug 1: 添加 buffer 释放

```cpp
// RtmpStreamer.cpp (Line ~240)

// 推送到 appsrc
GstFlowReturn ret = gst_app_src_push_buffer(GST_APP_SRC(appsrc_), buffer);
if (ret != GST_FLOW_OK) {
    logger_.error("推送 H.264 帧失败: GstFlowReturn = " + std::to_string(ret));

    // 🔧 关键修复: push_buffer 失败时,GStreamer 不会接管 buffer 所有权
    // 必须手动释放,否则会导致内存泄漏和野指针访问
    gst_buffer_unref(buffer);

    return false;
}

// 📌 注意: push_buffer 成功后,GStreamer 已接管 buffer 所有权
// 不需要也不能调用 gst_buffer_unref(buffer)
```

**原理**:

- **成功时**: GStreamer 内部会在适当时机自动调用 `gst_buffer_unref()`
- **失败时**: GStreamer 未接管,调用者负责释放

---

### 修复 Bug 2: 移除重复监听

```cpp
// RtmpStreamer.cpp (Line ~137)

// 启动管道
GstStateChangeReturn ret = gst_element_set_state(pipeline_, GST_STATE_PLAYING);
if (ret == GST_STATE_CHANGE_FAILURE) {
    logger_.error("启动 GStreamer 管道失败");
    cleanup();
    return false;
}

// 🔧 修复: 移除重复的总线监听
// 总线监听已在 createPipeline() 中通过 onBusMessage 函数添加
// 这里的 Lambda 版本是重复的

// ❌ 删除此重复代码:
// GstBus* bus = gst_element_get_bus(pipeline_);
// gst_bus_add_watch(bus, [...] {}, this);  // 重复!
// gst_object_unref(bus);

initialized_ = true;
```

## 📚 技术知识点

### GStreamer Buffer 内存管理

#### 基本规则

| 函数                        | 成功                    | 失败             |
| --------------------------- | ----------------------- | ---------------- |
| `gst_buffer_new_allocate()` | 调用者拥有 (refcount=1) | -                |
| `gst_app_src_push_buffer()` | GStreamer 接管          | **调用者仍拥有** |
| `gst_buffer_unref()`        | refcount-1              | -                |

#### 正确模式

```cpp
// 1. 创建 buffer
GstBuffer* buffer = gst_buffer_new_allocate(...);  // refcount = 1

// 2. 填充数据
gst_buffer_map(...);
memcpy(...);
gst_buffer_unmap(...);

// 3. 推送
GstFlowReturn ret = gst_app_src_push_buffer(src, buffer);

if (ret == GST_FLOW_OK) {
    // ✅ GStreamer 接管,不需要 unref
    // buffer 会在管道处理完后自动释放
} else {
    // ❌ GStreamer 拒绝,我们仍然拥有
    gst_buffer_unref(buffer);  // 必须手动释放!
}
```

#### 错误模式

```cpp
// ❌ 错误 1: 成功后也 unref (双重释放)
if (ret == GST_FLOW_OK) {
    gst_buffer_unref(buffer);  // 💥 崩溃!
}

// ❌ 错误 2: 失败后不 unref (内存泄漏)
if (ret != GST_FLOW_OK) {
    return false;  // 💧 泄漏!
}
```

### 总线监听去重

#### 问题代码

```cpp
// initialize() 中

// createPipeline() 中
```

**后果**: GStreamer 错误 "already there"

#### 正确做法

**方案 1**: 只在一个地方添加

```cpp

busWatchId_ = gst_bus_add_watch(bus_, onBusMessage, this);

// initialize() 中不添加
```

**方案 2**: 先移除旧的

```cpp
if (busWatchId_ > 0) {
    g_source_remove(busWatchId_);  // 移除旧监听
}
busWatchId_ = gst_bus_add_watch(bus_, onBusMessage, this);
```

## 🎓 面试八股

### Q1: 什么是内存泄漏?如何检测?

**定义**:
程序分配的内存在不再使用后未被释放,导致可用内存逐渐减少。

**检测方法**:

1. **Valgrind** (最常用)

   ```bash
   valgrind --leak-check=full ./program
   ```

2. **观察内存增长**

   ```bash
   watch -n 1 "ps aux | grep program"
   ```

3. **代码审查**: 检查 `new` vs `delete`, `malloc` vs `free`

**本项目案例**:

- 每帧泄漏 9KB
- 30 FPS → 每秒泄漏 270KB
- 172 秒后累积 46MB → 触发段错误

---

### Q2: GStreamer 的引用计数机制是什么?

**核心概念**:
GStreamer 使用 **引用计数** (Reference Counting) 管理对象生命周期。

**规则**:

- 对象创建时 `refcount = 1`
- 每次 `ref()` → `refcount++`
- 每次 `unref()` → `refcount--`
- `refcount == 0` → 自动释放

**所有权转移**:

```cpp
// 创建 buffer (我拥有)
GstBuffer* buf = gst_buffer_new();  // refcount = 1

// 交给 GStreamer (转移所有权)
gst_app_src_push_buffer(src, buf);  // GStreamer 接管

// 此时不能再访问 buf!
```

**本项目问题**:
push 失败时所有权未转移,但我们没有 `unref` → 泄漏

---

### Q3: 如何避免野指针?

**定义**:
指向已释放内存的指针。

**预防措施**:

1. **释放后置空**

   ```cpp
   delete ptr;
   ptr = nullptr;  // 防止野指针
   ```

2. **智能指针** (C++11+)

   ```cpp
   std::unique_ptr<int> ptr = std::make_unique<int>(42);
   // 自动释放,无野指针
   ```

3. **RAII 原则**
   - Resource Acquisition Is Initialization
   - 构造时获取,析构时释放

**本项目问题**:

- 泄漏的 GstBuffer 指向的内存可能被重用
- 后续访问 → 野指针 → 段错误
