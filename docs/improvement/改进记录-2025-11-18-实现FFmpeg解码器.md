## 🔧 技术细节

### **1. AVCodecParserContext 的核心作用**

**问题**: DJI Liveview 提供的 H.264 流缺少 SPS/PPS 头

**解决方案**: 使用 `av_parser_parse2()` 自动提取

```cpp
// 创建 Parser
pParser_ = av_parser_init(AV_CODEC_ID_H264);

// 解析字节流
int processedLen = av_parser_parse2(
    pParser_,         // Parser 上下文
    pCodecCtx_,       // 解码器上下文 (Parser 填充 extradata)
    &pkt.data,        // 输出: 完整帧
    &pkt.size,        // 输出: 帧大小
    pData,            // 输入: 原始字节流
    remainingLen,     // 输入: 长度
    AV_NOPTS_VALUE, AV_NOPTS_VALUE, AV_NOPTS_VALUE
);

// Parser 自动完成:
// 1. 扫描 NAL 起始码 (0x00 0x00 0x00 0x01)
// 2. 识别 NAL 类型 (SPS=7, PPS=8, Slice=1/5)
// 3. 提取 SPS/PPS → pCodecCtx->extradata
// 4. 输出完整帧 → pkt.data
```

**关键理解**:

- Parser **不解码**像素,只分析结构
- Decoder **解码**像素 (H.264 → YUV)
- Parser 是 DJI 视频流能正常工作的**关键**!

---

### **2. H.264 NAL 单元类型**

| Type  | 名称            | 描述           | 重要性 (NRI) | Parser 处理          |
| ----- | --------------- | -------------- | ------------ | -------------------- |
| 1     | Slice (Non-IDR) | P/B 帧         | 1-2          | 输出到 pkt.data      |
| 5     | Slice (IDR)     | I 帧           | 3            | 输出到 pkt.data      |
| 6     | SEI             | 补充信息       | 0            | 跳过或缓存           |
| **7** | **SPS**         | **序列参数集** | **3**        | **提取到 extradata** |
| **8** | **PPS**         | **图像参数集** | **3**        | **提取到 extradata** |

**NAL Header 结构**:

```
 7  6  5  4  3  2  1  0
+--+-----+-------------+
|F | NRI |    Type     |
+--+-----+-------------+
 1   2        5 位
```

**提取 NAL 类型**:

```cpp
const uint8_t* nalStart = data + 4;  // 跳过起始码 00 00 00 01
uint8_t nalType = nalStart[0] & 0x1F;  // 低 5 位
```

### **3. 解码流程**

```
DJI H.264 字节流
  ↓
av_parser_parse2()
  ├─ 提取 SPS/PPS → pCodecCtx->extradata
  └─ 输出完整帧 → pkt
  ↓
avcodec_decode_video2(pCodecCtx, pFrameYUV, &gotPicture, &pkt)
  ↓
YUV420P 帧
  ↓
sws_scale(pSwsCtx, pFrameYUV → pFrameRGB)
  ↓
RGB24 帧
  ↓
cv::cvtColor(rgbMat, bgrMat, cv::COLOR_RGB2BGR)
  ↓
cv::Mat (BGR24)
  ↓
回调用户 → 视觉检测
```

### **4. YUV420P 存储格式**

**1920x1080 图像**:

```
Y 平面 (亮度): 1920 x 1080 = 2,073,600 字节
U 平面 (色度): 960 x 540 = 518,400 字节  (宽高各减半)
V 平面 (色度): 960 x 540 = 518,400 字节
总计: 3,110,400 字节

对比 RGB24: 1920 x 1080 x 3 = 6,220,800 字节 (2 倍!)
```

**为什么用 YUV？**

1. **人眼特性**: 对亮度敏感,对色度不敏感
2. **色度采样**: U/V 减半存储,节省 50% 空间
3. **压缩效率**: YUV 更容易压缩

### **5. 线程安全设计**

**问题场景**:

```
线程 A (DJI 回调): 调用 decode()
线程 B (主线程): 调用 deinit()
```

**解决方案**:

```cpp
class H264Decoder {
private:
    mutable std::mutex decodeMutex_;

public:
    bool decode(...) {
        std::lock_guard<std::mutex> lock(decodeMutex_);
        // 解码逻辑...
    }

    void deinit() {
        std::lock_guard<std::mutex> lock(decodeMutex_);
        // 清理资源...
    }
};
```

**保护对象**: AVCodecContext, AVCodecParserContext (FFmpeg 不是线程安全的)

---

### **6. RAII 资源管理**

**释放顺序** (避免 use-after-free):

```cpp
void H264Decoder::deinit() {
    // 1. SwsContext (依赖 AVCodecContext)
    if (pSwsCtx_) sws_freeContext(pSwsCtx_);

    // 2. AVFrame (解码输出)
    if (pFrameYUV_) av_frame_free(&pFrameYUV_);
    if (pFrameRGB_) av_frame_free(&pFrameRGB_);

    // 3. RGB 缓冲区
    if (pRgbBuffer_) av_free(pRgbBuffer_);

    // 4. Parser (独立资源)
    if (pParser_) av_parser_close(pParser_);

    // 5. 解码器上下文 (最后释放)
    if (pCodecCtx_) {
        avcodec_close(pCodecCtx_);
        av_free(pCodecCtx_);
    }
}
```

**自动清理**:

```cpp
~H264Decoder() {
    deinit();  // 析构时自动清理
}
```

## 🎓 八股知识点汇总

### **知识点 1: AVCodecParserContext vs AVCodecContext**

**面试问题**: Parser 和 Decoder 有什么区别？

**标准答案**:

- **Parser (解析器)**: 分析流的**结构**,提取 NAL 单元,**不解码**像素
- **Decoder (解码器)**: 将 H.264 **解码**为像素数据 (YUV)

| 功能 | Parser                   | Decoder      |
| ---- | ------------------------ | ------------ |
| 输入 | 连续字节流               | NAL 单元     |
| 输出 | NAL 单元 (SPS/PPS/Slice) | YUV 帧       |
| 性能 | 极低 (<1ms)              | 高 (10-50ms) |

---

### **知识点 2: SPS/PPS 的作用**

**面试问题**: 什么是 SPS 和 PPS？为什么 H.264 需要它们？

**标准答案**:

- **SPS (Sequence Parameter Set)**: 视频序列参数

  - 分辨率 (width x height)
  - 帧率 (fps)
  - Profile/Level (编码复杂度)
  - 色度格式 (YUV420P)

- **PPS (Picture Parameter Set)**: 图像编码参数
  - 参考帧数量
  - 熵编码模式 (CAVLC/CABAC)
  - 去块滤波参数

**为什么需要？**

- 解码器需要这些参数才能正确解码
- 类似"视频流的身份证"
- 缺少 SPS/PPS 就像没有图纸的零件,无法组装

---

### **知识点 3: YUV420P vs RGB**

**面试问题**: 为什么 H.264 解码输出是 YUV 而不是 RGB？

**标准答案**:

**1. 人眼特性**

- 对亮度 (Y) 敏感
- 对色度 (U/V) 不敏感

**2. 色度采样** (节省空间)

```
YUV420P: Y 全采样, U/V 减半
  ├─ Y: 1920x1080
  ├─ U: 960x540  (减半)
  └─ V: 960x540  (减半)
  总计: 3.1 MB

RGB24: 全采样
  └─ RGB: 1920x1080x3
  总计: 6.2 MB (2 倍!)
```

**3. 压缩效率**

- YUV 可以独立压缩 Y/U/V 通道
- RGB 三通道耦合,压缩困难

---

### **知识点 4: 多线程解码**

**面试问题**: FFmpeg 如何实现多线程解码？

**标准答案**:

**配置**:

```cpp
pCodecCtx->thread_count = 4;  // 4 线程
pCodecCtx->thread_type = FF_THREAD_FRAME;  // 帧级并行
```

**工作原理**:

```
主线程:
  └─ Parser 解析 NAL → 提交任务到线程池

工作线程 1: 解码帧 N
工作线程 2: 解码帧 N+1
工作线程 3: 解码帧 N+2
工作线程 4: 解码帧 N+3

主线程:
  └─ 按顺序输出结果
```

**性能提升**:

- 单线程: 30 FPS → 80% CPU (单核)
- 4 线程: 30 FPS → 25% CPU (每核)

**限制**:

- B 帧需要参考帧,并行度受限
- I/P 帧可以完全并行

---

### **知识点 5: RAII 资源管理**

**面试问题**: 如何确保 FFmpeg 资源正确释放？

**标准答案**:

**RAII 原则** (Resource Acquisition Is Initialization):

```cpp
class H264Decoder {
public:
    ~H264Decoder() {
        deinit();  // 析构时自动清理
    }

    void deinit() {
        // 释放顺序: 从依赖者到被依赖者
        if (pSwsCtx_) sws_freeContext(pSwsCtx_);
        if (pFrameYUV_) av_frame_free(&pFrameYUV_);
        if (pParser_) av_parser_close(pParser_);
        if (pCodecCtx_) {
            avcodec_close(pCodecCtx_);
            av_free(pCodecCtx_);
        }
    }
};
```

**为什么这样设计？**

1. **异常安全**: 即使抛出异常,析构函数也会执行
2. **用户友好**: 用户忘记调用 deinit(),资源也能释放
3. **避免泄漏**: 智能指针语义,资源自动管理

---

### **知识点 6: 线程安全设计**

**面试问题**: 为什么 decode() 需要加锁？

**标准答案**:

**并发场景**:

```
线程 A (DJI 回调): decoder.decode(h264Data)
线程 B (主线程): decoder.deinit()
```

**问题**: AVCodecContext 不是线程安全的

- 如果并发访问,可能导致:
  - use-after-free (线程 B 释放,线程 A 使用)
  - 状态混乱 (线程 A 解码时,线程 B 修改状态)

**解决方案**:

```cpp
std::mutex decodeMutex_;

bool decode(...) {
    std::lock_guard<std::mutex> lock(decodeMutex_);
    // 解码逻辑 (独占访问)
}

void deinit() {
    std::lock_guard<std::mutex> lock(decodeMutex_);
    // 清理资源 (独占访问)
}
```

**性能考虑**: 锁粒度

- ❌ **粗粒度**: 锁住整个 decode() → 串行化,性能差
- ✅ **细粒度**: 只锁 FFmpeg API 调用 → 但实现复杂
- 📌 **项目选择**: 粗粒度 (简单,性能足够)
