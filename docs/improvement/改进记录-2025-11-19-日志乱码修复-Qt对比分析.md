# 改进记录 - 日志乱码修复与 Qt 对比分析

**日期**: 2025-11-19  
**作者**: GitHub Copilot  
**模块**: Core / Logger

## 1. 问题现象

用户反馈在 Windows 上查看由 Docker (Linux) 生成的日志文件时，中文字符显示为乱码（Mojibake）。
但用户指出：

1.  `config.json` 显示正常。
2.  **旧项目 (`esdk_on_sophon_old`) 的日志显示正常。**

## 2. 深度对比分析：为什么旧项目没问题？

经过对旧项目源码的分析，发现了根本原因：

### 旧项目 (Qt Framework)

- **源码**: `esdk_on_sophon_old/src/logger/LogManager.cpp`
- **核心类**: 使用了 `QFile` 和 `QTextStream`。
- **机制**:
  - Qt 的 `QTextStream` 是一个高级文本流类，它内部封装了复杂的编码处理逻辑。
  - Qt 默认使用 UTF-8，并且在处理跨平台文本文件时，通常会处理好 BOM (Byte Order Mark) 或者以一种 Windows 友好的方式写入。
  - 开发者不需要关心底层的字节序和编码标识，Qt 帮我们做了。

### 新项目 (Standard C++17)

- **源码**: `src/core/Logger.cpp`
- **核心类**: 使用了 `std::ofstream`。
- **机制**:
  - 标准 C++ 的文件流是非常底层的。当你写入 `std::string` 时，它只是忠实地将内存中的字节写入磁盘。
  - 在 Linux 下，默认是 UTF-8 (No BOM)。
  - **问题所在**: Windows 的记事本（Notepad）在打开没有 BOM 的文本文件时，默认会尝试猜测编码。如果文件开头是大量 ASCII 字符（如时间戳、日志级别），记事本往往会错误地猜测为 ANSI (GBK) 编码。
  - 当后续出现 UTF-8 中文字节时，在 GBK 模式下解析就变成了乱码。

## 3. 解决方案：手动模拟 Qt 的行为

既然我们为了减少依赖（去除了 Qt），改用了标准 C++，我们就需要手动做 Qt 默默帮我们做的事情：**添加 BOM**。

### 技术实现

1.  **BOM (Byte Order Mark)**:

    - UTF-8 的 BOM 是三个字节：`0xEF, 0xBB, 0xBF`。
    - 这就像是给文件戴了一顶"帽子"，告诉 Windows 记事本："我是 UTF-8 编码的，请按 UTF-8 解析我"。

2.  **代码改进 (`src/core/Logger.cpp`)**:
    - **移除 `std::locale`**: 之前的尝试使用了 `imbue` 设置 locale，但这在 Docker 这种精简 Linux 环境中往往无效甚至有害。我们现在回归最纯粹的字节流写入。
    - **强制写入 BOM**: 在 `open` 文件后，立即检查文件大小。如果是新文件（大小为 0），首先写入这 3 个字节。
    - **使用 `tellp()`**: 使用文件流指针位置判断文件是否为空，比 `fs::exists` 更准确，避免并发竞争。

```cpp
// 关键代码片段
logFile_.open(logFilePath_, std::ios::app | std::ios::out | std::ios::binary);

logFile_.seekp(0, std::ios::end);
if (logFile_.tellp() == 0) {
    const unsigned char bom[] = { 0xEF, 0xBB, 0xBF };
    logFile_.write(reinterpret_cast<const char*>(bom), sizeof(bom));
    logFile_.flush();
}
```

## 4. 验证与操作

**重要提示**:
代码修复只对**新创建**的文件有效。如果旧的乱码日志文件还存在，程序追加写入的内容虽然正确，但文件头依然缺失 BOM，Windows 依然会乱码。

**必须执行的操作**:
在编译运行新代码前，请删除旧日志：

```bash
rm -rf logs/*.log
```

## 5. 验证结果更新 (2025-11-19 16:40)

**验证情况**:

1.  **Windows 记事本 (Notepad)**: ✅ 显示正常。证明 BOM 已正确写入，文件格式为标准的 UTF-8。
2.  **MobaXterm 终端 (cat 命令)**: ✅ 显示正常。
3.  **MobaTextEditor (MobaXterm 自带编辑器)**: ❌ 依然显示乱码。

**结论**:
MobaTextEditor 在处理某些 UTF-8 文件时存在显示 Bug（即使有 BOM 也可能无法正确识别或渲染），但这不影响文件本身的正确性。以 Windows 记事本和终端显示为准。
