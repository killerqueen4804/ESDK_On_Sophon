# 改进记录 - 日志乱码修复

**日期**: 2025-11-19  
**作者**: GitHub Copilot  
**模块**: Core / Logger

## 1. 问题描述

用户反馈记录的日志文件在 Windows 环境下打开时出现乱码。

### 原因分析

1. **编码不匹配**:

   - Linux 环境（Docker/SE7）默认使用 UTF-8 编码。
   - Windows 环境下的文本编辑器（如 Notepad）如果未检测到 BOM (Byte Order Mark)，通常默认使用 ANSI (GBK) 编码打开。
   - 当 UTF-8 编码的中文字符被当作 GBK 解析时，就会显示为乱码。

2. **Locale 设置**:

   - Docker 容器中可能缺少 `zh_CN.UTF-8` locale，导致 `std::locale` 设置失败，回退到默认 locale (C/POSIX)，可能影响多字节字符的处理。

3. **追加写入问题**:
   - 如果日志文件已经存在且没有 BOM（例如由旧版本程序创建），新程序追加写入 UTF-8 内容时，整个文件仍然没有 BOM，Windows 依然会按 ANSI 打开。

## 2. 解决方案

### 2.1 代码修改 (`src/core/Logger.cpp`)

1. **增强 Locale 支持**:

   - 在设置 `zh_CN.UTF-8` 和 `en_US.UTF-8` 失败后，增加尝试 `C.UTF-8`。
   - `C.UTF-8` 是现代 Linux 发行版和容器中通用的 UTF-8 locale。

   ```cpp
   try {
       logFile_.imbue(std::locale("zh_CN.UTF-8"));
   } catch (...) {
       try {
           logFile_.imbue(std::locale("en_US.UTF-8"));
       } catch (...) {
           try {
               logFile_.imbue(std::locale("C.UTF-8")); // 新增
           } catch (...) {
               // 最后的降级方案
           }
       }
   }
   ```

2. **BOM 写入逻辑 (已存在)**:
   - 代码中已包含写入 UTF-8 BOM (`0xEF, 0xBB, 0xBF`) 的逻辑，但仅在**创建新文件**时生效。

### 2.2 操作建议

为了彻底解决现有日志文件的乱码问题，建议执行以下操作：

1. **删除旧日志**:

   - 删除 `logs/` 目录下现有的所有 `.log` 文件。
   - 这样下次运行程序时，会创建带有 BOM 的新日志文件，Windows 就能正确识别为 UTF-8。

   ```bash
   rm -rf logs/*.log
   ```

2. **查看方式**:
   - 推荐使用 VS Code 或 Notepad++ 打开日志文件，它们对 UTF-8 的识别更智能。
   - 如果必须使用 Windows 记事本，确保文件带有 BOM（通过上述步骤 1 保证）。

## 3. 验证方法

1. 重新编译程序。
2. 删除旧日志文件。
3. 运行程序产生新日志。
4. 将日志文件复制到 Windows，使用记事本打开，确认中文显示正常。
