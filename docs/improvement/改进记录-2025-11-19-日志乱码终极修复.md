# 改进记录 - 日志乱码终极修复

**日期**: 2025-11-19  
**作者**: GitHub Copilot  
**模块**: Core / Logger

## 1. 问题复盘

用户反馈即使在上次修复后，日志在 Windows 上依然显示乱码。但 `config.json` 和旧项目的日志显示正常。

### 深入分析

1.  **`imbue` 的副作用**:

    - 上次修复尝试使用 `logFile_.imbue(std::locale("zh_CN.UTF-8"))`。
    - 在 C++ 中，当使用 `std::ofstream` 写入 `std::string`（已经是 UTF-8 字节流）时，`imbue` 可能会导致流尝试进行不必要的编码转换，或者在环境缺少对应 locale 时导致流状态异常。
    - 尤其是在 Docker 容器这种精简环境中，locale 支持往往不完整。

2.  **旧项目对比**:

    - 旧项目使用 Qt (`QTextStream`)，默认处理得很好。
    - `config.json` 是标准的 UTF-8 文件（可能带 BOM）。

3.  **乱码根源**:
    - Windows 记事本（尤其是旧版）默认使用 ANSI (GBK) 编码打开文本文件，除非文件带有 BOM (Byte Order Mark) 或者内容特征非常明显。
    - 我们的日志文件虽然是 UTF-8 编码，但如果缺少 BOM，且开头是大量 ASCII 字符（时间戳、日志级别），记事本极易误判为 ANSI，导致后续的中文字符被错误解析为乱码。

## 2. 解决方案

**回归最纯粹的字节流写入**：

1.  **移除 `imbue`**:

    - 不再依赖系统的 locale 设置。
    - 直接将 UTF-8 编码的 `std::string` 作为字节流写入文件。这是 C++ 处理 UTF-8 的最佳实践之一（避免 `codecvt` 的复杂性）。

2.  **保留 BOM**:

    - 继续保留在**新文件创建时**写入 UTF-8 BOM (`0xEF, 0xBB, 0xBF`) 的逻辑。
    - 这是强制 Windows 记事本识别 UTF-8 的最可靠方法。

3.  **保留 Binary 模式**:
    - 使用 `std::ios::binary` 打开文件，确保写入的字节（包括 BOM 和换行符）不被系统修改。

## 3. 代码变更 (`src/core/Logger.cpp`)

- 移除了所有 `logFile_.imbue(...)` 调用。
- 移除了 `<locale>` 头文件引用。
- 保持了 BOM 写入逻辑。

## 4. 验证步骤（至关重要）

**必须删除旧日志文件！**

如果旧日志文件已经存在（且是乱码的），新程序追加写入的内容虽然正确，但文件头依然缺失 BOM，Windows 依然会按 ANSI 打开整个文件。

```bash
# 在 Docker 或设备终端中执行
rm -rf logs/*.log
```

然后重新编译运行。新生成的日志文件将带有 BOM 头，Windows 记事本应能完美识别。
