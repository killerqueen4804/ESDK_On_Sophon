## 📌 改进概述

### 问题发现

在设计 MediaFileTask 的工具层时，发生了两次重要的架构演进：

#### 第一次重构（v1.0）：功能提取

- **问题**: EXIF、GPS、事件缓存功能在 MediaFileTask 中重复
- **方案**: 提取为独立工具类 `ExifParser`、`GpsCalculator`、`EventCache`
- **结果**: ✅ 解决了代码重复问题

#### 第二次重构（v3.0）：功能聚合 ⭐

- **问题**: v1.0 的工具类粒度过细，导致文件数量爆炸
  - `ExifParser` 只做 EXIF 解析，未来需要图片缩放怎么办？
  - `GpsCalculator` 只做 GPS 计算，未来需要距离计算怎么办？
  - 10 个小功能 = 10 个头文件 → 维护困难
- **方案**: 将相关小功能聚合为大类

  - `ExifParser` → `ImageProcessor`（图片处理大类，10+ 方法）
  - `GpsCalculator` → `GeoUtils`（地理信息大类，15+ 方法）
  - `EventCache` → 保留（职责单一明确）

- **结果**: ✅ 既避免代码重复，又避免文件爆炸

## 🔧 具体改动

### 1. 创建 ImageProcessor 类

**文件**: `include/esdk_sophon/utils/ImageProcessor.h`

**设计理念**: 聚合所有图片相关操作

**核心功能**:

- EXIF 元数据解析（GPS、时间戳、相机参数）
- 图片缩放、裁剪、旋转
- 图片格式转换（JPEG、PNG、BMP）
- Base64 编码/解码
- 图片质量压缩
- 水印添加（预留）

**代码示例**:

```cpp
auto& processor = ImageProcessor::getInstance();

// EXIF 解析
auto metadata = processor.parseExif("photo.jpg");

// 图片缩放
auto resized = processor.resize(image, 800, 600);

// Base64 编码
std::string base64 = processor.encodeBase64(image);

// 压缩到指定大小
std::vector<uchar> buffer;
processor.compressToSize(image, 200, buffer);  // 200KB
```

**为什么不叫 ExifParser？**

> 因为图片处理不只有 EXIF 解析，还有缩放、编码、压缩等操作。如果每个功能一个类，会产生：
>
> - `ExifParser.h`
> - `ImageResizer.h`
> - `Base64Encoder.h`
> - `JpegCompressor.h`
> - `ImageRotator.h`
>
> → 5 个头文件，调用繁琐。
>
> `ImageProcessor` 聚合所有图片操作，一个类搞定！

---

### 2. 创建 GeoUtils 类

**文件**: `include/esdk_sophon/utils/GeoUtils.h`

**设计理念**: 聚合所有地理信息计算操作

**核心功能**:

- GPS 坐标转换（经纬度 → 像素坐标）
- 距离计算（Haversine、Vincenty）
- 区域判断（点是否在多边形内）
- 坐标系转换（WGS84、GCJ02、BD09）
- 轨迹分析（速度、方向、轨迹平滑）

**代码示例**:

```cpp
auto& geo = GeoUtils::getInstance();

// GPS → 像素坐标
auto pixel = geo.convertGpsToPixel(gpsCoord);

// 计算两点距离
double distance = geo.calculateDistance(p1, p2);

// 判断点是否在区域内
bool inside = geo.isPointInPolygon(point, polygon);

// 坐标系转换（WGS84 → GCJ02）
auto gcj02 = geo.convertCoordinate(wgs84,
                                  CoordinateSystem::WGS84,
                                  CoordinateSystem::GCJ02);

// 轨迹平滑
auto smoothed = geo.smoothTrajectory(trajectory);
```

**为什么不叫 GpsCalculator？**

> 因为地理信息不只有 GPS 计算，还有距离、区域、坐标转换、轨迹分析等。如果每个功能一个类：
>
> - `GpsCalculator.h`
> - `DistanceCalculator.h`
> - `AreaChecker.h`
> - `CoordinateConverter.h`
> - `TrajectoryAnalyzer.h`
>
> → 5 个头文件，功能分散。
>
> `GeoUtils` 聚合所有地理计算，统一调用！

### 3. 保留 EventCache 类

**文件**: `include/esdk_sophon/core/EventCache.h`

**设计理念**: 职责单一明确的核心服务

**为什么 EventCache 不聚合？**

## 📚 设计原则总结

### 类粒度设计三原则

#### 1. 高内聚原则（High Cohesion）

**定义**: 一个类的所有方法应该紧密相关，服务于同一个目标。

**判断标准**:

- 如果删除一个方法，其他方法是否仍然合理？
- 这些方法是否都操作相同的数据类型？
- 能否用一个词概括这个类？

**项目实例**:

```cpp
// ✅ 高内聚：ImageProcessor
class ImageProcessor {
    parseExif();    // 都是"图片处理"
    resize();
    encodeBase64();
};

// ❌ 低内聚：TaskManager
class TaskManager {
    startTask();        // 任务管理
    sendMqttEvent();    // MQTT 通信 ⚠️
    calculateGps();     // GPS 计算 ⚠️
};
```

#### 2. 功能聚合原则（Feature Aggregation）

**定义**: 将相关的小功能聚合到一个大类中，而不是每个小功能一个类。

**判断标准**:

- 功能是否属于同一主题？
- 功能是否操作相同数据类型？
- 功能是否在相同场景使用？
- 功能之间是否有依赖？

**项目实例**:

```cpp
// ❌ 过细粒度
class ExifParser { ... };
class ImageResizer { ... };
class Base64Encoder { ... };

// ✅ 合适粒度
class ImageProcessor {
    parseExif();
    resize();
    encodeBase64();
};
```

#### 3. 单一职责原则（Single Responsibility）

**定义**: 一个类应该只有一个变化的理由。

**判断标准**:

- 修改一个功能是否只影响这个类？
- 这个类是否有多个变化原因？

**项目实例**:

```cpp
// ✅ EventCache 职责单一：事件缓存
class EventCache {
    publishEvent();
    retryAll();
};

// ❌ 如果把 EventCache 合并到 ImageProcessor？
class ImageProcessor {
    parseExif();      // 变化原因 1：图片格式变化
    publishEvent();   // 变化原因 2：MQTT 协议变化 ⚠️
};
// → 违反 SRP
```

## 🎯 何时拆分，何时合并？

### 拆分类的信号 🚨

| 信号             | 示例                          | 解决方案           |
| ---------------- | ----------------------------- | ------------------ |
| **类过大**       | 一个类 > 1000 行代码          | 按职责拆分         |
| **职责混乱**     | TaskManager 又管任务又发 MQTT | 提取 MqttClient    |
| **多个变化原因** | 修改 GPS 逻辑影响图片处理     | 拆分为独立类       |
| **难以命名**     | TaskManagerMqttGpsHelper      | 职责不清晰，需拆分 |

### 合并类的信号 🚨

| 信号         | 示例                                                        | 解决方案              |
| ------------ | ----------------------------------------------------------- | --------------------- |
| **类过小**   | 一个类只有 1-2 个方法                                       | 合并到相关大类        |
| **紧密耦合** | ExifParser 总是和 ImageResizer 一起用                       | 合并为 ImageProcessor |
| **文件爆炸** | 10 个功能 = 10 个头文件                                     | 按主题合并            |
| **调用链长** | ExifParser::parse() → Resizer::resize() → Encoder::encode() | 合并为一个类          |

## 🎓 知识点积累

### 面试高频考点

**Q: 如何判断类的粒度是否合适？**

A: 我会从三个维度判断：

1. **内聚性**：类的所有方法是否围绕同一个主题？如果 `ImageProcessor` 里突然出现 `sendMqttEvent()`，就说明内聚性低。

2. **文件数量**：如果 10 个小功能产生 10 个头文件，说明粒度过细。我会将相关功能聚合为一个大类。

3. **变化频率**：如果修改一个小功能需要改多个类，说明职责分散。

**项目实例**：我们最初设计了 `ExifParser` 和 `GpsCalculator` 两个独立类，后来发现如果每个功能一个类，会产生 5-10 个头文件。于是重构为 `ImageProcessor`（图片处理）和 `GeoUtils`（地理信息）两个大类，每个类包含 10+ 个相关方法。
