### 💡 核心设计原则

1. **SOLID 原则**:

   - **S**RP (单一职责): 每个类只负责一件事

     - TaskService: 业务编排
     - TaskManager: 任务管理
     - ITask: 任务生命周期

   - **O**CP (开闭原则): 对扩展开放,对修改封闭

     - 新增任务类型: 继承 ITask,无需修改现有代码
     - 新增检测算法: 替换 Vision 实现,TaskService 无需改动

   - **L**SP (里氏替换): 派生类可以替换基类

     - LiveStreamTask 和 MediaFileTask 都可以赋值给 TaskPtr

   - **I**SP (接口隔离): 接口最小化

     - ITask 只定义任务必需的方法
     - TaskService 只定义业务编排方法

   - **D**IP (依赖倒置): 依赖抽象,不依赖具体
     - TaskService 依赖 Vision 和 MqttClient 接口,不依赖具体实现
     - TaskManager 依赖 ITask 接口,不依赖具体任务类

2. **设计模式应用**:
   - **Singleton**: TaskManager (Meyers' Singleton)
   - **Factory**: TaskManager::createTask() (简单工厂)
   - **Registry**: TaskManager 维护任务映射表
   - **Template Method**: ITask 定义生命周期框架
   - **Observer**: 回调机制 (std::function)
   - **Strategy**: 不同任务类型不同策略
   - **Pimpl**: TaskService 隐藏实现细节
   - **Dependency Injection**: 构造函数注入依赖

### 📚 学到的核心知识点

#### 1. **enum class** (强类型枚举)

- 类型安全: 不会隐式转换为 int
- 作用域隔离: 需要 `::` 访问,避免命名冲突
- 指定底层类型: `enum class State : uint8_t`

#### 2. **虚析构函数**

- 基类析构必须 `virtual`,否则多态删除时派生类资源泄漏
- `virtual ~ITask() = default` 明确表达意图

#### 3. **纯虚函数和抽象类**

- `virtual func() = 0` 强制派生类实现
- 抽象类不能实例化,只能作为接口

#### 4. **std::function 回调机制**

- 可以存储任何可调用对象 (函数、Lambda、Functor)
- Lambda 捕获外部变量: `[&count]` (引用), `[=]` (值)
- 底层原理: 类型擦除 (Type Erasure)

#### 5. **模板方法模式**

- 基类定义算法骨架,派生类实现细节
- `start()` 定义启动流程,`execute()` 由派生类实现

#### 6. **智能指针**

- `shared_ptr`: 共享所有权,引用计数
- `unique_ptr`: 独占所有权,零开销
- `make_shared`: 一次内存分配,性能更好

#### 7. **Pimpl 惯用法**

- 隐藏实现细节,减少编译依赖
- ABI 稳定性: 修改实现不影响二进制兼容性
- 缺点: 额外的内存分配和间接访问

#### 8. **Meyers' Singleton**

- C++11 线程安全单例: 局部静态变量
- 延迟初始化 + 自动析构
- 原理: 编译器保证静态变量初始化的线程安全

#### 9. **mutable 关键字**

- 允许在 const 函数中修改成员变量
- 典型场景: mutex, cache, 引用计数
- `mutable std::mutex mutex_` 用于 const 函数加锁

#### 10. **依赖注入**

- 通过构造函数注入依赖: `TaskService(vision, mqtt)`
- 优势: 可测试性、解耦、灵活性
- 符合 DIP (依赖倒置原则)

**讨论**: 用户提出 "六个组件是不是有点太多了"

**原始设计** (6 个组件):

1. MQTT Handler
2. Task Manager
3. Task (ITask)
4. Task Executor
5. Result Processor
6. MQTT Publisher

**优化后设计** (4 层架构):

1. Access Layer: MQTT Handler
2. Manager Layer: Task Manager + Task
3. **Service Layer**: Task Service (合并 Executor + Processor + Publisher)
4. Utility Layer: Vision, MQTT, Utils

**决策理由**:

- Task Executor 和 Result Processor 职责重叠,合并为 TaskService
- MQTT Publisher 作为工具类,由 TaskService 调用
- 减少类的数量,降低复杂度,但保持清晰的层次

**教训**:

- 架构设计要平衡复杂度和清晰度
- 听取用户反馈,及时调整设计
- "服务层" 的概念符合用户直觉

### 💡 核心设计原则

#### 1. **Pimpl 惯用法** (Pointer to Implementation)

**优势**:

- ✅ 编译隔离: 修改实现不影响头文件用户
- ✅ ABI 稳定性: 类内存布局不变
- ✅ 隐藏细节: 私有成员不暴露
- ✅ 减少依赖: 头文件不需要包含实现细节

**缺点**:

- ⚠️ 额外分配: new Impl() 带来开销
- ⚠️ 间接访问: impl\_->xxx 多一次解引用
- ⚠️ 代码复杂: 需要前向声明和 cpp 定义

**面试要点**:

- Q: 什么时候用 Pimpl?
- A: 库的公共 API、需要 ABI 稳定的代码 (如 Qt, Boost)


**优势**:

- ✅ 可测试性: 可以注入 Mock 对象

- ✅ 灵活性: 运行时可替换实现

#### 1. libcurl 的使用

**核心 API**:

```cpp

// 2. 设置选项
curl_easy_setopt(curl, CURLOPT_URL, "http://...");
```

**面试要点**:

- Q: libcurl 的回调函数为什么要返回接收的字节数？
- A: libcurl 用这个返回值判断是否成功处理数据。如果返回值不等于 `size * nmemb`，libcurl 认为出错并中止传输。

- Q: 多线程环境下使用 libcurl 需要注意什么？
- A:
  1. 全局初始化/清理只能在主线程调用一次
  2. 每个线程使用独立的 CURL 句柄
  3. 设置 `CURLOPT_NOSIGNAL` 避免信号处理问题
  4. 错误信息使用 `thread_local` 存储

```cpp
class CurlPool {
    std::queue<CURL*> pool_;
    std::mutex mutex_;

public:
    CURL* acquire() {
        std::lock_guard lock(mutex_);
        if (pool_.empty()) {
            return curl_easy_init();
        }
        CURL* handle = pool_.front();
        pool_.pop();
        return handle;
    }

    void release(CURL* handle) {
        curl_easy_reset(handle);  // 重置状态
        std::lock_guard lock(mutex_);
        pool_.push(handle);
    }
```

```cpp
    actualImagePath = "./" + uuid + ".jpg";
    cv::imwrite(actualImagePath, frame);
    needCleanup = true;
}

HttpClient::post(..., actualImagePath);
if (needCleanup) std::remove(actualImagePath.c_str());
```

**优点**:

- ✅ 节省磁盘 I/O
- ✅ 保留原始文件名
- ✅ 业务逻辑更清晰

**缺点**:

- 代码稍复杂（多一个条件分支）

**决策**: 选择方案 B（性能和可维护性更优）

### 📋 改进背景

用户审查 Day 3 补充的代码后，发现一个重要问题：

**问题描述**:

- DJI Edge-SDK 的 `MediaFile` 结构有 `file_name` 字段

- 导致 GPS 计算时只能使用 `config.mediaPath`，而不是具体的文件名


### 📚 本次学到的知识

#### 1. 接口设计的演进

**接口演进过程**:

```cpp
// 版本1: 最初设计（Day 2）
bool processFrame(const cv::Mat& frame, const TaskConfig& config);
// 问题：无法传递文件名

// 版本2: Day 3 补充（使用 config.mediaPath）
std::string imagePath = (config.source == DataSource::MEDIAFILE)
                        ? config.mediaPath : "";
// 问题：mediaPath 是配置路径，不是具体文件名

// 版本3: Day 3 补充 2（添加 fileName 参数）✅
bool processFrame(const cv::Mat& frame,
                 const TaskConfig& config,
                 const std::string& fileName = "");
// 优势：配置与状态分离，接口清晰
```

**设计原则**:

- **接口稳定性**: 使用默认参数保持向后兼容
- **职责单一**: `TaskConfig` 只负责配置，不包含运行时状态
- **依赖倒置**: 调用者决定传递什么文件名，服务层只使用

#### 2. 配置 vs 状态的区别

**配置数据 (Configuration)**:

- 定义：在任务启动前确定，整个任务期间不变
- 示例：`confidenceThreshold`, `reportIntervalSec`, `mediaPath`
- 存储：`TaskConfig` 结构体

**运行时状态 (Runtime State)**:

- 定义：任务运行过程中动态变化
- 示例：当前处理的文件名 (`file.file_name`)、当前帧号、检测结果
- 传递：通过函数参数传递

**为什么不把 `currentFileName` 放入 `TaskConfig`？**

| 原因         | 说明                                    |
| ------------ | --------------------------------------- |
| 职责混乱     | 配置和状态混在一起，违反单一职责原则    |
| 线程安全问题 | 多线程共享 `TaskConfig`，修改会引发竞态 |
| 难以测试     | 测试时需要构造完整的 `TaskConfig`       |
| 不符合直觉   | 配置应该是"不变的"，文件名是"变化的"    |

#### 3. 默认参数的向后兼容性

**C++ 默认参数的优势**:

```cpp
// 旧代码（不需要修改）
service.processFrame(frame, config);  // ✅ 仍然有效

// 新代码（传递文件名）
service.processFrame(frame, config, "DJI_0123.JPG");  // ✅ 新功能
```

**面试要点**:

- Q: 默认参数和函数重载的区别？
- A: 默认参数更简洁，但只能从右到左指定；函数重载更灵活，但代码重复。

#### 4. 参数传递链的设计

**完整的数据流**:

```
┌─────────────────┐
│ MediaFileTask   │
│ (具体任务类)    │
└────────┬────────┘
         │ file.file_name = "DJI_0123.JPG"
         ▼
┌─────────────────┐
│ processFrame()  │  ⭐ 新增 fileName 参数
│ (业务编排层)    │
└────────┬────────┘
         │ fileName = "DJI_0123.JPG"
         ▼
┌─────────────────┐
│ buildEvent()    │  ⭐ 新增 fileName 参数
│ (事件构建层)    │
└────────┬────────┘
         │ imagePath = fileName
         ▼
┌─────────────────────┐
│ calculateGPSCoordinates() │  ⭐ 使用 imagePath
│ (GPS 计算层)              │
└───────────────────────────┘
```

**设计特点**:

- ✅ 层层传递，职责清晰
- ✅ 每一层只关心自己的输入输出
- ✅ 可测试性强（每层可独立测试）
