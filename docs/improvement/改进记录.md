### 知识点

#### 1. C++17 std::filesystem

**优点：**

- 跨平台：Windows 和 Linux 统一 API
- 面向对象：path 对象，操作符重载
- 功能完善：文件、目录、权限、时间等

**常用 API：**

```cpp
fs::create_directories()    // 创建多级目录
fs::exists()                // 检查存在性
fs::file_size()             // 获取文件大小
fs::last_write_time()       // 最后修改时间
fs::directory_iterator()    // 遍历目录
fs::remove()                // 删除文件
fs::path / "subdir"         // 路径拼接
```

#### 2. 日志轮转策略

| 策略     | 实现方式       | 优点             | 缺点                     |
| -------- | -------------- | ---------------- | ------------------------ |
| 按日期   | 每天一个文件   | 管理方便，易查找 | 某天日志可能很大         |
| 按大小   | 超过 N MB 切换 | 文件大小可控     | 文件数量不确定           |
| 混合策略 | 日期+大小      | 兼顾两者优点     | 实现稍复杂（本项目采用） |

**本项目策略：**

- 主策略：按日期轮转（每天一个文件）
- 辅助策略：单文件超过 100MB 时添加序号
- 清理策略：只保留最近 15 天

**文件命名示例：**

```
logs/
├── esdk_sophon_2025-10-10.log (15天前，自动删除)
├── esdk_sophon_2025-10-24.log
├── esdk_sophon_2025-10-25.log       (当天)
└── esdk_sophon_2025-10-25_001.log   (文件过大，序号轮转)
```

#### 3. 时间处理进阶

**日期格式化：**

```cpp
std::put_time(std::localtime(&now_c), "%Y-%m-%d")       // 2025-10-25
std::put_time(std::localtime(&now_c), "%Y-%m-%d %H:%M:%S")  // 2025-10-25 16:30:45
```

**时间计算：**

```cpp
auto cutoffTime = now - std::chrono::hours(24 * 15);  // 15天前
```

**文件时间转换（C++17）：**

```cpp
auto fileTime = fs::last_write_time(entry.path());
// 转换为system_clock时间（用于比较）
auto sctp = std::chrono::time_point_cast<std::chrono::system_clock::duration>(
    fileTime - fs::file_time_type::clock::now() + std::chrono::system_clock::now()
);
```

> **注意**：C++20 提供了更简单的 file_time 转换方式

#### 4. RAII 在文件管理中的应用


### 遇到的问题及解决方案

#### 问题 1：std::filesystem 编译链接

**问题描述：**
某些旧版编译器需要显式链接`-lstdc++fs`

**解决方案：**
使用`readelf -d`检查依赖，发现 GCC 9.4 已将 filesystem 包含在 libstdc++.so.6 中，无需额外链接。

```bash
# 检查命令
readelf -d test_logger | grep NEEDED

# 输出包含libstdc++.so.6，说明已链接
NEEDED   Shared library: [libstdc++.so.6]
```

#### 问题 2：文件时间转换复杂

**问题描述：**
C++17 的`fs::file_time_type`与`std::chrono::system_clock`不兼容

**解决方案：**
使用时间点转换（C++17 方式）：

```cpp
auto sctp = std::chrono::time_point_cast<std::chrono::system_clock::duration>(
    fileTime - fs::file_time_type::clock::now() + std::chrono::system_clock::now()
);
```

> C++20 可用`std::chrono::file_clock::to_sys()`简化

#### 问题 3：配置硬编码

**当前方案：**
使用 constexpr 硬编码配置，方便快速实现和测试

### 面试要点总结

#### Q1: 如何管理日志文件，避免磁盘占满？

**答案：**

1. **按日期轮转**：每天一个日志文件，便于管理和查找
2. **文件大小限制**：单文件超过 100MB 自动切换（添加序号）
3. **定期清理**：只保留最近 N 天（如 15 天）的日志
4. **日志级别控制**：生产环境关闭 DEBUG 级别
5. **日志压缩**（可选）：旧日志压缩为.gz 格式，节省 70-90%空间

#### Q2: C++17 std::filesystem vs 传统 C API？

**答案：**

| 特性     | std::filesystem      | C API (stat/opendir)  |
| -------- | -------------------- | --------------------- |
| 跨平台   | ✅ 统一接口          | ❌ Windows/Linux 不同 |
| 类型安全 | ✅ 强类型            | ❌ 弱类型             |
| 易用性   | ✅ 面向对象          | ❌ C 风格，复杂       |
| 标准化   | ✅ C++17 标准        | ❌ POSIX 标准         |
| 示例     | `fs::exists("file")` | `stat("file", &st)`   |

**推荐**：优先使用 std::filesystem（C++17 及以上）

#### Q3: 日志轮转的实现要点？

**答案：**

1. **日期检测**：每次写入前检查日期是否变化
2. **文件切换**：关闭旧文件 → 生成新路径 → 打开新文件
3. **线程安全**：切换过程加锁，保证原子性
4. **轮转标记**：新文件写入轮转信息，便于追踪
5. **异常处理**：文件操作失败时的容错处理

#### Q4: 如何优化日志性能？

**答案：**

1. **缓冲写入**：积累一定量后 flush，减少系统调用
2. **异步日志**：独立线程写入，避免阻塞主线程
3. **无锁队列**：使用 lock-free queue 传递日志消息
4. **级别过滤**：早期过滤，避免不必要的格式化
5. **批量 flush**：定时 flush 而非每次都 flush

**本项目当前实现**：每次 flush（实时性优先），后续可优化

### 知识点

#### 1. 单例模式（Meyers Singleton）

```cpp
class Logger {
public:
    static Logger& getInstance() {
        static Logger instance;  // C++11保证线程安全
        return instance;
    }
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
private:
    Logger() {}
};
```

#### 2. Pimpl 惯用法

```cpp
class Logger {
private:
    class Impl;                    // 前向声明
    std::unique_ptr<Impl> pImpl_;  // 指向实现的智能指针
};
```

**优势**: 隐藏实现细节、减少编译依赖、加快编译速度

#### 3. RAII 原则

```cpp
class Logger {
public:
    Logger() { logFile_.open("app.log"); }     // 构造时获取资源
    ~Logger() { if (logFile_.is_open()) logFile_.close(); }  // 析构时释放
private:
    std::ofstream logFile_;
};
```

#### 4. CMake 依赖传递（PUBLIC/PRIVATE/INTERFACE）

```cmake
# PUBLIC: 当前需要 + 传递给依赖者
target_link_libraries(mqtt PUBLIC core)

# PRIVATE: 只有当前需要
target_link_libraries(mqtt PRIVATE ThirdParty::Qt5Mqtt)

# INTERFACE: 当前不需要 + 传递给依赖者
add_library(vision INTERFACE)
target_link_libraries(vision INTERFACE detector segmentation stream)
```

#### 5. 工厂模式 + 策略模式

```cpp
// 策略模式：抽象接口
class IDetector {
public:
    virtual DetectionResult detect(const cv::Mat& image) = 0;
};

// 工厂模式：创建对象
class DetectorFactory {
public:
    enum class Type { YOLOV10, YOLOV8 };
    static std::unique_ptr<IDetector> create(Type type);
};
```

#### 6. Repository 模式

```cpp
class Database {
public:
    // 面向业务对象的接口
    bool saveDetectionResult(const DetectionResult& result);
    std::vector<DetectionResult> getResults(const TimeRange& range);
};
```

#### 7. 命令模式

```cpp
class ICommand {
public:
    virtual void execute() = 0;
    virtual void undo() = 0;
};

class TakeOffCommand : public ICommand {
    void execute() override { drone_->takeOff(); }
    void undo() override { drone_->land(); }
};
```

#### 8. INTERFACE 库（CMake）

```cmake
add_library(vision INTERFACE)  # 不包含源文件
target_link_libraries(vision INTERFACE detector segmentation stream)
```

**作用**: 组合多个子模块，简化上层链接

### 面试要点

| 问题                          | 标准答案                                                   |
| ----------------------------- | ---------------------------------------------------------- |
| **PUBLIC vs PRIVATE?**        | 公共接口类型用 PUBLIC 传递，内部实现用 PRIVATE 隐藏        |
| **C++11 单例为什么线程安全?** | 静态局部变量初始化时编译器自动加锁，C++11 标准保证         |

| **静态库 vs 动态库?**         | 静态库编译时链接，动态库运行时加载；本项目用静态库简化部署 |

### 代码示例

**现代 CMake 推荐写法**:

```cmake
# 创建库
add_library(mylib STATIC utils.cpp)

# 设置属性（target_*命令）
target_include_directories(mylib
    PUBLIC include/   # 公共接口
    PRIVATE src/      # 内部实现
)

# 链接库（自动传递PUBLIC属性）

```

### 知识点

#### 1. CMake 核心概念

- **Target（目标）**: 要生成的可执行文件或库
- **Source（源文件）**: .cpp 文件
- **Header（头文件）**: .h 文件
- **Library（库）**: 静态库(.a)或动态库(.so)

#### 2. 重要目录变量

- `CMAKE_SOURCE_DIR`: 源码根目录
- `CMAKE_BINARY_DIR`: 构建目录
- `PROJECT_SOURCE_DIR`: project()所在目录
- `CMAKE_CURRENT_SOURCE_DIR`: 当前 CMakeLists.txt 所在目录

#### 3. 现代 CMake 特点

- 使用 target\_\*命令代替全局命令
- 明确指定可见性（PUBLIC/PRIVATE/INTERFACE）
- 模块化组织（add_subdirectory）
- 避免 file(GLOB)自动查找文件

#### 4. 可见性修饰符

- **PRIVATE**: 仅当前目标使用
- **PUBLIC**: 当前目标和链接它的目标都使用
- **INTERFACE**: 仅链接它的目标使用

### 面试要点

**Q1: CMakeLists.txt 和 Makefile 的区别？**
A: CMakeLists.txt 是跨平台的配置文件，Makefile 是 CMake 根据平台生成的具体构建脚本。

**Q2: 静态库和动态库的区别？**
A:

- 静态库(.a/.lib): 编译时链接到可执行文件中，程序体积大，无运行时依赖
- 动态库(.so/.dll): 运行时加载，程序体积小，多个程序可共享

**Q3: PUBLIC、PRIVATE、INTERFACE 的使用场景？**
A:

- PRIVATE: 内部实现，不暴露给用户
- PUBLIC: 公共接口，用户也需要
- INTERFACE: header-only 库，自己不用但用户需要

**Q4: 为什么不推荐 file(GLOB)？**
A: 因为添加新文件后需要重新运行 cmake，CMake 无法自动追踪依赖关系。明确列出文件更可靠。

- 开发/测试/生产共用同一份代码

#### 2. 降级方案

```cpp
// Config未加载时，Logger仍能正常工作
Logger::getInstance().info("即使Config失败也能运行");
```

#### 3. 依赖解耦

```
Logger 尝试读取 Config
    ↓
Config未初始化？
    ↓
使用默认值继续运行 ✓
```

**不强制依赖：** Logger 不要求 Config 必须初始化

### 关键知识点

#### 1. 配置驱动设计模式

**核心思想：**

- 配置与代码分离
- 运行时可调整
- 提供合理的默认值

#### 2. 降级方案（Fallback Pattern）

```cpp
try {
    // 尝试从Config读取
    logDir = config.getString("logger.log_directory", "logs");
} catch (...) {
    // 失败则使用默认值
    logDir = DEFAULT_LOG_DIRECTORY;
}
```

#### 3. 依赖注入思想

Logger 不直接依赖 Config，而是：

1. 尝试读取配置
2. 如果失败，使用默认值
3. 实现解耦，提高容错性

### 面试要点

**Q1: 为什么要用配置驱动而不是硬编码？**

1. 灵活性：无需重新编译
2. 可维护性：配置集中管理
3. 环境适配：开发/测试/生产不同配置
4. 降级方案：配置缺失时使用默认值
5. 运行时可调：支持热更新

**Q2: Logger 如何实现配置驱动？**

1. 构造函数中调用 `loadConfigSettings()`
2. 从 `Config::getInstance()` 读取配置项
3. 提供默认值作为降级方案
4. 将读取的配置存储为成员变量
5. 所有逻辑使用成员变量而非硬编码常量

**Q3: Config 未初始化会导致 Logger 失败吗？**
不会！Logger 采用 try-catch 捕获异常，如果 Config 读取失败：

1. 捕获异常
2. 使用 DEFAULT\_\* 常量作为默认值
3. 记录警告信息
4. 继续正常运行
