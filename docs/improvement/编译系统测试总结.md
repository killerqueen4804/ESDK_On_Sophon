## 🔧 遇到的问题和解决方案

### 问题 1: CMakeLists.txt 中交叉编译配置缺失

**错误现象**:

```
需要手动指定 -DCMAKE_TOOLCHAIN_FILE=...
```

**根本原因**:  
旧项目直接在 CMakeLists.txt 中配置交叉编译，新项目使用了分离的 toolchain 文件

**解决方案**:

```cmake
# 在CMakeLists.txt开头直接配置（project()之前）
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER /usr/bin/aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER /usr/bin/aarch64-linux-gnu-g++)
```

**教学要点**:

- 交叉编译配置必须在`project()`之前
- 有两种方式：1) 单独 toolchain 文件 2) 直接写在 CMakeLists.txt
- 本项目选择方式 2：简化操作，与旧项目保持一致

### 问题 2: add_definitions 使用了生成器表达式

**错误现象**:

```
error: ../src/utils/TimeUtils.cpp../src/utils/TimeUtils.cppCONFIG:Debug: No such file or directory
```

**根本原因**:

```cmake
# ❌ 错误写法
add_definitions($<$<CONFIG:Debug>:-DDEBUG>)
```

`add_definitions()`不支持生成器表达式（generator expressions）

**解决方案**:

```cmake
# ✅ 正确写法
set(CMAKE_CXX_FLAGS_DEBUG "-g -O0 -DDEBUG")
```

**教学要点**:

- `add_definitions()`: 只支持简单的宏定义
- `add_compile_options()`: 支持生成器表达式
- `CMAKE_CXX_FLAGS_DEBUG`: 特定配置的编译选项

### 问题 3: 第三方库 target 命名大小写不一致

**错误现象**:

```
Target "storage" links to target "ThirdParty::Libssh2" but the target was not found
```

**根本原因**:

- 定义: `ThirdParty::libssh2` (小写)
- 使用: `ThirdParty::Libssh2` (大写 L)

**解决方案**:
统一使用小写命名：

```cmake
ThirdParty::libssh2   # ✅
ThirdParty::libexif   # ✅
ThirdParty::exiv2     # ✅
```

**教学要点**:

- CMake 的 target 名称是大小写敏感的
- 建议：第三方库使用全小写，避免混淆
- 遵循命名规范：`ThirdParty::库名`

### 问题 4: ESDK 库类型错误（SHARED vs STATIC）

**错误现象**:

```
No rule to make target '../third_party/esdk/lib/aarch64/libedgesdk.so'
```

**根本原因**:
实际文件是`libedgesdk.a`（静态库），但 CMake 配置为 SHARED（动态库）

**解决方案**:

```cmake
# ❌ 错误
add_library(ThirdParty::ESDK SHARED IMPORTED GLOBAL)
set_target_properties(ThirdParty::ESDK PROPERTIES
    IMPORTED_LOCATION "${THIRD_PARTY_ROOT}/esdk/lib/aarch64/libedgesdk.so"
)

# ✅ 正确
add_library(ThirdParty::ESDK STATIC IMPORTED GLOBAL)
set_target_properties(ThirdParty::ESDK PROPERTIES
    IMPORTED_LOCATION "${THIRD_PARTY_ROOT}/esdk/lib/aarch64/libedgesdk.a"
)
```

**教学要点**:

- 静态库：`.a` (Linux), `.lib` (Windows)
- 动态库：`.so` (Linux), `.dll` (Windows)
- CMake 配置必须匹配实际文件类型

### 问题 5: 动态库符号链接缺失

**错误现象**:

```
No rule to make target '../third_party/gst/lib/libgstreamer-1.0.so'
```

**根本原因**:
实际文件：`libgstreamer-1.0.so.0.1603.0`（带版本号）  
CMake 期望：`libgstreamer-1.0.so`（标准名称）

**解决方案**:

```bash
# 创建符号链接
cd third_party/gst/lib
ln -sf libgstreamer-1.0.so.0.1603.0 libgstreamer-1.0.so
ln -sf libgstapp-1.0.so.0.1603.0 libgstapp-1.0.so
ln -sf libgobject-2.0.so.0.6400.6 libgobject-2.0.so
ln -sf libglib-2.0.so.0.6400.6 libglib-2.0.so

cd ../../exiv2/lib
ln -sf libexiv2.so.1.00.0.9 libexiv2.so

cd ../../libexif/lib
ln -sf libexif.so.12.3.4 libexif.so

cd ../../minizip/lib
ln -sf libminizip.so.4.0.9 libminizip.so
```

**教学要点**:

- Linux 动态库通常有三个名称：
  1. 实际文件：`libXXX.so.1.2.3` (带完整版本号)
  2. soname：`libXXX.so.1` (主版本号)
  3. linker name：`libXXX.so` (链接时使用)
- CMake 链接时使用 linker name
- 使用符号链接解决版本号问题

### 问题 6: 缺少头文件

**错误现象**:

```
fatal error: esdk_sophon/core/Config.h: No such file or directory
fatal error: MessageQueue.h: No such file or directory
```

**根本原因**:
只创建了.cpp 文件，没有创建对应的.h 头文件

**解决方案**:

- `include/esdk_sophon/core/Config.h`
- `include/esdk_sophon/core/Application.h`

- `src/mqtt/MessageQueue.h`

- 公共接口头文件：放在`include/esdk_sophon/模块名/`
- 私有实现头文件：放在`src/模块名/`
- 头文件位置影响`#include`路径

## 📚 关键知识点总结

### 1. 交叉编译配置

**Q: 为什么交叉编译配置要在 project()之前？**

A: CMake 在执行`project()`时会检测编译器和系统信息。
如果在`project()`之后设置，CMake 已经使用了默认编译器（x86），再改就晚了。

```cmake
# ✅ 正确顺序
cmake_minimum_required(VERSION 3.10)

# 1. 交叉编译配置
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)

# 2. 项目定义
project(ESDK_Sophon CXX)

# ❌ 错误顺序
cmake_minimum_required(VERSION 3.10)
project(ESDK_Sophon CXX)  # 此时已用默认编译器
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)  # 太晚了！
```

### 2. IMPORTED 库类型

**Q: STATIC vs SHARED IMPORTED 库有什么区别？**

A:
| 特性 | STATIC | SHARED |
|------|--------|--------|
| 文件扩展名 | `.a` (Linux), `.lib` (Windows) | `.so` (Linux), `.dll` (Windows) |
| 链接方式 | 静态链接，代码嵌入可执行文件 | 动态链接，运行时加载 |
| 可执行文件大小 | 大 | 小 |
| 部署 | 简单（单文件） | 复杂（需要.so 文件） |
| 更新库 | 需要重新编译 | 替换.so 即可 |

```cmake
# 静态库
add_library(ThirdParty::ESDK STATIC IMPORTED GLOBAL)
set_target_properties(ThirdParty::ESDK PROPERTIES
    IMPORTED_LOCATION "/path/to/libedgesdk.a"
)

# 动态库
add_library(ThirdParty::OpenCV SHARED IMPORTED GLOBAL)
set_target_properties(ThirdParty::OpenCV PROPERTIES
    IMPORTED_LOCATION "/path/to/libopencv_core.so"
)
```

### 3. 生成器表达式

**Q: 什么是生成器表达式？为什么 add_definitions 不支持？**

A: 生成器表达式（Generator Expressions）是 CMake 在生成阶段求值的表达式。

```cmake
# 生成器表达式示例
$<CONFIG:Debug>              # 当前配置是否为Debug
$<$<CONFIG:Debug>:-DDEBUG>   # Debug模式添加-DDEBUG

# ✅ 支持生成器表达式的命令
add_compile_options($<$<CONFIG:Debug>:-DDEBUG>)
target_compile_definitions(core PRIVATE $<$<CONFIG:Debug>:DEBUG>)

# ❌ 不支持生成器表达式的命令
add_definitions($<$<CONFIG:Debug>:-DDEBUG>)  # 错误！

# 原因：add_definitions在配置阶段处理，生成器表达式在生成阶段求值
# 解决：使用特定配置的变量
set(CMAKE_CXX_FLAGS_DEBUG "${CMAKE_CXX_FLAGS_DEBUG} -DDEBUG")
```

### 4. 符号链接管理

**Q: 为什么需要 libXXX.so 符号链接？**

A: Linux 动态库的三层命名约定：

```bash
# 1. 实际文件（soname，运行时使用）
libopencv_core.so.4.2.0  # 完整版本号

# 2. Major版本链接（ABI兼容）
libopencv_core.so.4 -> libopencv_core.so.4.2.0

# 3. 开发链接（编译时使用）
libopencv_core.so -> libopencv_core.so.4

# CMake链接时查找 libopencv_core.so
# 程序运行时加载 libopencv_core.so.4
```

**创建符号链接**:

```bash
ln -sf 真实文件名 链接名

# 示例
ln -sf libopencv_core.so.4.2.0 libopencv_core.so.4
ln -sf libopencv_core.so.4 libopencv_core.so
```

### 5. 模块化编译顺序

**Q: CMake 如何处理模块间的依赖关系？**

A: 通过`add_subdirectory()`的顺序和`target_link_libraries()`的依赖声明：

```cmake
# src/CMakeLists.txt

# 1. 按依赖层次添加子目录
add_subdirectory(core)         # 第1层：无依赖
add_subdirectory(mqtt)         # 第2层：依赖core
add_subdirectory(vision)       # 第2层：依赖core
add_subdirectory(device)       # 第3层：依赖mqtt和core

# 2. 创建可执行文件
add_executable(ESDK_Sophon main.cpp)

# 3. 链接依赖（自动处理传递依赖）
target_link_libraries(ESDK_Sophon
    PRIVATE
        device    # 会自动链接device依赖的mqtt和core
        vision    # 会自动链接vision依赖的core
)
```

**依赖传递规则**:

- `PUBLIC`: 依赖会传递给链接者
- `PRIVATE`: 依赖不传递
- `INTERFACE`: 只传递依赖，自己不使用

例如：

```cmake
# core模块
target_link_libraries(core
    PUBLIC ThirdParty::Qt5Core  # 使用core的人也需要Qt5Core
)

# mqtt模块
target_link_libraries(mqtt
    PUBLIC core                 # 使用mqtt的人也需要core
    PRIVATE ThirdParty::MQTT    # 使用mqtt的人不需要知道MQTT库
)

# 主程序
target_link_libraries(ESDK_Sophon
    PRIVATE mqtt    # 自动获得：mqtt → core → Qt5Core
)
```
