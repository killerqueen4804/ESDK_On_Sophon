
### **知识点 5: 单元测试框架选择 (GTest vs 手动 assert)**

**面试问题**: 为什么不使用 Google Test？手动 assert 有什么优缺点？

**标准答案**:

#### **不同测试框架对比**

| 测试框架        | 优点                             | 缺点                       | 适用场景                   |
| --------------- | -------------------------------- | -------------------------- | -------------------------- |
| **Google Test** | 功能强大、报告详细、自动发现测试 | 需要额外安装、交叉编译困难 | 桌面开发、CI/CD 完善的项目 |
| **Catch2**      | 头文件单一、易集成               | 编译慢、可执行文件大       | 中小型 C++ 项目            |
| **Boost.Test**  | Boost 生态、功能全面             | 依赖 Boost 库              | 已使用 Boost 的项目        |
| **手动 assert** | 无依赖、跨平台、编译快           | 功能简单、需要手写框架     | 嵌入式、交叉编译环境 ⭐    |

#### **本项目选择手动 assert 的原因**

**环境限制**:

1. ❌ SE7 设备没有安装 GTest
2. ❌ 交叉编译环境难以编译 GTest
3. ❌ Docker 容器空间有限

**项目需求**:

1. ✅ 测试简单（主要测试 RAII 和基本功能）
2. ✅ 快速验证（编译时间短）
3. ✅ 返回值明确（0 = 成功，非 0 = 失败）

**代码对比**:

**GTest 版本** (优雅但有依赖):

```cpp
#include <gtest/gtest.h>

TEST(H264DecoderTest, InitAndDeinit) {
    H264Decoder decoder;
    ASSERT_TRUE(decoder.init(1920, 1080));  // 失败自动退出
    decoder.deinit();
}

int main(int argc, char** argv) {
    ::testing::InitGoogleTest(&argc, argv);
    return RUN_ALL_TESTS();  // 自动运行所有测试
}
```

**手动 assert 版本** (简单但无依赖):

```cpp
#include <iostream>
#include <cassert>

bool test_InitAndDeinit() {
    H264Decoder decoder;
    if (!decoder.init(1920, 1080)) {
        std::cerr << "初始化失败!" << std::endl;
        return false;  // 手动返回结果
    }
    decoder.deinit();
    return true;
}

int main() {
    if (!test_InitAndDeinit()) {
        std::cout << "❌ [FAIL] 测试1" << std::endl;
        return 1;  // 手动返回错误码
    }
    std::cout << "✅ [PASS] 测试1" << std::endl;
    return 0;
}
```

#### **手动测试框架设计要点**

**1. 统一的结果报告**:

```cpp
void printTestResult(const std::string& testName, bool passed) {
    if (passed) {
        std::cout << "✅ [PASS] " << testName << std::endl;
    } else {
        std::cout << "❌ [FAIL] " << testName << std::endl;
        exit(1);  // 任何测试失败就退出
    }
}
```

**2. 清晰的测试函数签名**:

```cpp
// ✅ 好: 返回 bool，语义清晰
bool test_InitAndDeinit() {
    // ...
    return true;  // 成功
}

// ❌ 不好: 返回 void，无法判断结果
void test_InitAndDeinit() {
    assert(condition);  // 失败直接崩溃，无法继续其他测试
}
```

**3. 详细的错误信息**:

```cpp
if (!decoder.init(1920, 1080)) {
    std::cerr << "  ❌ 初始化失败!" << std::endl;
    return false;  // 提供上下文信息
}
```

**4. 测试统计**:

```cpp
int main() {
    int passedTests = 0;
    int totalTests = 6;

    if (test_InitAndDeinit()) passedTests++;
    if (test_DoubleInit()) passedTests++;
    // ...

    std::cout << "测试完成: " << passedTests << "/" << totalTests << " 通过\n";
    return (passedTests == totalTests) ? 0 : 1;
}
```

#### **面试加分点**

**Q1: 什么时候用 GTest？什么时候用手动 assert？**

A:

- **GTest**: 桌面开发、CI/CD 完善、测试复杂（Mock、参数化测试）
- **手动 assert**: 嵌入式、交叉编译、快速验证、学习项目

**Q2: 如何保证手动测试的质量？**

A:

1. ✅ 统一的测试框架（printTestResult）
2. ✅ 清晰的命名约定（test_XXX）
3. ✅ 详细的错误信息（why 失败）
4. ✅ 完整的测试覆盖（初始化、边界、异常）

**Q3: 手动 assert 的最大问题是什么？**

A: **一个测试失败会阻止后续测试运行**

- GTest: `EXPECT_*` 失败后继续，`ASSERT_*` 失败退出当前测试
- 手动: `return false` 或 `exit(1)` 都会停止

**解决方案**:

```cpp
// ✅ 改进: 记录失败但继续运行
bool allPassed = true;
allPassed &= test1();  // 即使失败也继续
allPassed &= test2();
allPassed &= test3();
return allPassed ? 0 : 1;
```

**标准答案**:

### **知识点 3: FFmpeg 新旧 API 对比**

**面试问题**: FFmpeg 4.x 的新旧解码 API 有什么区别？

**标准答案**:

#### **旧 API (FFmpeg 3.x ~ 4.x)**

```cpp
AVPacket pkt;
av_init_packet(&pkt);
pkt.data = h264Data;
pkt.size = dataLen;

int gotPicture = 0;
avcodec_decode_video2(pCodecCtx, pFrameYUV, &gotPicture, &pkt);

if (gotPicture) {
    // 成功解码一帧
    processFrame(pFrameYUV);
}
```

**特点**:

- ✅ 简单直观: 一次调用完成
- ✅ 返回值清晰: gotPicture 标志是否解码成功
- ❌ 废弃警告: FFmpeg 4.x 标记为 deprecated

#### **新 API (FFmpeg 4.x+)**

```cpp
AVPacket pkt;
av_init_packet(&pkt);
pkt.data = h264Data;
pkt.size = dataLen;

// 步骤1: 发送数据包到解码器
int ret = avcodec_send_packet(pCodecCtx, &pkt);
if (ret < 0) {
    // 处理错误
}

// 步骤2: 接收解码后的帧
while (ret >= 0) {
    ret = avcodec_receive_frame(pCodecCtx, pFrameYUV);
    if (ret == AVERROR(EAGAIN) || ret == AVERROR_EOF) {
        break;  // 需要更多数据或结束
    }

    if (ret >= 0) {
        // 成功解码一帧
        processFrame(pFrameYUV);
    }
}
```

**特点**:

- ✅ 更灵活: 支持异步解码
- ✅ 更高效: 可以缓冲多帧
- ❌ 更复杂: 需要两次调用 + 循环

#### **为什么选择旧 API？**

| 因素              | 旧 API           | 新 API      |
| ----------------- | ---------------- | ----------- |
| **代码量**        | 5 行             | 15+ 行      |
| **学习成本**      | 低               | 中等        |
| **性能**          | 足够 (30 FPS)    | 更高 (异步) |
| **兼容性**        | FFmpeg 3.x ~ 4.x | FFmpeg 4.x+ |
| **Edge-SDK 使用** | ✅ 使用旧 API    | ❌          |

**结论**: 对于实时视频流 (30 FPS),旧 API 性能足够,且代码更简单。

### **知识点 4: #pragma GCC 编译指令**

**面试问题**: #pragma GCC diagnostic 是什么？如何使用？

**标准答案**:

**作用**: 控制 GCC 编译器的警告行为

**语法**:

```cpp
// 1. 保存当前警告状态
#pragma GCC diagnostic push

// 2. 忽略特定警告
#pragma GCC diagnostic ignored "-Wdeprecated-declarations"

// 3. 可能产生警告的代码
avcodec_decode_video2(...);

// 4. 恢复警告状态
#pragma GCC diagnostic pop
```

**常用警告类型**:
| 警告名称 | 描述 | 示例 |
|----------|------|------|
| `-Wdeprecated-declarations` | 使用废弃函数 | avcodec_decode_video2() |
| `-Wunused-variable` | 未使用的变量 | int x = 0; |
| `-Wconversion` | 类型转换 | int i = 3.14; |
| `-Wsign-compare` | 有符号/无符号比较 | if (i < size) |

**为什么使用 push/pop？**

```cpp
// ❌ 不好: 全局禁用警告
#pragma GCC diagnostic ignored "-Wdeprecated-declarations"
// 后续所有代码的警告都被禁用!

// ✅ 好: 只在需要的地方禁用
#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wdeprecated-declarations"
avcodec_decode_video2(...);  // 只这一行忽略警告
#pragma GCC diagnostic pop
// 后续代码恢复正常警告检查
```

**面试加分点**:

- 理解 push/pop 的作用域控制
- 知道常见的警告类型
- 能解释为什么不应该全局禁用警告
