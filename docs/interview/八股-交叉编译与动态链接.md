## 📌 知识点 1: 交叉编译原理

### 定义

在**主机平台**(Host Platform)上编译生成**目标平台**(Target Platform)的可执行文件。

### 通用例子

```
开发机(x86_64 Linux) → 编译 → ARM嵌入式设备(aarch64)
Windows PC(x64)      → 编译 → Android手机(ARM)
Mac M1(arm64)        → 编译 → Intel Mac(x86_64)
```

### 项目中的例子

```cpp
// 开发环境
Docker容器 stream_lzy (x86_64 Ubuntu)
  - GCC交叉编译器: aarch64-linux-gnu-g++
  - CMake工具链文件: sophon-toolchain.cmake
  - 第三方库头文件: third_party/opencv4.2/include

// 目标环境
算能SE7微服务器 (aarch64 Linux)
  - 运行时库: /opt/sophon/lib/libbmrt.so
  - OpenCV库: /usr/lib/libopencv_core.so.4.2
  - TPU驱动: Sophon libsophon-0.4.6

// 编译命令
cd /workspace/ESDK_On_Sophon/build
cmake -DCMAKE_TOOLCHAIN_FILE=../cmake/sophon-toolchain.cmake ..
make test_detector  # 生成aarch64可执行文件
```

### 详细讲解

#### 为什么需要交叉编译?

1. **资源受限**: 嵌入式设备内存小(SE7 只有 4GB)、CPU 慢
2. **开发效率**: PC 上编译器优化好、调试工具丰富
3. **硬件差异**: 开发机 x86 架构无法直接运行 ARM 指令

#### 交叉编译工具链组成

```
┌────────────────────────────────────┐
│  GCC交叉编译工具链                  │
├────────────────────────────────────┤
│  aarch64-linux-gnu-gcc      编译器 │
│  aarch64-linux-gnu-g++      编译器 │
│  aarch64-linux-gnu-ld       链接器 │
│  aarch64-linux-gnu-as       汇编器 │
│  aarch64-linux-gnu-objcopy  工具   │
│  aarch64-linux-gnu-readelf  分析   │
└────────────────────────────────────┘
```

#### CMake 工具链文件示例

```cmake
# cmake/sophon-toolchain.cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

# 指定交叉编译器
set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)

# 指定目标设备的根文件系统(Sysroot)
set(CMAKE_SYSROOT /opt/sophon/sysroot)

# 只在Sysroot中搜索库
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
```

## 📌 知识点 2: 静态链接 vs 动态链接

### 定义

- **静态链接**: 编译时将库代码拷贝进可执行文件
- **动态链接**: 运行时加载共享库(`.so`/`.dll`)

### 通用例子

```bash
# 静态链接
g++ main.cpp -static -lpthread -o app_static
# 生成: app_static (10MB,自包含)

# 动态链接(默认)
g++ main.cpp -lpthread -o app_dynamic
# 生成: app_dynamic (100KB,依赖libpthread.so)
```

### 项目中的例子

```cpp
// 动态链接配置 (tests/CMakeLists.txt)
add_executable(test_detector test_detector.cpp)

target_link_libraries(test_detector
    PRIVATE
        detector                # 动态库: libdetector.so
        ThirdParty::OpenCV      # 动态库: libopencv_core.so.4.2
        ThirdParty::FastDeploy  # 动态库: libfastdeploy.so
)

// 查看依赖关系
$ ldd bin/tests/test_detector
    libdetector.so => /usr/local/lib/libdetector.so (0x...)
    libopencv_core.so.4.2 => /usr/lib/libopencv_core.so.4.2 (0x...)
    libfastdeploy.so => /opt/sophon/lib/libfastdeploy.so (0x...)
    libbmrt.so.1.0 => /opt/sophon/libsophon-0.4.6/lib/libbmrt.so.1.0 (0x...)
```

### 详细讲解

#### 对比表格

| 特性         | 静态链接 (`.a`)    | 动态链接 (`.so`)   |
| ------------ | ------------------ | ------------------ |
| **文件大小** | 大(包含所有库代码) | 小(只记录依赖信息) |
| **启动速度** | 快(无加载开销)     | 慢(需加载共享库)   |
| **内存占用** | 高(每进程独立)     | 低(多进程共享)     |
| **更新方式** | 重新编译           | 替换`.so`即可      |
| **依赖管理** | 无依赖             | 需确保库存在       |
| **调试难度** | 难(符号被剥离)     | 易(符号在`.so`中)  |
| **跨平台**   | 容易(自包含)       | 难(库路径不同)     |

#### 动态链接器工作原理

```
用户执行: ./test_detector
    ↓
内核启动: /lib/ld-linux-aarch64.so.1 (动态链接器)
    ↓
读取ELF头: NEEDED 段
    - libdetector.so
    - libopencv_core.so.4.2
    - libfastdeploy.so
    ↓
搜索路径(按顺序):
    1. RPATH (编译时指定)
    2. LD_LIBRARY_PATH (环境变量)
    3. /etc/ld.so.conf (系统配置)
    4. /lib, /usr/lib (默认路径)
    ↓
加载共享库到内存
    ↓
符号解析:
    test_detector中的bmrt_load_bmodel() → libbmrt.so中的实现
    ↓
执行main()
```

#### SE7 设备库路径配置

```bash
# 查看配置文件
$ cat /etc/ld.so.conf.d/sophon.conf
/opt/sophon/libsophon-current/lib
/opt/sophon/libsophon-current/lib/bmnn
/system/lib

# 更新库缓存
$ sudo ldconfig

# 验证库是否被缓存
$ ldconfig -p | grep bmrt
libbmrt.so.1.0 (libc6,AArch64) => /opt/sophon/libsophon-0.4.6/lib/libbmrt.so.1.0
```

## 📌 知识点 3: 链接器符号解析

### 定义

链接器将代码中的**符号引用**(函数调用、全局变量)与**符号定义**(函数实现)关联的过程。

### 通用例子

```cpp
// main.cpp
extern int add(int a, int b);  // 符号引用(声明)

int main() {
    int result = add(1, 2);    // 符号引用(调用)
    return result;
}

// math.cpp
int add(int a, int b) {        // 符号定义(实现)
    return a + b;
}

// 编译
g++ -c main.cpp -o main.o    // main.o: 包含add的未定义引用
g++ -c math.cpp -o math.o    // math.o: 包含add的定义

// 链接
g++ main.o math.o -o app     // 链接器解析: main.o的add → math.o的add
```

### 项目中的例子

```cpp
// PPYoloeDetector.cpp (符号引用)
#include <fastdeploy/vision.h>

bool PPYoloeDetector::initialize() {
    // 调用FastDeploy库的函数
    model_ = new fastdeploy::vision::detection::PPYOLOE(...);
    //              ↑ 符号引用: PPYOLOE构造函数

    bool success = model_->Initialized();
    //                     ↑ 符号引用: Initialized()方法
}

// libfastdeploy.so (符号定义)
namespace fastdeploy::vision::detection {
    PPYOLOE::PPYOLOE(...) {  // 符号定义
        // 构造函数实现
    }

    bool PPYOLOE::Initialized() {  // 符号定义
        // 方法实现
    }
}

// 链接时
$ aarch64-linux-gnu-g++ PPYoloeDetector.o -lfastdeploy -o libdetector.so
链接器搜索 libfastdeploy.so:
  ✅ 找到 PPYOLOE::PPYOLOE(...)
  ✅ 找到 PPYOLOE::Initialized()
  ✅ 链接成功

// 如果libfastdeploy.so不存在
❌ undefined reference to `fastdeploy::vision::detection::PPYOLOE::PPYOLOE(...)`
```

### 详细讲解

#### 符号类型

| 符号类型          | 说明              | 示例                     |
| ----------------- | ----------------- | ------------------------ |
| **U** (undefined) | 未定义,需外部提供 | `U bmrt_load_bmodel`     |
| **T** (text)      | 代码段定义        | `T main`                 |
| **D** (data)      | 已初始化数据      | `D global_var`           |
| **B** (bss)       | 未初始化数据      | `B static_array`         |
| **W** (weak)      | 弱符号(可被覆盖)  | `W __gxx_personality_v0` |

#### 查看符号表

```bash
# 查看目标文件符号
$ nm PPYoloeDetector.o | grep PPYOLOE
U _ZN11fastdeploy6vision9detection7PPYOLOEC1...  # 未定义(需链接)

# 查看共享库符号
$ nm -D /opt/sophon/lib/libfastdeploy.so | grep PPYOLOE
T _ZN11fastdeploy6vision9detection7PPYOLOEC1...  # 已定义(提供实现)

# C++ Name Mangling解码
$ c++filt _ZN11fastdeploy6vision9detection7PPYOLOEC1...
fastdeploy::vision::detection::PPYOLOE::PPYOLOE(...)
```

#### undefined reference 错误分析

```bash
# 错误信息
undefined reference to `bmrt_load_bmodel'

# 原因分析
1. libfastdeploy.so 调用了 bmrt_load_bmodel()
2. bmrt_load_bmodel() 定义在 libbmrt.so.1.0 中
3. 交叉编译环境没有 libbmrt.so.1.0
4. 链接器无法解析这个符号

# 解决方案A: --allow-shlib-undefined
target_link_options(test_detector PRIVATE
    -Wl,--allow-shlib-undefined  # 允许共享库有未定义符号
)
# 结果: 链接成功,运行时在SE7设备上解析

# 解决方案B: 提供sysroot
set(CMAKE_SYSROOT /opt/sophon/se7-sysroot)
# 结果: 链接器可以找到libbmrt.so.1.0
```

## 📌 知识点 4: 交叉编译链接器选项

### 定义

传递给链接器的参数,控制链接行为(搜索路径、符号解析、库类型等)。

### 通用例子

```bash
# 基本链接
g++ main.o -o app

# 指定库名(-l)和搜索路径(-L)
g++ main.o -L/usr/local/lib -lmylib -o app
#           ↑ 搜索路径         ↑ 链接libmylib.so

# 静态链接
g++ main.o -static -lmylib -o app

# 设置运行时库路径
g++ main.o -Wl,-rpath,/opt/lib -lmylib -o app
```

### 项目中的例子

```cmake
// tests/CMakeLists.txt
target_link_options(test_detector PRIVATE
    -Wl,-rpath-link,${CMAKE_SOURCE_DIR}/third_party/opencv4.2/lib
    #   │   └─ 链接器选项: 链接时搜索路径
    #   └─ 传递给链接器的前缀(-Wl表示linker option)

    -Wl,-rpath-link,${CMAKE_SOURCE_DIR}/third_party/fastdeploy/lib
    #   └─ 多个-rpath-link会累加搜索路径

    -Wl,--allow-shlib-undefined
    #   └─ 允许共享库有未定义符号(交叉编译关键选项)
)

// 实际链接命令(CMake生成)
aarch64-linux-gnu-g++ \
    test_detector.cpp.o \
    -o bin/tests/test_detector \
    -L../../lib \
    -ldetector \
    -L../../third_party/opencv4.2/lib \
    -lopencv_core -lopencv_imgcodecs \
    -L../../third_party/fastdeploy/lib \
    -lfastdeploy \
    -Wl,-rpath-link,../../third_party/opencv4.2/lib \
    -Wl,-rpath-link,../../third_party/fastdeploy/lib \
    -Wl,--allow-shlib-undefined
```

### 详细讲解

#### 常用链接器选项

| 选项                          | 作用                 | 影响阶段 | 示例                                  |
| ----------------------------- | -------------------- | -------- | ------------------------------------- |
| `-L<path>`                    | 添加库搜索路径       | 链接时   | `-L/usr/local/lib`                    |
| `-l<name>`                    | 链接库文件           | 链接时   | `-lopencv_core` → `libopencv_core.so` |
| `-Wl,-rpath,<path>`           | 设置运行时库路径     | 运行时   | `-Wl,-rpath,/opt/sophon/lib`          |
| `-Wl,-rpath-link,<path>`      | 链接时库搜索路径     | 链接时   | `-Wl,-rpath-link,./lib`               |
| `-static`                     | 静态链接             | 链接时   | `-static -lpthread`                   |
| `-shared`                     | 生成共享库           | 链接时   | `-shared -o libmy.so`                 |
| `-Wl,--allow-shlib-undefined` | 允许共享库未定义符号 | 链接时   | 交叉编译必备                          |
| `-Wl,--no-undefined`          | 禁止未定义符号       | 链接时   | 严格检查依赖                          |

#### rpath vs rpath-link 对比

```bash
# rpath: 运行时搜索路径(写入ELF文件)
$ g++ main.o -Wl,-rpath,/opt/sophon/lib -lfastdeploy -o app

$ readelf -d app | grep RPATH
0x000000000000000f (RPATH)    Library rpath: [/opt/sophon/lib]
# app运行时会在/opt/sophon/lib搜索libfastdeploy.so

$ ./app  # SE7设备上运行
# 动态链接器搜索顺序:
# 1. /opt/sophon/lib (RPATH)
# 2. LD_LIBRARY_PATH
# 3. /lib, /usr/lib
# ✅ 找到 /opt/sophon/lib/libfastdeploy.so


# rpath-link: 链接时搜索路径(不写入ELF文件)
$ aarch64-linux-gnu-g++ main.o \
    -Wl,-rpath-link,./third_party/lib \
    -lfastdeploy -o app

$ readelf -d app | grep RPATH
# (空,没有RPATH记录)

# 链接时:
# 链接器在 ./third_party/lib 找到 libfastdeploy.so
# 读取其依赖: libbmrt.so.1.0
# 继续在 ./third_party/lib 搜索 libbmrt.so.1.0
# ✅ 链接成功

# 运行时(SE7设备):
$ ./app
# 动态链接器搜索顺序:
# 1. LD_LIBRARY_PATH
# 2. /etc/ld.so.conf
# 3. /lib, /usr/lib, /opt/sophon/lib
# ✅ 在系统路径找到libfastdeploy.so和libbmrt.so
```

#### --allow-shlib-undefined 原理

```bash
# 正常链接(非交叉编译)
$ g++ main.o -lfastdeploy -o app
链接器检查:
  libfastdeploy.so → libbmrt.so.1.0 ✅ 找到
  libbmrt.so.1.0 → (系统库) ✅ 找到
✅ 所有符号都解析成功


# 交叉编译(没有--allow-shlib-undefined)
$ aarch64-linux-gnu-g++ main.o -lfastdeploy -o app
链接器检查:
  libfastdeploy.so → libbmrt.so.1.0 ❌ 找不到
  ❌ undefined reference to `bmrt_load_bmodel`
  ❌ 链接失败


# 交叉编译(使用--allow-shlib-undefined)
$ aarch64-linux-gnu-g++ main.o -lfastdeploy \
    -Wl,--allow-shlib-undefined -o app
链接器检查:
  libfastdeploy.so → libbmrt.so.1.0 ⚠️ 找不到,但允许未定义
  ✅ 链接成功(假设运行时能找到)

# SE7设备运行
$ ./app
动态链接器:
  libfastdeploy.so → libbmrt.so.1.0 ✅ 在/opt/sophon/lib找到
  ✅ 程序正常运行
```

#### Day 4 项目实战: 200+ 链接警告处理

**问题背景** (2025-11-09):

```bash
# CMake编译时出现大量警告
warning: libz.so.1, needed by libopencv_core.so, not found (try using -rpath or -rpath-link)
warning: libjpeg.so.8, needed by libopencv_imgcodecs.so, not found
warning: libpng16.so.16, needed by libopencv_imgcodecs.so, not found
warning: libglib-2.0.so.0, needed by libgstreamer-1.0.so, not found
... (200+ warnings)
```

**解决方案** (tests/CMakeLists.txt):

```cmake
# 添加全局链接器选项
set(CMAKE_EXE_LINKER_FLAGS
    "${CMAKE_EXE_LINKER_FLAGS} -Wl,--unresolved-symbols=ignore-in-shared-libs")
set(CMAKE_SHARED_LINKER_FLAGS
    "${CMAKE_SHARED_LINKER_FLAGS} -Wl,--unresolved-symbols=ignore-in-shared-libs")

# 或者针对特定目标添加
target_link_options(test_task_basic PRIVATE
    -Wl,--unresolved-symbols=ignore-in-shared-libs
)
```

**验证结果**:

```bash
# 编译: 警告消失
cd build && make test_task_basic
✅ Linking CXX executable bin/tests/test_task_basic (无警告)

# 运行时错误 (预期中)
./bin/tests/test_task_basic
error while loading shared libraries: libdc1394.so.22: cannot open shared object file

# 在SE7设备上安装运行时依赖
sudo apt-get install libdc1394-22
✅ 程序正常运行
```

**知识点总结**:

1. **编译时警告 ≠ 运行时错误**: 交叉编译忽略符号检查,运行时仍需真实库文件
2. **开发流程**: 编译(Docker) → 部署(SE7) → 安装依赖 → 运行
3. **风险控制**: 部署前用 `ldd` 检查依赖,提前安装缺失的库

## 🎯 面试高频问题

### Q1: 为什么交叉编译会出现 undefined reference 错误?

**标准答案**:

```
交叉编译环境(Docker容器)与目标环境(SE7设备)分离导致:

1. 根本原因:
   - 编译环境只有头文件和静态库,没有运行时共享库
   - 目标环境的运行时库(如libbmrt.so)不在编译环境中

2. 链接器行为:
   - 链接器需要检查所有符号能否解析
   - libfastdeploy.so依赖libbmrt.so
   - 编译环境找不到libbmrt.so → 符号解析失败

3. 解决思路:
   方案A: --allow-shlib-undefined (推荐)
     - 告诉链接器"运行时会有这个库"
     - 链接成功,运行时在SE7设备解析

   方案B: 提供Sysroot
     - 将SE7设备根文件系统镜像到编译环境
     - 链接器可以找到所有依赖库

   方案C: 静态链接(不推荐)
     - TPU驱动库无法静态链接
     - 可执行文件体积过大
```

**项目示例**:

```cmake
target_link_options(test_detector PRIVATE
    -Wl,--allow-shlib-undefined  // 方案A
)
```

### Q2: 静态链接和动态链接的优缺点?什么场景用哪个?

**标准答案**:

```
静态链接:
  优点:
    1. 自包含,无依赖问题
    2. 启动快(无动态加载)
    3. 版本锁定(不受系统库更新影响)

  缺点:
    1. 文件大(10MB+)
    2. 内存浪费(进程间无法共享)
    3. 更新困难(需重新编译)

  场景:
    - 一次性工具
    - 无操作系统的嵌入式设备
    - 部署环境不确定

动态链接:
  优点:
    1. 文件小(100KB vs 10MB)
    2. 内存共享(10个进程共享一个libopencv.so)
    3. 更新方便(替换.so即可)

  缺点:
    1. 依赖管理(需确保库存在)
    2. 启动慢(动态加载开销)
    3. 版本冲突(DLL Hell)

  场景:
    - 嵌入式Linux(本项目)
    - 桌面应用
    - 系统服务
```

**本项目选择**:

```
动态链接,原因:
1. SE7设备存储有限(8GB eMMC)
2. 多个程序共享OpenCV/FastDeploy库
3. TPU驱动库(libbmrt.so)只有动态版本
4. 方便更新算法库(无需重编译整个系统)
```

### Q3: 如何排查运行时找不到共享库的问题?

**标准答案**:

```bash
1. 查看程序依赖
$ ldd ./test_detector
    libdetector.so => not found ❌
    libopencv_core.so.4.2 => /usr/lib/libopencv_core.so.4.2 ✅
    libbmrt.so.1.0 => not found ❌
```

### Q4: 什么是 Name Mangling?为什么 C++需要?

**标准答案**:

```cpp
定义: 编译器将C++函数名编码成唯一符号的过程

原因: C++支持函数重载,需要区分:
void foo(int a);           // _Z3fooi
void foo(double d);        // _Z3food
void foo(int a, int b);    // _Z3fooii

C语言不需要:
void foo(int a);           // foo (无编码)

查看符号:
$ nm PPYoloeDetector.o
000000000000048c T _ZN13PPYoloeDetectorC1Ev
// C1Ev = 构造函数(Constructor 1) + Empty parameters + void return

$ c++filt _ZN13PPYoloeDetectorC1Ev
PPYoloeDetector::PPYoloeDetector()

extern "C"避免Name Mangling:
extern "C" void foo(int a);  // 生成符号: foo
// 用于C/C++混合编程
```

**本项目示例**:

```cpp
// FastDeploy库可能混用C/C++
namespace fastdeploy {
    extern "C" {
        void* bmrt_load_bmodel(const char* path);  // C接口
    }

    class PPYOLOE {  // C++接口
        bool Initialized();  // 会被Mangled
    };
}
```

### Q5: CMake 中如何正确配置交叉编译?

**标准答案**:

```cmake
1. 创建工具链文件 (cmake/sophon-toolchain.cmake)
set(CMAKE_SYSTEM_NAME Linux)         # 目标系统
set(CMAKE_SYSTEM_PROCESSOR aarch64)  # 目标架构

set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)

set(CMAKE_SYSROOT /opt/sophon/sysroot)  # 目标设备根文件系统

2. 配置第三方库路径
set(OPENCV_DIR ${CMAKE_SOURCE_DIR}/third_party/opencv4.2)
set(FASTDEPLOY_DIR ${CMAKE_SOURCE_DIR}/third_party/fastdeploy)

3. 添加链接器选项
target_link_options(${TARGET} PRIVATE
    -Wl,-rpath-link,${OPENCV_DIR}/lib
    -Wl,--allow-shlib-undefined
)

4. 使用工具链文件编译
cmake -DCMAKE_TOOLCHAIN_FILE=../cmake/sophon-toolchain.cmake ..
make

5. 验证生成的二进制
$ file bin/tests/test_detector
bin/tests/test_detector: ELF 64-bit LSB executable, ARM aarch64, ...
```
