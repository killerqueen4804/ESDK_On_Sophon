## 📌 核心知识点

### 1. Meyers' Singleton (C++11 线程安全)

#### 知识点

**Meyers' Singleton** 是 Scott Meyers 提出的单例模式实现,利用 C++11 的 magic static 特性实现线程安全。

```cpp
class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance;  // ⭐ Magic Static
        return instance;
    }

    // 禁止拷贝和赋值
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

private:
    Singleton() = default;
    ~Singleton() = default;
};
```

**核心原理**:

- C++11 标准保证静态局部变量的初始化是线程安全的
- 编译器自动生成初始化标志和互斥锁
- 第一次调用时初始化,后续直接返回

#### 经典例子

```cpp
// 配置管理单例
class Config {
public:
    static Config& getInstance() {
        static Config instance;
        return instance;
    }

    void load(const std::string& path) {
        // 加载配置文件...
    }

    std::string getString(const std::string& key) {
        // 读取配置...
    }

private:
    Config() = default;
};

// 使用
int main() {
    auto& config = Config::getInstance();
    config.load("config.json");
    std::string host = config.getString("host");
}
```

#### 详细讲解

##### 1. 为什么 Meyers' Singleton 是线程安全的?

**C++11 标准保证** (§6.7 [stmt.dcl]):

> If multiple threads attempt to initialize the same static local variable concurrently,
> the initialization occurs exactly once.

编译器生成的伪代码:

```cpp
Config& Config::getInstance() {
    // 编译器生成的隐藏代码
    static bool initialized = false;
    static std::mutex init_mutex;
    static alignas(Config) char buffer[sizeof(Config)];

    if (!initialized) {
        std::lock_guard<std::mutex> lock(init_mutex);
        if (!initialized) {  // Double-Checked Locking
            new (buffer) Config();  // Placement new
            initialized = true;
        }
    }

    return *reinterpret_cast<Config*>(buffer);
}
```

**关键点**:

1. 第一个线程进入初始化,获取锁
2. 其他线程等待锁释放
3. 初始化完成后,后续调用直接返回(无锁)

##### 2. 为什么不用 DCL (Double-Checked Locking)?

**传统 DCL 实现** (C++11 之前):

```cpp
// ❌ C++03 时代的错误实现
class Singleton {
private:
    static Singleton* instance;
    static std::mutex mutex_;

public:
    static Singleton* getInstance() {
        if (instance == nullptr) {  // 第一次检查(无锁)
            std::lock_guard<std::mutex> lock(mutex_);
            if (instance == nullptr) {  // 第二次检查(有锁)
                instance = new Singleton();  // ⚠️ 非原子操作!
            }
        }
        return instance;
    }
};

Singleton* Singleton::instance = nullptr;
```

**问题**:

```cpp
instance = new Singleton();

// 分解为三步:
1. 分配内存 p
2. 在 p 上构造对象 Singleton()
3. 将 p 赋值给 instance

// 编译器可能重排序为:
1. 分配内存 p
2. 将 p 赋值给 instance  ← instance != nullptr,但对象未构造!
3. 在 p 上构造对象

// 如果线程A执行到步骤2,线程B调用getInstance():
Thread B: if (instance == nullptr)  // false, instance已赋值
Thread B: return instance;          // 💥 返回未构造的对象!
```

**C++11 解决方案**:

- 使用 `std::atomic` + `std::memory_order`
- 或者直接用 Meyers' Singleton (编译器保证)

##### 3. 其他单例实现方式对比

| 方式              | 线程安全 | 懒加载 | 性能 | 复杂度 |
| ----------------- | -------- | ------ | ---- | ------ |
| Meyers' Singleton | ✅       | ✅     | 高   | 低     |
| 饿汉式            | ✅       | ❌     | 高   | 低     |
| 懒汉式+锁         | ✅       | ✅     | 中   | 低     |
| DCL(C++03)        | ❌       | ✅     | 高   | 高     |
| DCL(C++11)        | ✅       | ✅     | 高   | 高     |

**推荐**: Meyers' Singleton (简单、安全、高效)

#### 面试要点

##### Q1: Meyers' Singleton 的线程安全是如何实现的?

**A**:

```
关键:
C++11 标准保证静态局部变量初始化的线程安全性。

原理:
1. 编译器生成初始化标志 (initialized)
2. 编译器生成互斥锁 (init_mutex)
3. 第一次调用时:
   - 检查标志,未初始化
   - 获取锁(其他线程等待)
   - 执行构造函数
   - 设置标志
   - 释放锁
4. 后续调用:
   - 检查标志,已初始化
   - 直接返回 instance (无锁,快速)

优点:
- 线程安全:多线程同时调用,只初始化一次
- 高性能:初始化后无锁访问
- 懒加载:第一次使用时才初始化
- 简单:不需要手写锁和DCL逻辑

注意:
⚠️ 如果构造函数中调用其他正在构造的单例 → 死锁!
```

##### Q2: 为什么单例要禁止拷贝和赋值?

**A**:

```cpp
class Singleton {
public:
    // ✅ 禁止拷贝构造
    Singleton(const Singleton&) = delete;

    // ✅ 禁止拷贝赋值
    Singleton& operator=(const Singleton&) = delete;

    // ✅ C++11: 禁止移动构造(可选)
    Singleton(Singleton&&) = delete;

    // ✅ C++11: 禁止移动赋值(可选)
    Singleton& operator=(Singleton&&) = delete;
};

原因:
1. 保证全局唯一
   Singleton s1 = Singleton::getInstance();  // ❌ 创建副本,破坏单例

2. 避免资源重复释放
   如果单例管理资源(文件句柄、数据库连接等)
   拷贝会导致析构时重复释放 → 崩溃!

3. 语义一致性
   单例模式的定义就是"全局唯一实例"
   允许拷贝违反了设计意图
```

##### Q3: 单例模式的析构顺序问题?

**A**:

```cpp
问题:
如果单例 A 依赖单例 B,而 B 先析构,A 再析构时访问 B → 崩溃!

示例:
class Logger { /* ... */ };
class Config {
    ~Config() {
        Logger::getInstance().info("Config destroyed");  // 💥 Logger 可能已析构!
    }
};

// 析构顺序不确定!
// 可能 Logger 先析构,Config 析构时访问已析构的 Logger

解决方案:

1. 不在析构函数中使用其他单例
   ~Config() {
       std::cout << "Config destroyed" << std::endl;  // ✅ 不依赖 Logger
   }

2. 使用 std::atexit() 控制析构顺序
   struct SingletonDestroyer {
       ~SingletonDestroyer() {
           // 按正确顺序销毁单例
           config.destroy();
           logger.destroy();
       }
   };
   static SingletonDestroyer destroyer;

3. 使用智能指针延长生命周期
   class Singleton {
       static std::shared_ptr<Singleton> instance_;
   };

4. 接受"不完美"
   大多数情况下,程序退出时单例自动析构即可
   不需要手动控制顺序
```

#### 易错点

##### 错误 1: 构造函数中调用其他单例

```cpp
// ❌ 错误:可能死锁
class Config {
    Config() {
        Logger::getInstance().info("Config created");  // 💥 如果 Logger 还未构造?
    }
};

class Logger {
    Logger() {
        auto& config = Config::getInstance();  // 💥 如果 Config 还未构造?
        level_ = config.getString("logger.level");
    }
};

// 使用
auto& config = Config::getInstance();  // Config 构造调用 Logger
                                        // Logger 构造调用 Config
                                        // 💥 循环依赖,死锁!

// ✅ 正确:控制初始化顺序
int main() {
    auto& logger = Logger::getInstance();  // 先初始化 Logger
    auto& config = Config::getInstance();  // 再初始化 Config
}
```

##### 错误 2: 返回指针而不是引用

```cpp
// ❌ 不好
static Singleton* getInstance() {
    static Singleton instance;
    return &instance;  // 返回指针
}

// 使用
Singleton* s = Singleton::getInstance();
delete s;  // 💥 不能删除静态对象!

// ✅ 好
static Singleton& getInstance() {
    static Singleton instance;
    return instance;  // 返回引用
}

// 使用
Singleton& s = Singleton::getInstance();  // 不能 delete 引用,安全!
```

##### 错误 3: 忘记禁止拷贝

```cpp
// ❌ 错误:允许拷贝
class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance;
        return instance;
    }
    // 默认拷贝构造和赋值 → 可以创建副本!
};

// 使用
Singleton s1 = Singleton::getInstance();  // 💥 创建副本,不再是单例!

// ✅ 正确:禁止拷贝
class Singleton {
public:
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
};
```

## 📌 静态初始化顺序问题 (Static Initialization Order Fiasco)

### 知识点

**静态初始化顺序问题**: 全局/静态对象的初始化顺序在不同编译单元间是未定义的。

#### 经典例子

```cpp
// a.cpp
#include <iostream>
class A {
public:
    A() { std::cout << "A constructed" << std::endl; }
};
A globalA;  // 全局对象

// b.cpp
#include <iostream>
class B {
public:
    B() {
        std::cout << "B constructed" << std::endl;
        // 假设需要使用 globalA
    }
};
B globalB;  // 全局对象

// 问题:globalA 和 globalB 哪个先构造? 未定义!
// 如果 globalB 构造时使用 globalA,但 globalA 还未构造 → 💥 UB!
```

#### 项目中的例子

**ESDK_On_Sophon 中的死锁案例**:

```cpp
// 场景:test_detector 启动时卡死

// test_detector.cpp (修复前)
int main() {
    auto& config = Config::getInstance();
    config.load("config.json");  // 💥 卡死在这里!
}

// Config.cpp
bool Config::load(const std::string& path) {
    std::lock_guard<std::mutex> lock(mutex_);  // 获取锁

    if (!file.is_open()) {
        Logger::getInstance().error("...");  // ⭐ 第一次调用 Logger
    }
}

// Logger.cpp
Logger::Logger() {
    pImpl_->loadConfigSettings();  // 构造时加载配置
}

void Logger::Impl::loadConfigSettings() {
    auto& config = Config::getInstance();  // ⭐ 尝试获取 Config
    level_ = config.getString("logger.level");
}

// 死锁过程:
Config::load() 持有锁
  ↓
调用 Logger::getInstance()
  ↓
Logger 构造,调用 Config::getInstance()
  ↓
等待 Config 构造完成(等待锁释放)
  ↓
Config::load() 等待 Logger 构造完成
  ↓
💥 互相等待 → 死锁!
```

#### 详细讲解

##### 1. 为什么会有顺序问题?

**C++ 标准规定**:

- 同一编译单元内: 按声明顺序初始化
- 不同编译单元间: 顺序未定义

```cpp
// 同一文件内 (file.cpp)
A a;  // 先构造
B b;  // 后构造
C c;  // 最后构造

// 跨文件 (a.cpp, b.cpp, c.cpp)
// 顺序可能是: A → B → C
// 也可能是: B → C → A
// 或任意其他顺序!
```

##### 2. Meyers' Singleton 如何解决?

**关键**: 将静态对象从全局改为函数内静态局部变量

```cpp
// ❌ 全局静态 - 顺序未定义
// global.cpp
Config globalConfig;  // 什么时候构造? 不知道!

// ✅ Meyers' Singleton - 延迟初始化
Config& Config::getInstance() {
    static Config instance;  // ⭐ 第一次调用时才构造
    return instance;
}

优点:
1. 延迟加载:只有用到才初始化
2. 确定顺序:第一次调用决定顺序
3. 线程安全:C++11 保证

使用:
int main() {
    auto& logger = Logger::getInstance();  // 先初始化 Logger
    auto& config = Config::getInstance();  // 再初始化 Config
    // 顺序明确,可控!
}
```

##### 3. 循环依赖的检测和解决

**检测方法**:

```
症状:
- 程序启动时卡死
- CPU 占用率低(不是死循环)
- gdb backtrace 显示在单例构造中

调试:
$ gdb ./program
(gdb) run
<卡死>
Ctrl+C
(gdb) bt
#0  std::mutex::lock()
#1  Config::load()
#2  Logger::Logger()
#3  Config::load()  ← 发现循环!
```

**解决方法**:

```cpp
方法 1: 控制初始化顺序
int main() {
    auto& logger = Logger::getInstance();  // 先初始化不依赖其他的
    auto& config = Config::getInstance();  // 再初始化依赖 Logger 的
}

方法 2: 延迟依赖
class Logger {
    void log() {
        if (!configLoaded_) {
            loadConfig();  // 第一次使用时才读配置
        }
        // ...
    }
};

方法 3: 解除依赖
class Config {
    bool load() {
        // 不使用 Logger,用 std::cout
        std::cout << "Config loaded" << std::endl;
    }
};

方法 4: 依赖注入
class Logger {
    Logger(const LoggerConfig& config);  // 外部传入配置
};
```

#### 面试要点

##### Q1: 什么是静态初始化顺序问题?

**A**:

```
定义:
全局/静态对象的初始化顺序在不同编译单元(cpp文件)间是未定义的。

问题:
// a.cpp
Logger logger;  // 全局对象

// b.cpp
Config config;  // 构造时需要 logger

如果 b.cpp 先初始化:
→ Config 构造时访问 logger
→ 但 logger 还没构造
→ 💥 未定义行为!

解决方案:
1. 使用 Meyers' Singleton (函数内静态)
2. 延迟初始化(lazy initialization)
3. 依赖注入(不使用全局单例)

为什么 Meyers' Singleton 能解决?
- 函数内静态变量在第一次调用函数时初始化
- 不是程序启动时初始化
- 初始化顺序由调用顺序决定,可控!
```

##### Q2: 如何避免单例间的循环依赖?

**A**:

```
原则:
单例间应该是单向依赖,不能循环依赖。

好的设计:
Logger ← Config ← Application
(箭头表示依赖方向)

坏的设计:
Logger ↔ Config
(互相依赖,可能死锁)

检查清单:
1. 绘制依赖图
   - 每个单例是一个节点
   - 依赖关系是一条边
   - 检查是否有环

2. 构造函数不调用其他单例
   - 构造时使用默认值
   - 第一次使用时才读取配置

3. 延迟初始化
   - 构造时不初始化
   - 使用时才初始化

4. 明确初始化顺序
   int main() {
       Logger::getInstance();  // 先
       Config::getInstance();  // 后
   }
```
