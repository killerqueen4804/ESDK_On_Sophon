## 📌 异步回调中的对象生命周期管理 ⭐⭐⭐⭐⭐

### 知识点

在异步回调中使用对象指针时，必须确保对象在回调执行时仍然有效。特别是：

1. **回调上下文 (context)**: 通常是 `this` 指针或对象指针
2. **异步执行**: 回调可能在对象析构后才执行
3. **成员访问**: 访问已析构对象的成员会导致未定义行为（Segmentation Fault）

**三种保护方案**:

1. **状态标志检查** (简单高效) ✅ 本项目采用
2. **智能指针管理** (安全但复杂)
3. **同步取消注册** (彻底但可能阻塞)

---

### 经典例子

```cpp
class Server {
public:
    Server() {
        // 注册回调，传入 this 指针作为 context
        register_callback(&Server::on_message, this);
    }

    ~Server() {
        // 析构时必须取消注册回调，或确保回调不再执行
        unregister_callback();
    }

private:
    static void on_message(void* context, const char* msg) {
        auto* self = static_cast<Server*>(context);

        // ❌ 危险：如果 Server 已经析构，self 是悬空指针
        self->logger_.info(msg);  // 💥 可能崩溃
    }

    Logger logger_;
};
```

### 项目中的例子

```cpp
// ❌ Bug版本：没有检查对象状态
void MqttClient::Impl::onConnectionLostCallback(void* context, char* cause) {
    auto* self = static_cast<Impl*>(context);

    std::string causeStr = (cause != nullptr) ? std::string(cause) : "Unknown";

    // 💥 危险：如果对象正在析构，访问 logger_ 会崩溃
    self->logger_.warning("MQTT连接丢失: " + causeStr);

    // 触发重连
    self->attemptReconnect();
}

// ✅ 修复版本：添加对象状态检查
void MqttClient::Impl::onConnectionLostCallback(void* context, char* cause) {
    auto* self = static_cast<Impl*>(context);

    // ⭐ 关键修复：检查对象是否正在析构
    if (!self->connected_) {
        // 对象可能正在析构，不打印日志（访问logger_不安全）
        return;  // 提前返回，不执行任何操作
    }

    std::string causeStr = (cause != nullptr) ? std::string(cause) : "Unknown";

    // 现在可以安全访问成员
    self->logger_.warning("MQTT连接丢失: " + causeStr);

    // 触发重连
    self->attemptReconnect();
}

// ⭐ 配合 disconnect() 提前设置标志
void MqttClient::Impl::disconnect() {
    std::lock_guard<std::mutex> lock(connectionMutex_);

    if (!connected_ || pahoClient_ == nullptr) {
        return;
    }

    logger_.info("正在断开MQTT连接...");

    // ⚠️ 关键：在调用paho的disconnect之前，先设置connected_=false
    // 这样如果paho触发回调，回调会立即返回
    connected_ = false;  // ← 提前设置

    // 断开连接（可能触发onConnectionLostCallback）
    int rc = MQTTClient_disconnect(pahoClient_, timeoutMs_);

    if (rc != MQTTCLIENT_SUCCESS) {
        logger_.warning("断开MQTT连接失败, 错误码: " + std::to_string(rc));
    } else {
        logger_.info("MQTT连接已断开");
    }
}
```

**崩溃场景**:

```
正常关闭时:
1. 主线程: Application::shutdown()
2. 主线程: mqttClient_.disconnect()
3. 主线程: 调用 MQTTClient_disconnect(pahoClient_, timeoutMs_)
4. paho线程: 触发 onConnectionLostCallback()  ← 此时对象可能在析构
5. paho线程: 访问 self->logger_  ← 💥 Segmentation Fault!
```

**修复后的时序**:

```
正常关闭时:
1. 主线程: Application::shutdown()
2. 主线程: mqttClient_.disconnect()
3. 主线程: connected_ = false  ← 提前设置标志
4. 主线程: 调用 MQTTClient_disconnect(pahoClient_, timeoutMs_)
5. paho线程: 触发 onConnectionLostCallback()
6. paho线程: 检查 !self->connected_  ← 发现已断开
7. paho线程: return  ← 立即返回，不访问任何成员 ✅
```

### 详细讲解

**为什么需要检查对象状态？**

1. **异步性质**: paho 的回调在其内部线程中执行，与应用程序主线程异步
2. **析构时序**:
   - 主线程调用 `disconnect()` 或对象析构
   - paho 内部可能还有待处理的事件
   - paho 可能在对象析构期间或之后调用回调
3. **悬空指针**:
   - `context` 指针（即 `this`）可能指向已释放的内存
   - 访问成员变量会读取无效内存，导致段错误

**三种保护方案对比**:

| 方案         | 优点             | 缺点                     | 本项目选择 |
| ------------ | ---------------- | ------------------------ | ---------- |
| 状态标志检查 | 简单高效         | 需要确保标志访问的原子性 | ✅ 采用    |
| 智能指针管理 | 完全内存安全     | 增加复杂度和开销         | ❌         |
| 同步取消注册 | 确保回调不再执行 | 可能阻塞析构             | ❌         |

**方案 1：状态标志检查** (本项目采用)

```cpp
void callback(void* context) {
    auto* self = static_cast<MyClass*>(context);
    if (!self->is_valid_) return;  // ← 检查标志
    self->logger_.info("...");     // 安全
}

void disconnect() {
    is_valid_ = false;  // 提前设置
    paho_disconnect();  // 再调用可能触发回调的函数
}
```

**方案 2：智能指针管理**

```cpp
class MyClass : public std::enable_shared_from_this<MyClass> {
    void register_callback() {
        // 传递 weak_ptr 而不是 this
        auto weak_self = weak_from_this();
        register_callback([weak_self]() {
            auto self = weak_self.lock();  // 尝试获取 shared_ptr
            if (!self) return;  // 对象已销毁，直接返回
            // 使用 self
        });
    }
};
```

**方案 3：同步取消注册**

```cpp
~MyClass() {
    unregister_all_callbacks();  // 确保不再有回调执行
    wait_for_callbacks_finish();  // 等待正在执行的回调完成
}
```

### 面试要点

**Q: 如何保证异步回调中对象指针的有效性？**

**A**: 有三种主要方法：

1. **状态标志检查** (简单)

   - 在回调开头检查对象的有效性标志
   - 对象析构前先设置标志为无效
   - 优点：简单高效；缺点：需要确保标志访问的原子性

2. **智能指针管理** (安全)

   - 使用 `shared_ptr` 管理对象生命周期
   - 回调中通过 `weak_ptr` 尝试获取对象
   - 优点：完全内存安全；缺点：增加复杂度和开销

3. **同步取消注册** (彻底)
   - 析构时取消所有回调注册
   - 等待正在执行的回调完成
   - 优点：确保回调不会在析构后执行；缺点：可能阻塞析构

**本项目采用方案 1**，因为：

- MQTT 客户端是单例，生命周期由程序管理
- 只需在 `disconnect()` 时设置标志即可
- 性能开销最小

❌ **错误 1**: 不检查对象状态，直接访问成员

```cpp

```

```cpp
void disconnect() {

```

```cpp
}
```

## 📌 Copy-on-Iterate 模式（观察者模式线程安全） ⭐⭐⭐⭐⭐

### 知识点

**Copy-on-Iterate**: 在迭代容器前先拷贝一份，确保迭代过程不受原容器修改影响。

**核心思想**:

- 时间换安全: 拷贝有开销，但保证迭代器不失效
- 快照语义: 迭代的是"当时"的观察者列表
- 解耦生命周期: 原容器修改不影响迭代

**为什么需要？**

在观察者模式中，通知观察者时可能发生：

1. **观察者注册**: 在回调中添加新观察者
2. **观察者注销**: 在回调中移除观察者（包括自己）
3. **观察者析构**: 另一个线程正在析构观察者

---

### 经典例子

```cpp
class EventDispatcher {
private:
    std::vector<EventListener*> listeners_;
    std::mutex listenersMutex_;

public:
    // ❌ 错误：直接迭代可能导致迭代器失效
    void notifyBad(const Event& event) {
        std::lock_guard<std::mutex> lock(listenersMutex_);

        for (auto* listener : listeners_) {
            listener->onEvent(event);  // 如果回调中移除了listener，崩溃
        }
    }

    // ✅ 正确：copy-on-iterate
    void notifyGood(const Event& event) {
        std::lock_guard<std::mutex> lock(listenersMutex_);

        // 拷贝列表（只拷贝指针，很快）
        std::vector<EventListener*> listenersCopy = listeners_;

        // 迭代拷贝（原列表修改不影响）
        for (auto* listener : listenersCopy) {
            if (listener == nullptr) continue;  // 空指针检查

            try {
                listener->onEvent(event);
            } catch (const std::exception& e) {
                // 异常隔离：一个观察者崩溃不影响其他
                log_error("Listener error: " + std::string(e.what()));
            } catch (...) {
                // 捕获所有异常
                log_error("Listener unknown error");
            }
        }
    }
};
```

```cpp
// ❌ Bug版本：直接迭代，不安全
void MqttClient::Impl::notifyConnected(const std::string& serverUri) {
    std::lock_guard<std::mutex> lock(observersMutex_);

    // 直接迭代 observers_
    for (auto* observer : observers_) {
        try {
            observer->onConnected(serverUri);  // ← 💥 可能访问已删除的观察者
        } catch (const std::exception& e) {
            logger_.error("观察者处理连接成功异常: " + std::string(e.what()));
        }

// ✅ 修复版本：copy-on-iterate + 空指针检查 + 完整异常处理
void MqttClient::Impl::notifyConnected(const std::string& serverUri) {
    std::lock_guard<std::mutex> lock(observersMutex_);

    logger_.debug("🔔 notifyConnected 开始，观察者数量: " + std::to_string(observers_.size()));
    logger_.info("🎯 准备通知观察者: MQTT连接成功");

    // ⭐ 1. 拷贝列表（防止迭代器失效）
    std::vector<IMqttMessageObserver*> observersCopy = observers_;

    logger_.debug("✅ 观察者列表已拷贝，开始通知...");

    int index = 0;
    for (auto* observer : observersCopy) {  // 迭代拷贝
        logger_.info("📍 通知观察者 #" + std::to_string(index) + " 地址=" +
                     std::to_string(reinterpret_cast<uintptr_t>(observer)));

        // ⭐ 2. 空指针检查（防止访问nullptr）
        if (observer == nullptr) {
            logger_.warning("⚠️ 观察者 #" + std::to_string(index) + " 是空指针，跳过");
            index++;
            continue;
        }

        try {
            logger_.info("➡️ 即将调用观察者 #" + std::to_string(index) + "->onConnected()");
            observer->onConnected(serverUri);
            logger_.info("✅ 观察者 #" + std::to_string(index) + " 处理完成");
        } catch (const std::exception& e) {
            // ⭐ 3. 异常隔离（一个观察者崩溃不影响其他）
            logger_.error("❌ 观察者 #" + std::to_string(index) + " 处理连接成功异常: " + std::string(e.what()));
        } catch (...) {
            // ⭐ 4. 捕获所有异常（包括访问悬空指针可能抛出的异常）
            logger_.error("💥 观察者 #" + std::to_string(index) + " 处理连接成功时发生未知异常");
        }

        index++;
    }

    logger_.info("🏁 notifyConnected 完成，已通知 " + std::to_string(index) + " 个观察者");
}
```

**崩溃场景**:

```
时间线                 线程A (通知线程)              线程B (析构线程)
─────────────────────────────────────────────────────────────────────
T1                     Lock observersMutex_
T2                     Start iterate observers_
                       [MqttHandler*]
T3                     Call observer[0]->onConnected()
                                                     T4: ~MqttHandler() 析构
                                                     T5: removeObserver(this)
                                                     T6: Wait for observersMutex_...
                                                         (被Thread A持有)
T7                     Continue iterate...
T8                     Unlock observersMutex_
                                                     T9: Acquire lock
                                                     T10: Remove MqttHandler
                                                     T11: Delete MqttHandler
T12                    Access next observer
                       ← 💥 访问已删除的对象！
                          Segmentation Fault!
```

**修复后的时序**:

```
时间线                 线程A (通知线程)              线程B (析构线程)
─────────────────────────────────────────────────────────────────────
T1                     Lock observersMutex_
T2                     Copy observers_ → observersCopy  ← ⭐ 拷贝
                       [MqttHandler*]
T3                     Start iterate observersCopy  ← ⭐ 迭代拷贝
T4                     Call observer[0]->onConnected()
                                                     T5: ~MqttHandler() 析构
                                                     T6: removeObserver(this)
                                                     T7: Wait for observersMutex_...
T8                     Continue iterate observersCopy  ← ⭐ 继续迭代拷贝
T9                     Unlock observersMutex_
                                                     T10: Acquire lock
                                                     T11: Remove MqttHandler from observers_
                                                     T12: Delete MqttHandler
T13                    ← ⭐ 已经迭代完成，没有访问原列表
                       ✅ 不会崩溃！
```

### 详细讲解

**为什么必须在锁内拷贝？**

```cpp
// ❌ 错误写法：锁外拷贝
void notifyConnected(const std::string& serverUri) {
    std::vector<IMqttMessageObserver*> observersCopy;

    {
        std::lock_guard<std::mutex> lock(observersMutex_);
        observersCopy = observers_;  // 在锁内拷贝
    }  // ← 锁释放了

    // ⚠️ 问题：从这里到下面的循环之间，observers_可能已经改变
    // 但observersCopy还是旧的，可能包含已删除的观察者指针

    for (auto* observer : observersCopy) {
        observer->onConnected(serverUri);  // ← 可能访问悬空指针！
    }
}

// ✅ 正确写法：锁内拷贝，锁内迭代
void notifyConnected(const std::string& serverUri) {
    std::lock_guard<std::mutex> lock(observersMutex_);

    // 1. 在锁保护下拷贝（保证拷贝时列表稳定）
    std::vector<IMqttMessageObserver*> observersCopy = observers_;

    // 2. 虽然持有锁，但迭代的是拷贝（不影响原列表）
    // 3. 如果其他线程调用removeObserver()，会等待锁
    // 4. 等我们迭代完释放锁后，removeObserver()才能执行
    // 5. 此时即使原列表被修改，也不影响我们的observersCopy

    for (auto* observer : observersCopy) {
        if (observer == nullptr) continue;
        observer->onConnected(serverUri);
    }
}
```

**三重保护机制**:

```cpp
void notifyConnected(const std::string& serverUri) {
    std::lock_guard<std::mutex> lock(observersMutex_);

    // ⭐ 保护1：拷贝（防止迭代器失效）
    std::vector<IMqttMessageObserver*> observersCopy = observers_;

    for (auto* observer : observersCopy) {
        // ⭐ 保护2：空指针检查（防止访问nullptr）
        if (observer == nullptr) {
            continue;
        }

        try {
            observer->onConnected(serverUri);
        } catch (const std::exception& e) {
            // ⭐ 保护3a：异常隔离（一个观察者崩溃不影响其他）
            logger_.error("观察者处理连接成功异常: " + std::string(e.what()));
        } catch (...) {
            // ⭐ 保护3b：捕获所有异常（包括访问悬空指针可能抛出的异常）
            logger_.error("观察者处理连接成功时发生未知异常");
        }
    }
}
```

### 面试要点

**Q1: 为什么观察者模式容易出现线程安全问题？**

**A**:

1. **生命周期不对等**: Subject 持有 Observer 指针，但不拥有生命周期
2. **异步通知**: 通知可能在回调线程、重连线程等多个线程发生
3. **容器修改**: 回调过程中 Observer 可能注册/注销，修改容器
4. **时间窗口**: 从"开始通知"到"通知结束"之间，状态可能改变

**项目例子**:

```cpp
// MqttClient 通知 MqttHandler 连接成功
// 同时 Application 正在析构 MqttHandler
// 导致 MqttClient 访问已删除的 MqttHandler 指针
```

**Q2: Copy-on-Iterate 模式的开销大吗？**

**A**:

- **拷贝开销**: O(N)，N 是观察者数量
- **通常可接受**: 观察者数量一般很少（<10 个）
- **vector 拷贝**: 只拷贝指针，非常快（每个 8 字节）
- **相比崩溃**: 这点开销完全值得

**优化建议**:

```cpp
// 如果观察者数量巨大（>1000），可以考虑：
// 1. 使用 shared_ptr 管理观察者生命周期
// 2. 使用 weak_ptr 存储观察者，通知时lock()
// 3. 使用读写锁（shared_mutex）减少锁竞争
```

**Q3: 为什么需要 catch(...) 捕获所有异常？**

**A**:

1. **未知异常**: 访问悬空指针可能抛出任何异常
2. **异常隔离**: 确保一个观察者崩溃不影响其他观察者
3. **日志记录**: 至少记录下发生了异常，方便排查
4. **健壮性**: 即使出现预期外的异常，也不会导致程序崩溃

❌ **错误 3**: 没有异常处理

```cpp
void notify() {
    std::lock_guard<std::mutex> lock(mutex_);
    std::vector<Observer*> copy = observers_;
    for (auto* observer : copy) {
        observer->onEvent();  // 💥 一个异常会中断所有通知
    }
}
```

✅ **正确 3**: 完整异常处理

```cpp
void notify() {
    std::lock_guard<std::mutex> lock(mutex_);
    std::vector<Observer*> copy = observers_;
    for (auto* observer : copy) {
        if (observer == nullptr) continue;
        try {
            observer->onEvent();
        } catch (const std::exception& e) {
            log_error("Observer error: " + std::string(e.what()));
        } catch (...) {
            log_error("Observer unknown error");
        }
    }
}
```

## 📌 原子操作与 CAS（Compare-And-Swap） ⭐⭐⭐⭐

### 知识点

**原子操作**: 不可分割的操作，在多线程环境中不会被中断。

**CAS (Compare-And-Swap)**:

- 比较变量的当前值和期望值
- 如果相等，则将变量设置为新值
- 如果不相等，则不修改，返回失败
- **整个过程是原子的**

**为什么需要？**

防止并发操作导致的竞争条件（Race Condition）。

---

### 经典例子

```cpp
#include <atomic>

// ❌ 错误：非原子操作
class Counter {
private:
    int count_ = 0;

public:
    void increment() {
        count_++;  // 💥 非原子！分为3步：读取、加1、写回
    }

    int get() const {
        return count_;  // 💥 可能读到不一致的值
    }
};

// ✅ 正确：原子操作
class AtomicCounter {
private:
    std::atomic<int> count_{0};

public:
    void increment() {
        count_++;  // ✅ 原子操作
        // 等价于: count_.fetch_add(1);
    }

    int get() const {
        return count_.load();  // ✅ 原子读取
    }
};

// ✅ 高级：CAS操作
class FlagGuard {
private:
    std::atomic<bool> flag_{false};

public:
    // 尝试获取权限
    bool tryAcquire() {
        bool expected = false;  // 期望值：当前为false
        // 如果 flag_ == false，则设置为 true，返回 true
        // 如果 flag_ == true，则不修改，返回 false
        return flag_.compare_exchange_strong(expected, true);
    }

    // 释放权限
    void release() {
        flag_.store(false);  // 原子写入
    }
};

// 使用示例
FlagGuard guard;

// 线程1
if (guard.tryAcquire()) {
    // 成功获取权限，执行操作
    do_work();
    guard.release();
} else {
    // 失败，已有其他线程在执行
}

// 线程2
if (guard.tryAcquire()) {
    // 失败（线程1已获取）
} else {
    // ...
}
```

### 项目中的例子

```cpp
// ❌ Bug版本：没有防止并发重连
void MqttClient::Impl::attemptReconnect() {
    logger_.info("尝试第 " + std::to_string(currentRetries_) + " 次重连...");

    // 💥 问题：多个线程可能同时进入这里
    std::this_thread::sleep_for(std::chrono::milliseconds(retryIntervalMs_));

    bool result = connect();
    if (result) {
        logger_.info("MQTT重连成功");
        currentRetries_ = 0;
    } else {
        logger_.warning("MQTT重连失败");
        // 递归重试
        if (currentRetries_ < maxRetries_) {
            attemptReconnect();  // 💥 多个线程递归调用
        }
    }
}

// ✅ 修复版本：使用原子标志防止并发重连
class MqttClient::Impl {
private:
    std::atomic<bool> reconnecting_{false};  // 原子标志

public:
    void attemptReconnect() {
        // ⭐ 使用CAS原子操作检查并设置重连标志
        bool expected = false;
        if (!reconnecting_.compare_exchange_strong(expected, true)) {
            // CAS失败：已有重连在进行，直接返回
            logger_.warning("已有重连在进行中，跳过本次重连");
            return;
        }

        logger_.info("🔒 获取重连权限，开始重连...");

        // 执行重连逻辑
        logger_.info("尝试第 " + std::to_string(currentRetries_) + " 次重连...");
        std::this_thread::sleep_for(std::chrono::milliseconds(retryIntervalMs_));

        bool result = connect();
        if (result) {
            logger_.info("MQTT重连成功");
            currentRetries_ = 0;
        } else {
            logger_.warning("MQTT重连失败");
            if (currentRetries_ < maxRetries_) {
                // 递归重试（但只有一个线程会执行）
                attemptReconnect();
            }
        }

        // 释放重连权限
        reconnecting_ = false;
        logger_.info("💔 ✅ 重连流程结束，释放重连权限");
    }
};
```

**并发场景**:

```
时间线                 线程A                       线程B                       线程C
────────────────────────────────────────────────────────────────────────────────────
T1                     onConnectionLostCallback()
T2                     reconnecting_ = false
T3                     CAS(false, true) = true ✅
T4                     开始重连...
                                                   T5: onConnectionLostCallback()
                                                   T6: reconnecting_ = true
                                                   T7: CAS(true, true) = false ❌
                                                   T8: 直接返回 ✅
                                                                               T9: onConnectionLostCallback()
                                                                               T10: reconnecting_ = true
                                                                               T11: CAS(true, true) = false ❌
                                                                               T12: 直接返回 ✅
T13                    connect() 成功
T14                    reconnecting_ = false
```

**修复效果**:

- ✅ 同一时间只有一个线程在重连
- ✅ 其他线程的重连请求被忽略
- ✅ 避免了多个线程同时连接的资源竞争

### 详细讲解

**CAS 操作的原理**:

```cpp
// compare_exchange_strong() 的伪代码
bool compare_exchange_strong(T& expected, T desired) {
    // 原子地执行以下逻辑：
    if (current_value == expected) {
        current_value = desired;
        return true;  // 成功
    } else {
        expected = current_value;  // 更新期望值为当前值
        return false;  // 失败
    }
}
```

**项目中的使用**:

```cpp
std::atomic<bool> reconnecting_{false};

// 尝试获取重连权限
bool expected = false;  // 期望当前为false（没有重连）
if (reconnecting_.compare_exchange_strong(expected, true)) {
    // CAS成功：reconnecting_ 从 false 变为 true
    // 现在只有这个线程在执行重连
    do_reconnect();
    reconnecting_ = false;  // 释放权限
} else {
    // CAS失败：reconnecting_ 已经是 true（有其他线程在重连）
    // expected 被更新为 true
    return;  // 直接返回，不重连
}
```

**为什么不用 mutex？**

```cpp
// 方案1：使用mutex（更重）
std::mutex reconnect_mutex_;
bool reconnecting_ = false;

void attemptReconnect() {
    std::lock_guard<std::mutex> lock(reconnect_mutex_);  // 获取锁
    if (reconnecting_) {
        return;  // 已有重连
    }
    reconnecting_ = true;

    do_reconnect();

    reconnecting_ = false;
}

// 方案2：使用atomic（更轻）
std::atomic<bool> reconnecting_{false};

void attemptReconnect() {
    bool expected = false;
    if (!reconnecting_.compare_exchange_strong(expected, true)) {
        return;  // 已有重连
    }

    do_reconnect();

    reconnecting_ = false;
}
```

**对比**:

| 特性       | mutex                | atomic + CAS       |
| ---------- | -------------------- | ------------------ |
| 性能       | 较低（涉及系统调用） | 高（CPU 原子指令） |
| 开销       | 较大                 | 极小               |
| 阻塞       | 可能阻塞             | 不阻塞（直接返回） |
| 适用场景   | 保护复杂临界区       | 简单标志检查       |
| 代码复杂度 | 简单                 | 简单               |

**本项目选择 atomic 的原因**:

- 只需要一个简单的标志
- 不需要保护复杂的数据结构
- 性能要求高（回调频繁触发）

### 面试要点

**Q1: 什么是原子操作？为什么需要？**

**A**:

- **定义**: 不可分割的操作，在多线程环境中不会被中断
- **问题**: 普通的 `count++` 分为 3 步：读取、加 1、写回，多线程会出现竞争
- **解决**: `std::atomic<int>` 提供原子操作，保证线程安全

**Q2: CAS 操作有什么用？**

**A**:

- **用途**: 无锁编程，避免互斥锁的开销
- **原理**: 比较当前值和期望值，相等才修改
- **优点**:
  - 性能高（CPU 原子指令）
  - 无阻塞（失败直接返回）
  - 适合简单的标志检查

**项目例子**:

```cpp
// 防止并发重连
bool expected = false;
if (reconnecting_.compare_exchange_strong(expected, true)) {
    // 成功获取重连权限
    do_reconnect();
    reconnecting_ = false;
} else {
    // 失败，已有重连在进行
    return;
}
```

**Q3: 原子操作 vs 互斥锁，如何选择？**

**A**:

| 场景             | 选择         | 原因                  |
| ---------------- | ------------ | --------------------- |
| 简单标志检查     | atomic       | 性能高，无阻塞        |
| 计数器           | atomic       | 原子递增/递减         |
| 保护复杂数据结构 | mutex        | 需要保护多个操作      |
| 长时间临界区     | mutex        | atomic 不适合复杂逻辑 |
| 读写锁场景       | shared_mutex | 读多写少的场景        |

### 易错点

❌ **错误 1**: 普通变量当原子变量用

```cpp
bool flag = false;  // 💥 非原子

void thread1() {
    flag = true;  // 💥 可能被优化，其他线程看不到
}

void thread2() {
    if (flag) {  // 💥 可能读到旧值
        // ...
    }
}
```

✅ **正确 1**: 使用 std::atomic

```cpp
std::atomic<bool> flag{false};  // ✅ 原子

void thread1() {
    flag.store(true);  // ✅ 原子写入
}

void thread2() {
    if (flag.load()) {  // ✅ 原子读取
        // ...
    }
}
```

❌ **错误 2**: 原子操作的组合不是原子的

```cpp
std::atomic<int> count{0};

void increment() {
    if (count < 10) {  // 读取
        count++;       // 修改
    }
    // 💥 两个原子操作的组合不是原子的！
}
```

✅ **正确 2**: 使用 CAS 或 mutex 保护

```cpp
std::atomic<int> count{0};

void increment() {
    int expected;
    do {
        expected = count.load();
        if (expected >= 10) break;
    } while (!count.compare_exchange_weak(expected, expected + 1));
    // ✅ 使用CAS确保整个操作原子性
}
```

❌ **错误 3**: 错误理解 CAS 的 expected 参数

```cpp
std::atomic<bool> flag{false};

void tryAcquire() {
    bool expected = false;
    if (!flag.compare_exchange_strong(expected, true)) {
        // 💥 错误：expected的值已经被修改了
        // 以为expected还是false，实际上已经是true
    }
}
```

✅ **正确 3**: 理解 expected 会被修改

```cpp
std::atomic<bool> flag{false};

void tryAcquire() {
    bool expected = false;
    if (!flag.compare_exchange_strong(expected, true)) {
        // ✅ 正确：expected现在是flag的当前值（true）
        std::cout << "CAS failed, current value: " << expected << std::endl;
    }
}
```
