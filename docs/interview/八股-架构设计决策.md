## 🎯 标准回答框架

### 第一步：讲述背景（Situation）

```
"在我们的 DJI ESDK 项目重构中，Vision 模块包含三个组件：
1. VisionUtils：核心算法（NMS、IoU 等）
2. VisionConfigLoader：配置文件管理
3. Visualizer：检测结果可视化

项目初期这三个是独立的模块，但随着代码量增加，
我们需要评估是否应该合并它们以简化架构。"
```

### 第二步：分析决策依据（Task + Analysis）

我使用了一个 **四维度决策矩阵**：

| 决策维度          | 权重 | 说明                   |
| ----------------- | ---- | ---------------------- |
| **1. 职责相关性** | 35%  | 功能是否属于同一领域？ |
| **2. 代码规模**   | 25%  | 合并后是否过大？       |
| **3. 依赖一致性** | 25%  | 依赖库是否相同？       |
| **4. 改变频率**   | 15%  | 修改原因是否相同？     |

### 第三步：实际评估（Action）

#### 评估 1：Visualizer vs VisionUtils

```
维度分析（5分制）：

1. 职责相关性：5/5 ✅
   - Visualizer：绘制检测框
   - VisionUtils：处理检测结果
   - 结论：都属于视觉处理领域，职责高度相关

2. 代码规模：5/5 ✅
   - Visualizer：100 行
   - VisionUtils：750 行
   - 合并后：850 行
   - 结论：规模适中，单一文件不超过 1000 行

3. 依赖一致性：5/5 ✅
   - Visualizer：OpenCV (cv::rectangle, cv::putText)
   - VisionUtils：OpenCV (cv::Rect, cv::Mat)
   - 结论：依赖完全一致

4. 改变频率：5/5 ✅
   - 修改原因：算法优化、可视化效果调整
   - 结论：通常同步修改（如 NMS 改进时需要更新可视化）

总分：20/20 → 决策：✅ 合并
```

#### 评估 2：VisionConfigLoader vs VisionUtils

```
维度分析（5分制）：

1. 职责相关性：2/5 ❌
   - VisionConfigLoader：配置文件读写、JSON 解析
   - VisionUtils：算法实现、数据处理
   - 结论：属于不同领域（配置管理 vs 算法实现）

2. 代码规模：2/5 ❌
   - VisionConfigLoader：300+ 行
   - VisionUtils：750 行
   - 合并后：1050+ 行
   - 结论：过大，违反"单一文件不超过 1000 行"原则

3. 依赖一致性：2/5 ❌
   - VisionConfigLoader：nlohmann::json, std::filesystem
   - VisionUtils：OpenCV
   - 结论：依赖不同，职责不同

4. 改变频率：2/5 ❌
   - 修改原因：
     - VisionConfigLoader：配置格式变化
     - VisionUtils：算法优化
   - 结论：独立变化，不同步

总分：8/20 → 决策：❌ 不合并
```

## 📚 深入知识点

### 知识点 1：SOLID 原则中的 SRP（单一职责原则）

**定义**：

> "A class should have only one reason to change."  
> 一个类应该只有一个改变的理由。

**应用到我们的案例**：

```cpp
// ✅ 正确示例：职责分离
class VisionUtils {
    // 改变原因：算法优化
    static std::vector<BBox> nms(...);
    static float calculateIoU(...);
    static void drawDetections(...);  // 可视化也属于算法输出
};

class VisionConfigLoader {
    // 改变原因：配置格式变化
    bool loadConfig(const std::string& path);
    void saveConfig(const std::string& path);
};

// ❌ 错误示例：职责混乱
class VisionModule {
    // 多个改变原因！
    std::vector<BBox> nms(...);        // 原因 1：算法优化
    bool loadConfig(...);              // 原因 2：配置格式
    void connectDatabase(...);         // 原因 3：数据库迁移
    void sendEmail(...);               // 原因 4：邮件服务变化
    // 这个类有 4 个改变的理由，违反 SRP！
};
```

**判断方法**：

1. 列出类的所有方法
2. 思考每个方法为什么会修改
3. 如果有多个不同的原因 → 违反 SRP → 需要拆分

### 知识点 2：高内聚、低耦合

**内聚（Cohesion）**：模块内部元素的紧密程度

```cpp
// ✅ 高内聚：VisionUtils 的方法都相互关联
class VisionUtils {
    static std::vector<BBox> nms(const std::vector<BBox>& boxes, float iouThreshold) {
        std::vector<BBox> result;
        for (const auto& box : boxes) {
            bool keep = true;
            for (const auto& selected : result) {
                if (calculateIoU(box, selected) > iouThreshold) {  // ← 调用同模块方法
                    keep = false;
                    break;
                }
            }
            if (keep) result.push_back(box);
        }
        return result;
    }

    static float calculateIoU(const BBox& a, const BBox& b) {
        // IoU 计算
    }
};
// nms() 和 calculateIoU() 紧密相关 → 高内聚 ✅

// ❌ 低内聚：方法之间没有关联
class RandomUtils {
    static std::vector<BBox> nms(...);     // 视觉算法
    static bool loadConfig(...);           // 配置管理
    static void sendEmail(...);            // 邮件发送
    static int calculateAge(...);          // 业务逻辑
    // 这些方法毫不相关 → 低内聚 ❌
};
```

**耦合（Coupling）**：模块之间的依赖程度

```cpp
// ✅ 低耦合：Visualizer 合并后不增加依赖
// 合并前：
class VisionUtils {
    // 依赖：OpenCV
};
class Visualizer {
    // 依赖：OpenCV
};

// 合并后：
class VisionUtils {
    // 依赖：OpenCV（没有增加！）
    static void drawDetections(...);  // 来自 Visualizer
};

// ❌ 高耦合：如果合并 VisionConfigLoader
class VisionUtils {
    // 依赖：OpenCV + nlohmann::json + std::filesystem
    // 依赖增加 → 耦合度提高 → 不推荐
};
```

### 知识点 3：代码规模的阈值

**经验法则**：

| 文件类型 | 推荐行数  | 最大行数  | 超过时的处理   |
| -------- | --------- | --------- | -------------- |
| 头文件   | < 500     | < 1000    | 拆分为多个接口 |
| 源文件   | < 800     | < 1500    | 提取辅助类     |
| 类定义   | < 30 方法 | < 50 方法 | 拆分职责       |
| 函数     | < 50 行   | < 100 行  | 提取子函数     |

**实际案例**：

```cpp
// VisionUtils.cpp 当前状态
// - P0 NMS 实现：~150 行
// - P1 高级 NMS：~200 行
// - P1 过滤方法：~180 行
// - P1 坐标转换：~130 行
// - P1 IoU 计算：~150 行
// - 可视化：~120 行
// - P2 评估指标：~80 行
// 总计：~1010 行

// 判断：刚好超过 1000 行阈值
// 策略：
// 1. P2 方法目前是空实现（只有框架）
// 2. 可视化只有 2 个方法，职责相关
// 3. 决策：✅ 可以接受（临界值）
// 4. 如果将来 P2 实现后超过 1500 行 → 考虑拆分

// 拆分方案（如果需要）：
// VisionUtils.cpp         (核心 NMS/IoU，~600 行)
// VisionFilters.cpp       (过滤/转换，~300 行)
// VisionMetrics.cpp       (评估指标，~200 行)
// VisionVisualization.cpp (可视化，~120 行)
```

### 知识点 4：依赖分析

**依赖类型**：

```cpp
// 1. 编译期依赖（头文件）
#include <opencv2/opencv.hpp>    // OpenCV
#include <nlohmann/json.hpp>     // JSON 库
// 影响：增加编译时间

// 2. 链接期依赖（库文件）
target_link_libraries(vision PRIVATE
    ThirdParty::OpenCV    # libopencv_core.so
    ThirdParty::Json      # 头文件库（无链接产物）
)
// 影响：增加可执行文件大小

// 3. 运行期依赖（动态库）
dlopen("libopencv_core.so")
// 影响：启动时间、部署复杂度
```

**依赖一致性评估**：

```
场景 1：Visualizer + VisionUtils
  Visualizer 依赖：OpenCV
  VisionUtils 依赖：OpenCV
  ✅ 依赖一致 → 合并不增加复杂度

场景 2：VisionConfigLoader + VisionUtils
  VisionConfigLoader 依赖：nlohmann::json, std::filesystem
  VisionUtils 依赖：OpenCV
  ❌ 依赖不同 → 合并增加耦合

场景 3：MqttHandler + TaskManager
  MqttHandler 依赖：paho.mqtt.c, nlohmann::json
  TaskManager 依赖：OpenCV, std::thread
  ❌ 依赖完全不同 → 应该分离
```

## 🎓 面试延伸问题

### Q1: 如果项目快速迭代，时间紧张，是否可以放宽合并标准？

**A**: 可以，但要权衡：

```
短期策略（快速迭代）：
- 允许临时合并（如 850 → 1200 行）
- 在注释中标记 "TODO: 重构"
- 设置技术债务追踪

长期策略（稳定后）：
- 安排重构任务（Sprint 最后一周）
- 遵循严格的模块划分
- 定期 Code Review

实际案例：
我们项目初期 VisionUtils 达到 1200 行，
但在 Day 14 重构时严格按标准拆分。
结果：后续开发效率提升 30%（减少冲突、易于测试）
```

### Q2: 如果两个模块职责相关，但依赖不同，如何取舍？

**A**: 优先考虑职责，但需要分层：

```cpp
// 方案 1：分层架构（推荐）
class VisionCore {
    // 核心算法，无外部依赖
    static float calculateIoU(const BBox& a, const BBox& b);
};

class VisionUtils : public VisionCore {
    // 依赖 OpenCV 的实现
    static void drawDetections(cv::Mat& image, const std::vector<BBox>& boxes);
};

class VisionConfigLoader {
    // 依赖 nlohmann::json
    bool loadConfig(const std::string& path);
};

// 方案 2：依赖注入（高级）
class VisionUtils {
    VisionUtils(IConfigLoader* loader, IVisualizer* viz);  // 注入依赖
    // 降低耦合，但增加复杂度
};
```

### Q3: 如何评估一个模块划分是否合理？

**A**: 使用 **LCOM (Lack of Cohesion of Methods)** 指标：

```cpp
// ✅ 低 LCOM（高内聚）
class VisionUtils {
private:
    static std::vector<BBox> boxes_;  // 共享数据

public:
    static void addBox(const BBox& box) { boxes_.push_back(box); }
    static void removeBox(int index) { boxes_.erase(boxes_.begin() + index); }
    static std::vector<BBox> nms(float threshold) { /* 使用 boxes_ */ }
};
// 所有方法都访问共享数据 → LCOM = 0 → 高内聚 ✅

// ❌ 高 LCOM（低内聚）
class RandomModule {
private:
    int age_;        // 只被 calculateAge() 使用
    std::string ip_; // 只被 sendRequest() 使用

public:
    int calculateAge() { return age_; }
    void sendRequest() { /* 使用 ip_ */ }
};
// 方法之间没有共享数据 → LCOM = 高 → 低内聚 → 应该拆分 ❌
```

**计算公式**：

```
LCOM = (P - Q) / M
P = 方法对之间没有共享变量的数量
Q = 方法对之间有共享变量的数量
M = 方法总数

LCOM 越小 → 内聚越高 → 模块划分越合理
```

### 技巧 2：使用 "单一改变点" 测试

```
问题：如果我要修改 XXX，需要改几个文件？

示例：
1. 修改 NMS 算法：
   - VisionUtils.cpp（1 个文件）
   - ✅ 单一改变点

2. 修改配置文件格式：
   - VisionConfigLoader.cpp（1 个文件）
   - ✅ 单一改变点

3. 如果合并：
   - VisionUtils.cpp（包含算法 + 配置）
   - ❌ 两个不相关的改变原因在同一文件
   - 结论：不应该合并
```

## ✅ 总结

**模块合并的黄金法则**：

1. **职责相关性优先**：不相关的功能坚决分离
2. **代码规模适中**：单文件不超过 1000 行
3. **依赖一致性**：避免引入不必要的依赖
4. **改变频率相同**：同步修改的代码应该在一起

**记忆口诀**：

```
职责相关才合并，
代码规模要适中，
依赖一致降耦合，
改变同步好维护。
```

**实战案例**：

- ✅ Visualizer → VisionUtils（职责相关、依赖一致、规模适中）
- ❌ VisionConfigLoader → VisionUtils（职责不同、依赖不同、规模过大）
