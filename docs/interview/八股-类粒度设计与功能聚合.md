## 📌 什么是类粒度设计？

### 知识点

**类粒度（Class Granularity）** 是指类的大小和职责范围。

- **粗粒度类**：功能多、职责广，一个类包含多个相关功能
- **细粒度类**：功能少、职责窄,一个类只做一件事

### 经典例子

```cpp
// ❌ 过细粒度：一个功能一个类
class ExifParser {
    std::optional<ExifMetadata> parse(const std::string& file);
};

class ImageResizer {
    cv::Mat resize(const cv::Mat& img, int w, int h);
};

class Base64Encoder {
    std::string encode(const cv::Mat& img);
};

class JpegCompressor {
    bool compress(const cv::Mat& img, int quality);
};

// 问题：
// - 类数量爆炸（4个功能 = 4个头文件）
// - 职责分散，难以维护
// - 调用繁琐：ImageResizer::resize(), Base64Encoder::encode()

// ✅ 合适粒度：功能聚合
class ImageProcessor {
    // EXIF 解析
    std::optional<ExifMetadata> parseExif(const std::string& file);

    // 图片缩放
    cv::Mat resize(const cv::Mat& img, int w, int h);

    // Base64 编码
    std::string encodeBase64(const cv::Mat& img);

    // JPEG 压缩
    bool compressJpeg(const cv::Mat& img, int quality);
};

// 优点：
// - 高内聚：图片相关功能在一起
// - 易扩展：新增图片功能只需加方法
// - 易使用：ImageProcessor::getInstance().parseExif(...)
```

## 🎯 类粒度设计原则

### 1. 高内聚原则（High Cohesion）

**定义**: 一个类的所有方法应该紧密相关，服务于同一个目标。

#### ✅ 正确示例：ImageProcessor

```cpp
class ImageProcessor {
    // ✅ 高内聚：所有方法都是"图片处理"
    std::optional<ExifMetadata> parseExif(const std::string& file);
    cv::Mat resize(const cv::Mat& img, int w, int h);
    std::string encodeBase64(const cv::Mat& img);
    bool compressJpeg(const cv::Mat& img, int quality);
    cv::Mat crop(const cv::Mat& img, int x, int y, int w, int h);
};

// 判断标准：
// - 如果删除一个方法，其他方法是否仍然合理？✅ 是
// - 这些方法是否都操作相同的数据类型？✅ cv::Mat
// - 能否用一个词概括这个类？✅ "图片处理器"
```

#### ❌ 错误示例：低内聚

```cpp
class TaskManager {
    // ❌ 低内聚：职责混乱
    void startTask(const TaskConfig& config);      // 任务管理
    void sendMqttEvent(const std::string& topic);  // MQTT 通信 ⚠️
    void saveToDatabase(const Data& data);         // 数据库操作 ⚠️
    void calculateGps(double lat, double lon);     // GPS 计算 ⚠️
};

// 问题：
// - MQTT、数据库、GPS 都不是"任务管理"的核心职责
// - 修改 MQTT 逻辑可能影响 TaskManager（不稳定）
// - 违反单一职责原则（SRP）
```

### 2. 功能聚合原则（Feature Aggregation）

**定义**: 将相关的小功能聚合到一个大类中，而不是每个小功能一个类。

#### 判断标准

| 条件         | 说明                       | 结果               |
| ------------ | -------------------------- | ------------------ |
| **共同主题** | 功能是否属于同一主题？     | 图片处理 ✅        |
| **共同数据** | 功能是否操作相同数据类型？ | cv::Mat ✅         |
| **使用场景** | 功能是否在相同场景使用？   | 图片处理流程 ✅    |
| **依赖关系** | 功能之间是否有依赖？       | Resize → Encode ✅ |

#### 🔥 项目实例

**改进前**:

```cpp
// ❌ 过细粒度
class ExifParser { ... };        // 仅 EXIF 解析
class GpsCalculator { ... };     // 仅 GPS 计算
```

**改进后**:

```cpp
// ✅ 合适粒度
class ImageProcessor {           // 所有图片操作
    parseExif();                 // EXIF 解析
    resize();                    // 缩放
    encodeBase64();              // 编码
    // ... 其他图片处理功能
};

class GeoUtils {                 // 所有地理信息操作
    convertGpsToPixel();         // GPS 转像素
    calculateDistance();         // 距离计算
    isPointInPolygon();          // 区域判断
    // ... 其他地理计算功能
};
```

## 🎯 何时拆分，何时合并？

### 拆分类的信号 🚨

| 信号             | 示例                                 | 解决方案           |
| ---------------- | ------------------------------------ | ------------------ |
| **类过大**       | 一个类 > 1000 行代码                 | 按职责拆分         |
| **职责混乱**     | TaskManager 又管任务又发 MQTT        | 提取 MqttClient    |
| **多个变化原因** | 修改 GPS 逻辑影响图片处理            | 拆分为独立类       |
| **难以命名**     | TaskManagerMqttGpsHelper（名字太长） | 职责不清晰，需拆分 |

#### ❌ 错误示例：上帝类（God Class）

```cpp
class TaskManager {
    // ❌ 职责过多，应该拆分

    // 任务管理
    void createTask();
    void startTask();
    void stopTask();

    // MQTT 通信 ⚠️ 应提取为 MqttClient
    void connectMqtt();
    void publishEvent();

    // 数据库操作 ⚠️ 应提取为 Database
    void saveTask();
    void loadTask();

    // 日志管理 ⚠️ 应提取为 Logger
    void log(const std::string& msg);

    // 文件操作 ⚠️ 应提取为 FileUtils
    void readFile();
    void writeFile();
};

// 重构后：
class TaskManager { createTask(); startTask(); stopTask(); };
class MqttClient { connect(); publish(); };
class Database { save(); load(); };
class Logger { log(); };
class FileUtils { read(); write(); };
```

### 合并类的信号 🚨

| 信号         | 示例                                                        | 解决方案              |
| ------------ | ----------------------------------------------------------- | --------------------- |
| **类过小**   | 一个类只有 1-2 个方法                                       | 合并到相关大类        |
| **紧密耦合** | ExifParser 总是和 ImageResizer 一起用                       | 合并为 ImageProcessor |
| **文件爆炸** | 10 个功能 = 10 个头文件                                     | 按主题合并            |
| **调用链长** | ExifParser::parse() → Resizer::resize() → Encoder::encode() | 合并为一个类          |

#### ❌ 错误示例：过度分解

```cpp
// ❌ 每个小功能一个类
class ExifGpsExtractor {
    bool extractGps(const std::string& file, double& lat, double& lon);
};

class ExifTimestampExtractor {
    std::string extractTimestamp(const std::string& file);
};

class ExifCameraInfoExtractor {
    std::string extractCameraInfo(const std::string& file);
};

// 问题：
// - 3 个类都操作 EXIF 数据
// - 重复代码：都要打开文件、读取 EXIF
// - 调用繁琐：三个类分别调用

// ✅ 合并后：
class ImageProcessor {
    std::optional<ExifMetadata> parseExif(const std::string& file);
    // ExifMetadata 包含 GPS、时间戳、相机信息
};
```

## 🔥 项目实例对比

### 案例：图片处理功能

#### 改进前（过细粒度）❌

```cpp
// ❌ 5 个功能 = 5 个头文件
include/esdk_sophon/utils/
├── ExifParser.h              // EXIF 解析
├── ImageResizer.h            // 图片缩放
├── Base64Encoder.h           // Base64 编码
├── JpegCompressor.h          // JPEG 压缩
└── ImageRotator.h            // 图片旋转

// 使用时：
auto& exifParser = ExifParser::getInstance();
auto exif = exifParser.parse("photo.jpg");

auto& resizer = ImageResizer::getInstance();
auto resized = resizer.resize(image, 800, 600);

auto& encoder = Base64Encoder::getInstance();
auto base64 = encoder.encode(resized);

// 问题：
// - 5 个单例实例
// - 调用链冗长
// - 文件数量多
```

#### 改进后（合适粒度）✅

```cpp
// ✅ 所有功能 = 1 个头文件
include/esdk_sophon/utils/
└── ImageProcessor.h          // 所有图片处理功能

// 使用时：
auto& processor = ImageProcessor::getInstance();

// 链式调用
auto exif = processor.parseExif("photo.jpg");
auto resized = processor.resize(image, 800, 600);
auto base64 = processor.encodeBase64(resized);

// 优点：
// - 1 个单例实例
// - 调用简洁
// - 文件数量少
// - 易于扩展（新增方法即可）
```

### 案例：GPS 功能扩展

#### 改进前（只有 GPS 计算）❌

```cpp
// ❌ 功能单一
class GpsCalculator {
    PixelCoordinate calculate(const GpsInput& input);
    std::vector<PixelCoordinate> calculateBatch(const std::vector<GpsInput>& inputs);
};

// 问题：
// - 未来需要距离计算 → 创建 DistanceCalculator？
// - 未来需要区域判断 → 创建 AreaChecker？
// - 未来需要坐标转换 → 创建 CoordinateConverter？
```

```cpp
// ✅ 预留扩展空间
class GeoUtils {
    // GPS 计算（现有功能）
    PixelCoordinate convertGpsToPixel(const GpsCoordinate& gps);

                                   CoordinateSystem from,
                                   CoordinateSystem to);
};

// 优点：
// - 一次性设计，预留扩展
// - 新增功能不需要新文件
// - 调用统一：GeoUtils::getInstance().xxx()
```

## 🎯 面试标准答案

### Q1: 如何判断类的粒度是否合适？

**标准答案**:

> 我会从三个维度判断：
>
> 1. **内聚性**：类的所有方法是否围绕同一个主题？如果 `ImageProcessor` 里突然出现 `sendMqttEvent()`，就说明内聚性低。
>
> 2. **文件数量**：如果 10 个小功能产生 10 个头文件，说明粒度过细。我会将相关功能聚合为一个大类，比如 `ImageProcessor` 包含 EXIF 解析、缩放、编码等所有图片操作。
>
> 3. **变化频率**：如果修改一个小功能需要改多个类，说明职责分散。我会将紧密耦合的功能合并，减少修改范围。
>
> **项目实例**：我们最初设计了 `ExifParser` 和 `GpsCalculator` 两个独立类，后来发现：
>
> - `ExifParser` 只做 EXIF 解析，未来还需要图片缩放、Base64 编码等功能
> - 如果每个功能一个类，会产生 5-10 个头文件
>
> 于是我们重构为 `ImageProcessor`（图片处理）和 `GeoUtils`（地理信息）两个大类，每个类包含 10+ 个相关方法，既保持高内聚，又避免文件爆炸。

### Q2: 什么时候应该拆分类？

**标准答案**:

> 出现以下信号时应该拆分：
>
> 1. **类过大**：超过 1000 行代码，说明职责过多
> 2. **多个变化原因**：修改 GPS 逻辑影响图片处理，说明违反 SRP
> 3. **难以命名**：`TaskManagerMqttGpsHelper` 这种名字说明职责不清晰
>
> **项目实例**：我们的 `TaskManager` 最初既管任务生命周期，又负责 MQTT 通信。后来发现：
>
> - 修改 MQTT 重连逻辑需要改 `TaskManager`（不稳定）
> - 测试任务管理时被 MQTT 依赖干扰
>
> 于是拆分为：
>
> - `TaskManager`：只管任务生命周期（创建、启动、停止）
> - `MqttClient`：只管 MQTT 通信（连接、发布、订阅）
>
> 拆分后每个类职责单一，易于测试和维护。

### Q3: 什么时候应该合并类？

**标准答案**:

> 出现以下信号时应该合并：
>
> 1. **类过小**：只有 1-2 个方法，独立存在价值不大
> 2. **紧密耦合**：`ExifParser` 和 `ImageResizer` 总是一起用
> 3. **文件爆炸**：10 个小功能产生 10 个头文件，维护困难
>
> **项目实例**：我们最初设计了这些类：
>
> - `ExifParser`：解析 EXIF
> - `ImageResizer`：缩放图片
> - `Base64Encoder`：Base64 编码
> - `JpegCompressor`：JPEG 压缩
>
> 发现问题：
>
> - 每次处理图片都要调用 4 个类
> - 代码分散在 4 个文件，修改时需要跳转
> - 重复代码：都要读取文件、错误处理
>
> 合并为 `ImageProcessor` 后：
>
> - 一个类提供所有图片处理功能
> - 代码集中，易于维护
> - 调用简洁：`ImageProcessor::getInstance().resize()`

## 📊 设计对比总结表

| 维度           | 过细粒度 ❌                | 合适粒度 ✅        | 过粗粒度 ❌         |
| -------------- | -------------------------- | ------------------ | ------------------- |
| **类数量**     | 10+ 个类（文件爆炸）       | 2-3 个大类         | 1 个上帝类          |
| **单个类大小** | < 100 行                   | 300-500 行         | > 2000 行           |
| **职责**       | 过于单一                   | 高内聚             | 职责混乱            |
| **调用链**     | `A::a() → B::b() → C::c()` | `Utils::process()` | `God::everything()` |
| **文件数量**   | 10 个头文件                | 2-3 个头文件       | 1 个巨型头文件      |
| **扩展性**     | 新增功能 = 新文件          | 新增方法           | 修改已有类          |
| **维护性**     | 分散，难以定位             | 集中，易于维护     | 耦合严重            |

## 💡 设计建议

### 1. 先粗后细

```cpp
// 步骤 1：先设计粗粒度类
class ImageProcessor {
    // 预留所有可能的功能
    parseExif();
    resize();
    crop();
    rotate();
    encodeBase64();
    compressJpeg();
    // ...
};

// 步骤 2：如果发现某个子功能过于复杂（> 500 行）
// 再考虑拆分，比如：
class ExifParser {  // ImageProcessor 的内部辅助类
    // 复杂的 EXIF 解析逻辑
};
```

### 2. 按主题聚合

```cpp
// ✅ 按主题组织
class ImageProcessor { /* 图片处理 */ };
class GeoUtils { /* 地理信息 */ };
class EventCache { /* 事件缓存 */ };

// ❌ 按功能组织
class ExifParser { /* EXIF */ };
class GpsCalculator { /* GPS */ };
class Base64Encoder { /* Base64 */ };
```

### 3. 优先组合，而非继承

```cpp
// ✅ 组合：ImageProcessor 使用 ExifParser
class ImageProcessor {
private:
    std::unique_ptr<ExifParser> exifParser_;  // 内部辅助类
};

// ❌ 继承：不推荐
class ImageProcessor : public ExifParser, public Base64Encoder { };
```

## 🚀 重构检查清单

设计新类时，问自己以下问题：

- [ ] 这个类能用一个词概括吗？（如"图片处理器"）
- [ ] 所有方法是否围绕同一个主题？
- [ ] 是否有 3 个以上的方法？（< 3 个可能过细）
- [ ] 是否超过 1000 行代码？（> 1000 可能过粗）
- [ ] 修改一个功能是否只影响这个类？（单一职责）
- [ ] 新增功能是否只需加方法，而非新建类？（开闭原则）
- [ ] 类名是否简洁？（如 `ImageProcessor` 而非 `ImageExifParserAndResizerAndEncoder`）
