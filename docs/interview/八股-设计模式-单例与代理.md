# 八股知识点：设计模式与 SDK 集成

## 1. 单例模式 (Singleton Pattern)

### 知识点

单例模式确保一个类只有一个实例，并提供一个全局访问点。

### 核心场景

- **硬件资源管理**: 如相机、传感器、GPU 上下文，通常物理上只有一个，软件上也应只有一个控制器。
- **昂贵对象**: 创建/销毁成本极高的对象（如数据库连接池、大型 AI 模型）。
- **不稳定对象**: 某些第三方 SDK 对象在反复创建/销毁时容易崩溃或死锁（如本项目的 DJI Liveview）。

### 实现方式 (C++11 线程安全)

**Meyers' Singleton (推荐):**
利用 C++11 静态局部变量初始化的线程安全性。

```cpp
class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance; // 线程安全，首次调用时初始化
        return instance;
    }

    void doSomething() {}

private:
    Singleton() = default;
    ~Singleton() = default;
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
};
```

**本项目中的变体 (Lazy Init with Shared Ptr):**
因为我们需要控制初始化时机（依赖配置），且对象由第三方工厂创建，所以使用了 `static std::shared_ptr` + `mutex`。

```cpp
namespace {
    std::shared_ptr<Liveview> g_instance = nullptr;
    std::mutex g_mutex;
}

void init() {
    std::lock_guard<std::mutex> lock(g_mutex);
    if (!g_instance) {
        g_instance = createLiveview();
    }
}
```

## 2. 静态代理回调 (Static Proxy Callback)

### 知识点

C 语言风格的 API（如大多数 SDK）通常要求传入函数指针作为回调。C++ 的非静态成员函数包含隐藏的 `this` 指针，无法直接转换为普通的函数指针。

### 解决方案

使用 **静态成员函数** 或 **全局函数** 作为中间代理，通过 `void* user_data` 或 **全局变量** 找回对象实例。

### 代码示例

**场景**: SDK 只接受 `void (*cb)(int)`，不接受 `std::function` 或 `void* context`。

**错误写法**:

```cpp
class Handler {
    void onData(int d) {}

    void register() {
        sdk_register_callback(onData); // ❌ 编译错误：类型不匹配
    }
};
```

**正确写法 (使用全局路由):**

```cpp
class Handler {
public:
    void onData(int d) { /* 处理数据 */ }
};

// 全局路由
std::atomic<Handler*> g_activeHandler{nullptr};

// 静态代理
void ProxyCallback(int d) {
    Handler* h = g_activeHandler.load();
    if (h) h->onData(d); // ✅ 转发
}

// 注册
void register(Handler* h) {
    g_activeHandler.store(h);
    sdk_register_callback(ProxyCallback);
}
```

## 3. 死锁与资源泄漏 (Deadlock & Leak)

### 面试题：如何处理第三方库的死锁 Bug？

**Q: 如果调用第三方库的某个函数（如析构函数）会必然导致死锁，且无法修改源码，你怎么处理？**

**A (标准答案):**

1.  **避免调用**: 如果可能，改变使用方式，不再调用该函数。例如本项目中，改为**单例模式**，程序运行期间不再析构对象。
2.  **隔离 (Isolation)**: 将该库的操作封装在独立的进程中（而非线程）。如果卡死，直接杀掉子进程。进程间通过 IPC（共享内存、Socket）通信。
3.  **流放 (Fire-and-Forget)**: (下策) 将阻塞调用扔到 detached 线程中，主线程继续运行。缺点是会导致资源泄漏，仅适用于程序即将退出的场景。

### 本项目案例

- **问题**: `Liveview::DeInit()` 在 Sophon 平台上 100% 死锁。
- **尝试**: 流放线程方案 -> 导致内存泄漏，不适合 7x24 小时运行。
- **最终**: 单例模式 -> 既然析构会死锁，那就永远别析构它。初始化一次，复用到底。

## 4. 访问权限 (Access Control)

### 知识点

- `public`: 所有人可见。
- `protected`: 子类和自己可见。
- `private`: 只有自己和 `friend` 可见。

### 常见陷阱

当使用 C 风格回调或静态代理函数时，代理函数通常位于类外部。如果回调逻辑（如 `onH264Data`）是 `private` 的，代理函数将无法调用它。

### 解决

1.  将回调逻辑改为 `public`。
2.  将代理函数声明为类的 `friend`。
