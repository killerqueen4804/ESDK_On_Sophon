## 📌 单例模式 (Singleton Pattern)

### 知识点

**单例模式**确保一个类只有一个实例，并提供全局访问点。

**使用场景**:

- 资源管理器（日志、配置、连接池）
- 硬件接口（打印机、TPU 设备）
- 全局状态管理（任务管理器、设备管理器）

---

### 项目中的例子

**TaskManager 单例**（任务管理器）:

```cpp
// include/esdk_sophon/task/TaskManager.h
class TaskManager {
public:
    // 获取唯一实例
    static TaskManager& getInstance();

    // 禁止拷贝和赋值
    TaskManager(const TaskManager&) = delete;
    TaskManager& operator=(const TaskManager&) = delete;

private:
    // 私有构造函数
    TaskManager();
    ~TaskManager();
};

// src/task/TaskManager.cpp
TaskManager& TaskManager::getInstance() {
    static TaskManager instance;  // Meyers' Singleton
    return instance;
}
```

**为什么 TaskManager 要用单例？**

1. 全局只需要一个任务管理器
2. MQTT、Vision、Device 模块都需要访问同一个任务列表
3. 避免多个实例导致任务状态不一致

**使用方式**:

```cpp
// 在任何地方都可以访问
auto& manager = TaskManager::getInstance();
manager.startTask(config);
```

---

### 详细讲解

#### 四种实现方式对比

**1. 饿汉式（Eager Initialization）**

```cpp
class Singleton {
private:
    static Singleton instance;  // 程序启动时就创建
    Singleton() {}

public:
    static Singleton& getInstance() {
        return instance;
    }
};

// cpp文件
Singleton Singleton::instance;  // 静态成员需要定义
```

✅ **优点**: 线程安全（静态变量在程序启动时初始化）  
❌ **缺点**: 即使不使用也会创建，浪费内存

---

**2. 懒汉式（Lazy Initialization - 不安全）**

```cpp
class Singleton {
private:
    static Singleton* instance;
    Singleton() {}

public:
    static Singleton& getInstance() {
        if (instance == nullptr) {          // ❌ 线程不安全！
            instance = new Singleton();
        }
        return *instance;
    }
};
```

❌ **问题**: 多线程环境下可能创建多个实例

```cpp
// 线程1执行到这里          // 线程2也执行到这里
if (instance == nullptr) {   if (instance == nullptr) {
    instance = new ...;          instance = new ...;  // 创建了两个实例！
}                            }
```

---

**3. 双检锁（Double-Checked Locking）**

```cpp
class Singleton {
private:
    static Singleton* instance;
    static std::mutex mtx;
    Singleton() {}

public:
    static Singleton& getInstance() {
        if (instance == nullptr) {          // 第一次检查（无锁）
            std::lock_guard<std::mutex> lock(mtx);
            if (instance == nullptr) {      // 第二次检查（有锁）
                instance = new Singleton();
            }
        }
        return *instance;
    }
};
```

✅ **优点**: 减少加锁开销  
⚠️ **问题**: C++11 前有内存重排序问题，现在已解决（使用 `std::atomic`）

---

**4. Meyers' Singleton（推荐）✅**

```cpp
class Singleton {
private:
    Singleton() {}

public:
    static Singleton& getInstance() {
        static Singleton instance;  // C++11 保证线程安全
        return instance;
    }

    // 禁止拷贝
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
};
```

**为什么是最佳实践？**

1. **线程安全**: C++11 标准保证局部静态变量的初始化是线程安全的
2. **懒加载**: 第一次调用 `getInstance()` 时才创建
3. **自动析构**: 程序结束时自动调用析构函数，无需手动 delete
4. **代码简洁**: 无需手动加锁，编译器自动处理

**编译器生成的伪代码**:

```cpp
static Singleton& getInstance() {
    // 编译器自动添加的线程安全保护
    static bool initialized = false;
    static std::mutex init_mutex;
    static alignas(Singleton) char buffer[sizeof(Singleton)];

    if (!initialized) {
        std::lock_guard<std::mutex> lock(init_mutex);
        if (!initialized) {
            new (buffer) Singleton();  // placement new
            initialized = true;
        }
    }

    return *reinterpret_cast<Singleton*>(buffer);
}
```

### 面试要点

#### Q1: 单例模式有哪些实现方式？各有什么优缺点？

**A**:

| 实现方式 | 线程安全 | 懒加载 | 优点       | 缺点       |
| -------- | -------- | ------ | ---------- | ---------- |
| 饿汉式   | ✅       | ❌     | 简单、安全 | 浪费内存   |
| 懒汉式   | ❌       | ✅     | 节省内存   | 不安全     |
| 双检锁   | ✅       | ✅     | 性能好     | 实现复杂   |
| Meyers'  | ✅       | ✅     | 简洁、安全 | 需要 C++11 |

**推荐**: Meyers' Singleton（现代 C++项目的标准做法）

---

#### Q2: 为什么 Meyers' Singleton 是线程安全的？

**A**:

C++11 标准规定（§6.7 [stmt.dcl] p4）：

> "如果控制流同时进入多个线程的声明，则并发执行应等待初始化完成。"

**简单来说**:

1. 编译器会在第一次进入时加锁
2. 后续线程会等待初始化完成
3. 初始化完成后，所有线程直接返回同一个实例

**证明**（编译器生成的汇编代码）:

```assembly
call __cxa_guard_acquire  ; 加锁检查
test eax, eax
jz   .already_init        ; 如果已初始化，跳过
call Singleton::Singleton ; 初始化
call __cxa_guard_release  ; 释放锁
.already_init:
```

#### Q3: 单例模式的析构顺序问题

**问题**: 如果两个单例互相依赖，可能出现析构顺序错误

```cpp
class Logger {
public:
    static Logger& getInstance() {
        static Logger instance;
        return instance;
    }

    ~Logger() {
        // 可能在 TaskManager 析构后才调用
    }
};

class TaskManager {
public:
    ~TaskManager() {
        Logger::getInstance().log("TaskManager 析构");
        // ❌ 如果 Logger 已经析构，崩溃！
    }
};
```

**解决方案**:

1. **避免在析构函数中使用其他单例**
2. **使用智能指针控制析构顺序**
3. **检查单例是否还有效**

```cpp
~TaskManager() {
    // 简单打印到 stderr，不依赖 Logger
    std::cerr << "TaskManager 析构" << std::endl;
}
```

#### Q4: 项目中为什么 TaskManager 要禁止拷贝？

**A**:

```cpp
class TaskManager {
public:
    TaskManager(const TaskManager&) = delete;            // 禁止拷贝构造
    TaskManager& operator=(const TaskManager&) = delete; // 禁止拷贝赋值
};
```

**原因**:

1. **语义上不合理**: 任务管理器只能有一个，拷贝没有意义
2. **资源管理**: TaskManager 持有 mutex、任务列表等资源，拷贝会导致共享问题
3. **防止误用**: 避免程序员意外拷贝

**如果不禁止会怎样？**

```cpp
TaskManager manager1 = TaskManager::getInstance();  // 拷贝
TaskManager manager2 = TaskManager::getInstance();  // 又拷贝

// manager1 和 manager2 的 mutex_ 是两个不同的锁！
// runningTasks_ 也是两份数据！
// 完全失去了单例的意义
```

```cpp
// 错误
```

## 📌 工厂模式 (Factory Pattern)

### 知识点

**工厂模式**定义创建对象的接口，让子类决定实例化哪个类。

**使用场景**:

- 对象创建逻辑复杂
- 需要根据配置动态创建不同类型的对象
- 隐藏对象创建细节

---

### 项目中的例子

**TaskConfig 的静态工厂方法**:

```cpp
// include/esdk_sophon/types/TaskConfig.h
class TaskConfig {
public:
    /**
     * @brief 从 JSON 创建 TaskConfig（工厂方法）
     */
    static TaskConfig fromJson(const std::string& jsonStr) {
        TaskConfig config;

        try {
            auto j = nlohmann::json::parse(jsonStr);

            // 解析基本字段
            config.taskId = j.value("task_id", "");
            config.eventType = j.value("event_type", "");

            // 解析复杂字段：算法类型数组
            if (j.contains("algorithm_types")) {
                for (const auto& algo : j["algorithm_types"]) {
                    AlgorithmType algType;
                    algType.name = algo.value("name", "");

                    if (algo.contains("classes")) {
                        for (const auto& cls : algo["classes"]) {
                            algType.classes.push_back(cls.get<std::string>());
                        }
                    }

                    config.algorithmTypes.push_back(algType);
                }
            }

            // 验证配置
            if (!config.isValid()) {
                throw std::runtime_error("Invalid task config");
            }

        } catch (const std::exception& e) {
            // 记录错误日志
            core::Logger::getInstance().error("解析 TaskConfig 失败: {}", e.what());
            throw;
        }

        return config;
    }

private:
    // 构造函数可以是私有的（强制使用工厂方法）
    TaskConfig() = default;
};
```

**使用方式**:

```cpp
// MQTT 收到任务消息
void onMqttMessage(const std::string& jsonMsg) {
    try {
        // 使用工厂方法创建配置
        TaskConfig config = TaskConfig::fromJson(jsonMsg);

        // 启动任务
        TaskManager::getInstance().startTask(config);

    } catch (const std::exception& e) {
        // 处理错误
        Logger::getInstance().error("任务配置错误: {}", e.what());
    }
}
```

**为什么用工厂方法？**

1. **封装复杂性**: JSON 解析、验证逻辑封装在一个地方
2. **错误处理**: 统一的异常处理
3. **扩展性**: 未来可以添加 `fromXml()`, `fromProtobuf()` 等
4. **类型安全**: 返回完整构造好的对象，不会有半成品

---

### 详细讲解

#### 三种工厂模式对比

**1. 简单工厂（Static Factory Method）**

```cpp
class TaskConfig {
public:
    static TaskConfig fromJson(const std::string& json) {
        // 本项目使用的方式
    }

    static TaskConfig fromFile(const std::string& filename) {
        std::ifstream file(filename);
        std::string json((std::istreambuf_iterator<char>(file)),
                         std::istreambuf_iterator<char>());
        return fromJson(json);
    }
};
```

**2. 工厂方法（Factory Method）**

```cpp
// 抽象产品
class Algorithm {
public:
    virtual ~Algorithm() = default;
    virtual void process() = 0;
};

// 具体产品
class YoloDetector : public Algorithm {
    void process() override { /* YOLO 推理 */ }
};

class SegmentationModel : public Algorithm {
    void process() override { /* 分割推理 */ }
};

// 抽象工厂
class AlgorithmFactory {
public:
    virtual std::unique_ptr<Algorithm> createAlgorithm() = 0;
};

// 具体工厂
class YoloFactory : public AlgorithmFactory {
    std::unique_ptr<Algorithm> createAlgorithm() override {
        return std::make_unique<YoloDetector>();
    }
};
```

**3. 抽象工厂（Abstract Factory）**

```cpp
// 可以创建一系列相关对象
class AlgorithmSuite {
public:
    virtual std::unique_ptr<Detector> createDetector() = 0;
    virtual std::unique_ptr<Segmentor> createSegmentor() = 0;
    virtual std::unique_ptr<Tracker> createTracker() = 0;
};
```

## 📌 RAII 原则

### 知识点

**RAII (Resource Acquisition Is Initialization)** - 资源获取即初始化

**核心思想**:

- 在对象构造时获取资源
- 在对象析构时释放资源
- 利用 C++ 的栈对象自动析构机制

**管理的资源**:

- 内存（new/delete）
- 文件句柄（fopen/fclose）
- 锁（lock/unlock）
- 网络连接（connect/disconnect）
- TPU 资源（分配/释放）

---

### 项目中的例子

**1. 智能指针管理任务辅助对象**

```cpp
// include/esdk_sophon/task/TaskManager.h
struct TaskState {
    std::string taskId;
    TaskStatus status;

    // RAII: 使用 unique_ptr 自动管理生命周期
    std::unique_ptr<CompletionDetector> detector;
    std::unique_ptr<MediaFileFilter> fileFilter;
    std::unique_ptr<PerformanceMonitor> perfMonitor;

    ~TaskState() {
        // 无需手动 delete，unique_ptr 自动析构！
        // detector->~CompletionDetector();
        // fileFilter->~MediaFileFilter();
        // perfMonitor->~PerformanceMonitor();
    }
};

// src/task/TaskManager.cpp
void TaskManager::createTaskHelpers(TaskState& state) {
    // 创建资源
    state.detector = std::make_unique<CompletionDetector>(state.config);
    state.fileFilter = std::make_unique<MediaFileFilter>(state.config);
    state.perfMonitor = std::make_unique<PerformanceMonitor>(state.config);

    // ✅ 无需担心内存泄漏，即使后面抛出异常也会自动释放
}

bool TaskManager::stopTask(const std::string& taskId) {
    auto it = runningTasks_.find(taskId);

    // 删除任务
    runningTasks_.erase(it);
    // ✅ TaskState 析构 -> unique_ptr 析构 -> 辅助对象自动释放

    return true;
}
```

**对比手动管理**（不使用 RAII）:

```cpp
// ❌ 传统C风格 - 容易泄漏
struct TaskState {

    state.fileFilter = new MediaFileFilter();

    // ❌ 如果这里抛出异常，前面已分配的内存泄漏！
```

**2. std::lock_guard 管理互斥锁**

```cpp
// src/task/TaskManager.cpp
bool TaskManager::startTask(const TaskConfig& config) {
    {
        std::lock_guard<std::mutex> lock(mutex_);  // RAII: 构造时加锁

        // 临界区代码
        if (runningTasks_.find(config.taskId) != runningTasks_.end()) {
            return false;  // ✅ 提前返回，lock 自动解锁
        }

        runningTasks_.emplace(config.taskId, TaskState(...));

        // ✅ 即使这里抛出异常，lock 也会自动解锁

    }  // ✅ 离开作用域，lock 自动解锁

    return true;
}
```

**对比手动管理**:

```cpp
// ❌ 手动加锁 - 容易忘记解锁
bool startTask(const TaskConfig& config) {
    mutex_.lock();

    if (runningTasks_.find(config.taskId) != runningTasks_.end()) {
        // ❌ 忘记解锁就返回了！死锁！
        return false;
    }

    runningTasks_.emplace(...);

    // ❌ 如果这里抛出异常，锁永远不会释放！死锁！

    mutex_.unlock();
    return true;
}

// ✅ 使用 RAII
bool startTask(const TaskConfig& config) {
    std::lock_guard<std::mutex> lock(mutex_);

    if (...) return false;  // ✅ 自动解锁

    runningTasks_.emplace(...);  // ✅ 异常也会自动解锁

    return true;
}
```

### 详细讲解

#### RAII 的三个要素

1. **资源在构造时获取**
2. **资源在析构时释放**
3. **利用栈对象的自动析构**

#### 智能指针详解

**std::unique_ptr** - 独占所有权

```cpp
{
    std::unique_ptr<int> ptr = std::make_unique<int>(42);

    // ❌ 不能拷贝
    // std::unique_ptr<int> ptr2 = ptr;  // 编译错误

    // ✅ 可以移动（转移所有权）
    std::unique_ptr<int> ptr2 = std::move(ptr);
    // 现在 ptr 是 nullptr，ptr2 拥有资源

}  // ptr2 析构，自动 delete
```

**std::shared_ptr** - 共享所有权

```cpp
{
    std::shared_ptr<int> ptr1 = std::make_shared<int>(42);
    std::shared_ptr<int> ptr2 = ptr1;  // ✅ 可以拷贝，引用计数 = 2

    // 两个指针共享同一块内存
}  // ptr1 和 ptr2 都析构，引用计数归零，自动 delete
```

**std::weak_ptr** - 弱引用（不增加引用计数）

```cpp
std::shared_ptr<int> shared = std::make_shared<int>(42);
std::weak_ptr<int> weak = shared;  // 弱引用，不影响引用计数

// 使用前需要检查是否还有效
if (auto locked = weak.lock()) {  // 尝试获取 shared_ptr
    std::cout << *locked << std::endl;
} else {
    std::cout << "资源已释放" << std::endl;
}
```

### 面试要点

#### Q1: 什么是 RAII？有什么好处？

**A**:

RAII (Resource Acquisition Is Initialization) - 资源获取即初始化

**核心思想**: 将资源的生命周期绑定到对象的生命周期

**好处**:

1. **自动管理**: 无需手动释放，不会忘记
2. **异常安全**: 即使抛出异常也会自动释放
3. **代码简洁**: 无需 try-catch-finally
4. **防止泄漏**: 编译器保证析构函数一定调用

---

#### Q2: RAII 与 GC (垃圾回收) 的区别？

**A**:

| 特性     | RAII (C++)       | GC (Java/Python)    |
| -------- | ---------------- | ------------------- |
| 释放时机 | 确定（析构时）   | 不确定（GC 运行时） |
| 性能开销 | 低（无 GC 线程） | 高（需要 GC 线程）  |
| 适用资源 | 所有资源         | 主要是内存          |
| 异常安全 | 保证             | 不保证              |

**C++ 的优势**:

- 可以管理内存以外的资源（文件、锁、TPU）
- 释放时机确定，适合实时系统

---

#### Q3: 项目中为什么用 unique_ptr 而不是 shared_ptr？

**A**:

```cpp
struct TaskState {
    // ✅ 使用 unique_ptr
    std::unique_ptr<CompletionDetector> detector;

    // 如果用 shared_ptr 会怎样？
    // std::shared_ptr<CompletionDetector> detector;
};
```

**选择 unique_ptr 的原因**:

1. **所有权清晰**: TaskState 独占 detector，不会共享
2. **性能更好**: unique_ptr 无引用计数，开销更小
3. **语义正确**: detector 的生命周期就是跟随 TaskState

**什么时候用 shared_ptr？**

- 多个对象需要共享同一个资源
- 所有权不明确
- 循环引用需要用 weak_ptr 打破

**本项目中的例子**:

- `TaskState::detector` - unique_ptr（TaskState 独占）
- 未来如果多个任务共享同一个模型 - 可以用 shared_ptr

#### Q4: RAII 如何保证异常安全？

**A**:

```cpp
void processTask() {
    std::lock_guard<std::mutex> lock(mutex_);  // RAII 锁

    auto task = std::make_unique<Task>();      // RAII 内存

    task->run();  // ❌ 假设这里抛出异常

    // 即使异常发生：
    // 1. task 自动析构 -> delete
    // 2. lock 自动析构 -> 解锁
    // ✅ 不会泄漏内存，不会死锁
}
```

**C++ 保证**: 栈展开（Stack Unwinding）时，所有已构造的对象都会析构

### 易错点

#### ❌ 错误 1: 忘记使用 std::move

```cpp
std::unique_ptr<int> ptr1 = std::make_unique<int>(42);

// ❌ 错误：unique_ptr 不能拷贝
// std::unique_ptr<int> ptr2 = ptr1;  // 编译错误

// ✅ 正确：使用 std::move 转移所有权
std::unique_ptr<int> ptr2 = std::move(ptr1);
// 现在 ptr1 是 nullptr
```

---

#### ❌ 错误 2: 手动 delete unique_ptr 管理的对象

```cpp
std::unique_ptr<int> ptr = std::make_unique<int>(42);

// ❌ 千万不要这样做！
delete ptr.get();  // 手动 delete

// 离开作用域时，ptr 会再次 delete -> 双重释放！崩溃！
```

---

#### ❌ 错误 3: 循环引用导致内存泄漏

```cpp
struct Node {
    std::shared_ptr<Node> next;  // ❌ 如果形成环，永远不会释放
};

std::shared_ptr<Node> a = std::make_shared<Node>();
std::shared_ptr<Node> b = std::make_shared<Node>();

a->next = b;  // a 引用 b，引用计数 = 2
b->next = a;  // b 引用 a，引用计数 = 2

// a 和 b 离开作用域：
// - a 的引用计数变为 1（b->next 还在引用）
// - b 的引用计数变为 1（a->next 还在引用）
// ❌ 两者都不会释放，内存泄漏！
```

**解决方案**: 使用 weak_ptr 打破循环

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;  // ✅ 使用 weak_ptr
};
```

```cpp
class ResourceGuard {
public:
    ResourceGuard() {
        // 获取资源
        resource_ = acquire();
    }

    ~ResourceGuard() {
        // 释放资源
        if (resource_) {
            release(resource_);
        }
    }

    // 禁止拷贝
    ResourceGuard(const ResourceGuard&) = delete;
    ResourceGuard& operator=(const ResourceGuard&) = delete;

    // 允许移动
    ResourceGuard(ResourceGuard&& other) noexcept
        : resource_(other.resource_)
    {
        other.resource_ = nullptr;
    }

private:
    Resource* resource_;
};
```
