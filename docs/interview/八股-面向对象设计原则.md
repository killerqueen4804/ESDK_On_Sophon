## SOLID 原则总览

SOLID 是面向对象设计的五大原则，由 Robert C. Martin（Uncle Bob）提出：

| 原则    | 英文                            | 核心思想                 | 作用           |
| ------- | ------------------------------- | ------------------------ | -------------- |
| **S**RP | Single Responsibility Principle | 一个类只有一个改变的理由 | 降低耦合       |
| **O**CP | Open-Closed Principle           | 对扩展开放，对修改关闭   | 提高可扩展性   |
| **L**SP | Liskov Substitution Principle   | 子类可以替换父类         | 保证多态正确性 |
| **I**SP | Interface Segregation Principle | 接口应该小而专           | 避免接口污染   |
| **D**IP | Dependency Inversion Principle  | 依赖抽象而非具体         | 降低耦合       |

## 接口隔离原则（ISP）

### 📌 定义

**Interface Segregation Principle**: 客户端不应该依赖它不需要的接口。

> "Make fine grained interfaces that are client specific." - Robert C. Martin

### 📖 通俗解释

- **错误做法**: 创建一个"胖接口"，包含所有可能的方法
- **正确做法**: 将大接口拆分为多个小接口，客户端只依赖需要的部分

**比喻**: 瑞士军刀 vs 专用工具

- ❌ 瑞士军刀：功能多，但很多用不上
- ✅ 专用工具：每个工具只做一件事，用什么拿什么

### 📝 经典错误示例

```cpp
// ❌ 违反 ISP：胖接口
class IWorker {
public:
    virtual void work() = 0;
    virtual void eat() = 0;      // 所有工人都要吃饭？
    virtual void sleep() = 0;    // 所有工人都要睡觉？
    virtual void code() = 0;     // 所有工人都要写代码？
};

class Programmer : public IWorker {
    void work() override { /* 写代码 */ }
    void eat() override { /* 吃饭 */ }
    void sleep() override { /* 睡觉 */ }
    void code() override { /* 写代码 */ }
};

class Robot : public IWorker {
    void work() override { /* 工作 */ }
    void eat() override { /* ❌ 机器人不吃饭！*/ }  // 被迫实现无用方法
    void sleep() override { /* ❌ 机器人不睡觉！*/ }
    void code() override { /* ❌ 机器人不会写代码！*/ }
};
```

### ✅ 正确示例（拆分接口）

```cpp
// ✅ 符合 ISP：小而专的接口
class IWorkable {
public:
    virtual void work() = 0;
};

class IFeedable {
public:
    virtual void eat() = 0;
};

class ISleepable {
public:
    virtual void sleep() = 0;
};

// 程序员：需要工作、吃饭、睡觉
class Programmer : public IWorkable, public IFeedable, public ISleepable {
    void work() override { /* 写代码 */ }
    void eat() override { /* 吃饭 */ }
    void sleep() override { /* 睡觉 */ }
};

// 机器人：只需要工作
class Robot : public IWorkable {
    void work() override { /* 工作 */ }
    // ✅ 不需要 eat/sleep，不继承相应接口
};
```

### 🔥 项目中的实例：ITask::onTaskEnd()

**背景**: 不是所有任务都需要处理 `device_task_end` 消息

```cpp
// ✅ 符合 ISP：虚函数 + 默认空实现
class ITask {
public:
    // 所有任务都需要的核心接口
    virtual bool start() = 0;
    virtual void stop() = 0;
    virtual bool isRunning() const = 0;

    // 可选接口：提供默认实现
    virtual void onTaskEnd() {
        // 默认空实现：不支持此功能的任务类型忽略此消息
    }
};

// LiveStreamTask：需要 onTaskEnd
class LiveStreamTask : public ITask {
    void onTaskEnd() override {
        logger_.info("收到 task_end，立即停止");
        stop();
    }
};

// SimpleTask：不需要 onTaskEnd
class SimpleTask : public ITask {
    // ✅ 不覆盖 onTaskEnd()，使用默认空实现
};
```

**设计决策**:

- **为什么不用纯虚函数** (`= 0`)？
  - 纯虚函数会强制所有子类实现，违反 ISP
  - 许多简单任务不需要 `onTaskEnd` 逻辑
- **为什么不拆分接口**（如 `ITaskEndable`）？
  - 接口太细碎，增加复杂度
  - `onTaskEnd` 与任务生命周期紧密相关，适合放在 ITask

### 🎯 面试标准答案

**Q**: 什么是接口隔离原则？

**A**:

> "接口隔离原则是指客户端不应该依赖它不需要的接口。在设计接口时，应该保持接口小而专，避免创建臃肿的'胖接口'。
>
> 在我的项目中，`ITask` 接口定义了任务的核心方法（start/stop），而 `onTaskEnd()` 作为可选方法提供默认空实现，这样不需要此功能的任务类（如 SimpleTask）可以不覆盖，符合接口隔离原则。"

## 开闭原则（OCP）

### 📌 定义

**Open-Closed Principle**: 软件实体应该对扩展开放，对修改关闭。

> "Software entities should be open for extension, but closed for modification."

### 📖 通俗解释

- **对扩展开放**: 可以添加新功能
- **对修改关闭**: 不修改现有代码

**关键手段**: 抽象 + 多态

### ❌ 违反 OCP 的代码

```cpp
// ❌ 每次新增任务类型都要修改这里
void MqttHandler::handleTaskEnd(const nlohmann::json& data) {
    auto task = getTask(taskId);

    if (auto liveTask = dynamic_cast<LiveStreamTask*>(task.get())) {
        liveTask->stopImmediately();
    } else if (auto mediaTask = dynamic_cast<MediaFileTask*>(task.get())) {
        mediaTask->markEnded();
    } else if (auto simpleTask = dynamic_cast<SimpleTask*>(task.get())) {
        // ⚠️ 新增类型，必须修改此处！
        simpleTask->justStop();
    }
    // 更多 if-else...
}
```

**问题**:

- 每次新增任务类型，必须修改 `MqttHandler`
- 违反"对修改关闭"原则
- 容易遗漏，导致 Bug

### ✅ 符合 OCP 的代码

```cpp
// ✅ 新增任务类型无需修改此处
void MqttHandler::handleTaskEnd(const nlohmann::json& data) {
    auto task = getTask(taskId);

    // 多态调用，自动路由到正确的实现
    task->onTaskEnd();
}
```

**优势**:

- ✅ 新增 `NewTask` 类型，只需实现 `onTaskEnd()`
- ✅ 无需修改 `MqttHandler` 代码
- ✅ 完全符合开闭原则

### 🔥 项目中的实例：TaskManager 工厂模式

```cpp
// ✅ 扩展：添加新任务类型
class TaskManager {
    TaskPtr createTask(const TaskConfig& config) {
        if (config.type == TaskType::LIVESTREAM) {
            return std::make_shared<LiveStreamTask>(config, service_);
        } else if (config.type == TaskType::MEDIAFILE) {
            // 新增类型：只修改这里，不改其他代码
            return std::make_shared<MediaFileTask>(config, service_);
        }
        return nullptr;
    }
};
```

### 🎯 面试标准答案

**Q**: 如何实现开闭原则？

**A**:

> "通过抽象和多态实现开闭原则。在基类中定义虚函数接口，派生类实现具体逻辑。这样，调用方依赖抽象接口，新增子类时无需修改调用代码。
>
> 例如在我的项目中，`MqttHandler::handleTaskEnd()` 调用 `task->onTaskEnd()`，利用多态自动路由。当新增 `MediaFileTask` 时，只需实现其 `onTaskEnd()` 方法，无需修改 `MqttHandler`，符合对扩展开放、对修改关闭的原则。"

## 里氏替换原则（LSP）

### 📌 定义

**Liskov Substitution Principle**: 子类对象能够替换父类对象，且程序行为不变。

> "Objects of a superclass should be replaceable with objects of a subclass without breaking the application."

### 📖 通俗解释

- 子类**是一个**父类（is-a 关系）
- 子类可以增强父类功能，但不能削弱
- 使用父类指针/引用的地方，替换为子类应该仍然正确

**比喻**: 鸟类和企鹅

- ❌ `class Penguin : public Bird` → `fly()` 方法企鹅无法实现
- ✅ `class Penguin : public Flightless Bird` → 符合 LSP

### ❌ 违反 LSP 的例子

```cpp
class Rectangle {
public:
    virtual void setWidth(int w) { width_ = w; }
    virtual void setHeight(int h) { height_ = h; }
    int area() { return width_ * height_; }

private:
    int width_;
    int height_;
};

// ❌ 违反 LSP：正方形不能随意改宽度
class Square : public Rectangle {
public:
    void setWidth(int w) override {
        width_ = w;
        height_ = w;  // 破坏了 Rectangle 的行为！
    }

    void setHeight(int h) override {
        width_ = h;
        height_ = h;
    }
};

// 测试代码
void testRectangle(Rectangle& rect) {
    rect.setWidth(5);
    rect.setHeight(4);
    assert(rect.area() == 20);  // ❌ Square 传入会失败！
}
```

### ✅ 符合 LSP 的设计

```cpp
class Shape {
public:
    virtual int area() = 0;
};

class Rectangle : public Shape {
    int area() override { return width_ * height_; }
};

class Square : public Shape {
    int area() override { return side_ * side_; }
};

// ✅ 所有 Shape 子类都可以替换使用
void printArea(Shape& shape) {
    std::cout << shape.area() << std::endl;
}
```

### 🔥 项目中的实例：ITask 多态

```cpp
// ✅ 所有 ITask 子类都可以替换使用
void TaskManager::processTask(const std::string& taskId) {
    TaskPtr task = getTask(taskId);  // 返回 std::shared_ptr<ITask>

    // 无需知道具体类型
    task->start();       // 多态调用
    task->onTaskEnd();   // 多态调用
    task->stop();        // 多态调用
}

// LiveStreamTask 替换 ITask ✅
// MediaFileTask 替换 ITask ✅
// 程序行为正确
```

### 🎯 面试标准答案

**Q**: 什么是里氏替换原则？举个项目例子。

**A**:

> "里氏替换原则是指子类对象能够替换父类对象使用，且程序行为不变。子类可以扩展父类功能，但不能改变父类原有的行为。
>
> 在我的项目中，`TaskManager` 返回 `std::shared_ptr<ITask>`，无论实际类型是 `LiveStreamTask` 还是 `MediaFileTask`，都可以通过基类指针调用 `start()`, `stop()`, `onTaskEnd()` 等方法，行为完全符合预期。这就是里氏替换原则的体现。"

## 单一职责原则（SRP）

### 📌 定义

**Single Responsibility Principle**: 一个类应该只有一个改变的理由。

> "A class should have only one reason to change."

### 📖 通俗解释

- 一个类只负责一件事
- 避免"上帝类"（God Class）

**判断标准**: 描述类的功能时，如果需要用"和"连接，可能违反 SRP

- ❌ "这个类负责**用户管理和订单处理和日志记录**"
- ✅ "这个类负责用户管理"

### ❌ 违反 SRP 的例子

```cpp
// ❌ 一个类做太多事
class Employee {
public:
    void calculatePay();      // 计算工资
    void saveToDatabase();    // 保存到数据库
    void generateReport();    // 生成报表
    void sendEmail();         // 发送邮件

private:
    std::string name_;
    double salary_;
    std::string email_;
};

// 问题：
// - 工资算法改变 → 修改此类
// - 数据库改变 → 修改此类
// - 报表格式改变 → 修改此类
// - 邮件系统改变 → 修改此类
// 太多改变的理由！
```

### ✅ 符合 SRP 的设计

```cpp
// ✅ 每个类只负责一件事
class Employee {
public:
    std::string getName() const { return name_; }
    double getSalary() const { return salary_; }

private:
    std::string name_;
    double salary_;
};

class PayrollCalculator {
public:
    double calculate(const Employee& emp);
};

class EmployeeRepository {
public:
    void save(const Employee& emp);
};

class ReportGenerator {
public:
    void generate(const Employee& emp);
};

class EmailService {
public:
    void send(const Employee& emp, const std::string& message);
};
```

### 🔥 项目中的实例：ITask vs TaskService

```cpp
// ✅ ITask：只负责任务生命周期
class ITask {
    virtual bool start() = 0;
    virtual void stop() = 0;
    virtual TaskState getState() const = 0;
    // 改变理由：任务管理逻辑变化
};

// ✅ TaskService：只负责业务逻辑编排
class TaskService {
    bool processFrame(const cv::Mat& frame, const TaskConfig& config);
    void detectObjects(...);
    void publishEvent(...);
    // 改变理由：业务流程变化
};

// ✅ MqttClient：只负责 MQTT 通信
class MqttClient {
    bool publish(const std::string& topic, const std::string& msg);
    bool subscribe(const std::string& topic);
    // 改变理由：MQTT 协议变化
};
```

### 🎯 面试标准答案

**Q**: 如何判断一个类是否违反单一职责原则？

**A**:

> "判断方法是问自己：这个类有多少个改变的理由？如果有多个不同的原因导致类修改，就违反了单一职责原则。
>
> 例如在我的项目中，`ITask` 只负责任务生命周期管理，`TaskService` 只负责检测业务逻辑，`MqttClient` 只负责 MQTT 通信。它们各自只有一个改变的理由，符合单一职责原则。如果将这些功能都塞进一个类，任何一个需求变更都会修改这个类，导致类过于臃肿。"

## 依赖倒置原则（DIP）

### 📌 定义

**Dependency Inversion Principle**:

1. 高层模块不应该依赖低层模块，两者都应该依赖抽象
2. 抽象不应该依赖细节，细节应该依赖抽象

> "Depend upon abstractions, not concretions."

### 📖 通俗解释

- 不要直接 `new` 具体类，而是依赖接口/抽象类
- 使用**依赖注入**（Dependency Injection）

**比喻**: 插座和电器

- ❌ 电器直接焊死在墙上（硬编码依赖）
- ✅ 电器通过插座连接（依赖抽象接口）

### ❌ 违反 DIP 的例子

```cpp
// ❌ 高层直接依赖低层具体类
class TaskManager {
public:
    void startTask(const TaskConfig& config) {
        // ❌ 直接 new 具体类
        auto task = std::make_shared<LiveStreamTask>(config);
        task->start();
    }
};
```

**问题**:

- `TaskManager` 与 `LiveStreamTask` 紧耦合
- 无法替换为其他任务类型
- 难以单元测试（无法 mock）

### ✅ 符合 DIP 的设计

```cpp
// ✅ 依赖抽象接口
class TaskManager {
public:
    void startTask(TaskPtr task) {  // TaskPtr = std::shared_ptr<ITask>
        task->start();  // 依赖抽象，不依赖具体类
    }
};

// 使用依赖注入
void main() {
    auto service = std::make_shared<TaskService>(...);

    // 外部创建具体对象，注入到高层
    TaskPtr task1 = std::make_shared<LiveStreamTask>(config1, service);
    TaskPtr task2 = std::make_shared<MediaFileTask>(config2, service);

    manager.startTask(task1);  // ✅ 依赖抽象
    manager.startTask(task2);  // ✅ 依赖抽象
}
```

### 🔥 项目中的实例：TaskService 注入

```cpp
// ✅ LiveStreamTask 依赖抽象（TaskService 接口）
class LiveStreamTask : public ITask {
public:
    LiveStreamTask(const TaskConfig& config,
                   std::shared_ptr<TaskService> service)  // 依赖注入
        : config_(config), service_(service) {}

private:
    std::shared_ptr<TaskService> service_;  // 依赖抽象
};

// 创建时注入依赖
auto service = std::make_shared<TaskService>(vision, mqtt);
auto task = std::make_shared<LiveStreamTask>(config, service);
```

**优势**:

- ✅ 可以替换 `TaskService` 实现（如测试时用 Mock）
- ✅ `LiveStreamTask` 不依赖具体的 `TaskService` 实现
- ✅ 易于单元测试

### 🎯 面试标准答案

**Q**: 什么是依赖倒置原则？如何实现？

**A**:

> "依赖倒置原则是指高层模块不应该依赖低层模块，两者都应该依赖抽象。实现方式是通过依赖注入，将具体对象从外部传入，而非内部直接创建。
>
> 在我的项目中，`LiveStreamTask` 构造函数接受 `std::shared_ptr<TaskService>`，而非内部 `new TaskService()`。这样，`LiveStreamTask` 只依赖 `TaskService` 的抽象接口，在测试时可以注入 Mock 对象，提高了代码的可测试性和灵活性。"

## 面试高频问题

### Q1: SOLID 原则之间的关系？

**A**:

- **SRP + ISP**: SRP 是类级别，ISP 是接口级别，都强调"单一职责"
- **OCP + DIP**: 通过依赖抽象实现开闭原则
- **LSP**: 是多态的基础，违反 LSP 会破坏 OCP

### Q2: 虚函数默认实现 vs 纯虚函数，如何选择？

**A**:
| 场景 | 选择 | 示例 |
|------|------|------|
| **所有子类都必须实现** | 纯虚函数 `= 0` | `virtual bool start() = 0;` |
| **大多数子类需要，少数不需要** | 虚函数 + 默认空实现 | `virtual void onTaskEnd() {}` |
| **所有子类都用同一实现** | 非虚函数 | `std::string getTaskId() const;` |

### Q3: 什么时候用抽象类，什么时候用接口？

**A**:

- **C++ 没有纯粹的"接口"**，只有抽象类
- **模拟接口**: 只有纯虚函数，没有成员变量
- **抽象类**: 可以有部分实现和成员变量

```cpp
// 模拟"接口"（只有纯虚函数）
class IObserver {
public:
    virtual ~IObserver() = default;
    virtual void onUpdate() = 0;
};

// 抽象类（有部分实现）
class ITask {
public:
    virtual ~ITask() = default;
    virtual bool start() = 0;  // 纯虚
    virtual void onTaskEnd() {}  // 有默认实现

protected:
    std::string taskId_;  // 可以有成员变量
};
```

### Q4: 如何避免类型转换（dynamic_cast）？

**A**:
使用虚函数 + 多态，而非类型判断：

```cpp
// ❌ 类型转换
if (auto liveTask = dynamic_cast<LiveStreamTask*>(task.get())) {
    liveTask->specialMethod();
}

// ✅ 多态
task->onTaskEnd();  // 自动调用正确的实现
```

### Q5: 依赖注入的方式有哪些？

**A**:

1. **构造函数注入**（推荐）:

   ```cpp
   LiveStreamTask(const TaskConfig& config, std::shared_ptr<TaskService> service);
   ```

2. **Setter 注入**:

   ```cpp
   task->setService(service);
   ```

3. **接口注入**（不常用）:
   ```cpp
   void injectService(TaskService* service);
   ```
