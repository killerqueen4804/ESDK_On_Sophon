## 1. 内存管理

### 📌 栈内存 vs 堆内存

#### 知识点

- **栈内存(Stack)**: 自动分配和释放，函数调用时分配，返回时释放
- **堆内存(Heap)**: 手动分配和释放，使用 new/delete 或 malloc/free

#### 经典例子

```cpp
void example() {
    // 栈内存 - 自动管理
    int stackVar = 42;  // 函数结束时自动销毁

    // 堆内存 - 需要手动管理
    int* heapVar = new int(42);  // 必须手动delete
    delete heapVar;  // 释放内存
}
```

#### 项目中的例子

```cpp
// src/core/Logger.cpp
class Logger {
private:
    // 栈内存：作为成员变量，随对象生命周期管理
    std::string logLevel_;

    // 堆内存：使用智能指针管理，自动释放
    std::unique_ptr<std::ofstream> logFile_;
};
```

#### 详细讲解

**为什么区分栈和堆？**

1. **性能**: 栈分配速度快(只需移动栈指针)，堆分配慢(需要查找合适空间)
2. **大小**: 栈空间有限(通常 1-8MB)，堆空间大(受系统内存限制)
3. **生命周期**: 栈变量自动管理，堆变量需要手动管理或使用智能指针

**面试常见问题**:

- Q: 什么时候使用堆？什么时候使用栈？
- A:
  - 栈：小对象、生命周期明确、性能要求高
  - 堆：大对象、动态大小、需要延长生命周期

**易错点**:

```cpp
// ❌ 错误：返回栈变量的指针
int* dangerousFunction() {
    int local = 42;
    return &local;  // 危险！local已被销毁
}

// ✅ 正确：返回堆变量或使用智能指针
std::unique_ptr<int> safeFunction() {
    return std::make_unique<int>(42);
}
```

## 2. 智能指针

### 📌 unique_ptr - 独占所有权

#### 知识点

- **独占所有权**: 同一时刻只能有一个 unique_ptr 指向对象
- **不可拷贝**: 只能移动(move)，不能拷贝
- **自动释放**: 离开作用域时自动 delete

#### 经典例子

```cpp
#include <memory>

void uniquePtrExample() {
    // 创建unique_ptr
    std::unique_ptr<int> ptr1 = std::make_unique<int>(42);

    // ❌ 错误：不能拷贝
    // std::unique_ptr<int> ptr2 = ptr1;

    // ✅ 正确：可以移动
    std::unique_ptr<int> ptr2 = std::move(ptr1);
    // 此时ptr1为nullptr，ptr2拥有对象
}
```

#### 项目中的例子

```cpp
// src/core/Logger.h
class Logger {
public:
    static Logger& getInstance() {
        static Logger instance;
        return instance;
    }

private:
    // 使用unique_ptr管理文件句柄
    std::unique_ptr<std::ofstream> logFile_;

    // Pimpl惯用法 - 隐藏实现细节
    class Impl;
    std::unique_ptr<Impl> pImpl_;
};
```

#### 详细讲解

**为什么使用 unique_ptr？**

1. **自动内存管理**: 避免忘记 delete 导致内存泄漏
2. **异常安全**: 即使抛出异常也会自动释放资源(RAII 原则)
3. **零开销**: 与原始指针性能相同
4. **表达所有权**: 代码意图更清晰

**面试要点**:

- Q: unique_ptr 和原始指针的区别？
- A: unique_ptr 自动管理内存，原始指针需要手动 delete。unique_ptr 表达独占所有权语义。

**使用场景**:

- Pimpl 惯用法(隐藏实现)
- 工厂函数返回值
- 容器中存储多态对象

### 📌 shared_ptr - 共享所有权

#### 知识点

- **引用计数**: 内部维护引用计数，最后一个 shared_ptr 销毁时释放对象
- **可拷贝**: 拷贝时引用计数+1
- **线程安全**: 引用计数的修改是线程安全的

#### 经典例子

```cpp
void sharedPtrExample() {
    std::shared_ptr<int> ptr1 = std::make_shared<int>(42);
    std::cout << "引用计数: " << ptr1.use_count() << std::endl;  // 1

    {
        std::shared_ptr<int> ptr2 = ptr1;  // 拷贝，引用计数+1
        std::cout << "引用计数: " << ptr1.use_count() << std::endl;  // 2
    }  // ptr2销毁，引用计数-1

    std::cout << "引用计数: " << ptr1.use_count() << std::endl;  // 1
}  // ptr1销毁，引用计数归0，释放对象
```

#### 项目中的例子

```cpp
// src/vision/detector/Yolov10Detector.h
class Yolov10Detector {
private:
    // 多个检测器可能共享同一个模型
    std::shared_ptr<fastdeploy::vision::detection::YOLOv10> model_;

    // 共享配置对象
    std::shared_ptr<DetectorConfig> config_;
};
```

#### 详细讲解

**什么时候使用 shared_ptr？**

1. 多个对象需要共享资源
2. 对象所有权不明确
3. 回调函数需要延长对象生命周期

**注意事项**:

```cpp
// ❌ 错误：循环引用导致内存泄漏
class Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;  // 循环引用！
};

// ✅ 正确：使用weak_ptr打破循环
class Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;  // 弱引用，不增加引用计数
};
```

## 3. 面向对象

### 📌 封装 (Encapsulation)

#### 知识点

- 隐藏内部实现细节
- 通过 public 接口访问
- 使用 private/protected 保护数据

#### 项目中的例子

3. **便于维护**: 接口稳定，实现可变

### 📌 继承 (Inheritance)

#### 知识点

- 代码复用
- is-a 关系
- public/protected/private 继承

#### 项目中的例子

```cpp
// src/vision/detector/IDetector.h
// 检测器基类接口
class IDetector {
public:
    virtual ~IDetector() = default;
    virtual DetectionResult detect(const cv::Mat& image) = 0;
    virtual bool initialize(const std::string& modelPath) = 0;
};

// YOLOv10检测器 - 继承接口
class Yolov10Detector : public IDetector {
public:
    DetectionResult detect(const cv::Mat& image) override;
    bool initialize(const std::string& modelPath) override;
};

// YOLOv8检测器 - 同样的接口，不同的实现
class Yolov8Detector : public IDetector {
public:
    DetectionResult detect(const cv::Mat& image) override;
    bool initialize(const std::string& modelPath) override;
};
```

#### 详细讲解

**虚函数表(vtable)**:

```cpp
// 编译器为每个含虚函数的类生成虚函数表
class Base {
    virtual void foo() { }  // 虚函数
    // 内部隐式添加: void* __vptr;  // 指向vtable的指针
};
```

**面试要点**:

- Q: 虚函数的实现原理？
- A: 通过虚函数表(vtable)实现动态绑定。对象内部有 vptr 指向类的 vtable，调用虚函数时通过 vtable 查找实际函数地址。

## 4. 设计模式

### 📌 单例模式 (Singleton)

#### 知识点

确保一个类只有一个实例，并提供全局访问点

#### 经典实现

```cpp
// C++11 线程安全的单例
class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance;  // C++11保证线程安全
        return instance;
    }

    // 禁止拷贝
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

private:
    Singleton() = default;  // 私有构造
};
```

#### 项目中的例子

```cpp
// src/core/Logger.h
class Logger {
public:
    static Logger& getInstance() {
        static Logger instance;
        return instance;
    }

    void info(const std::string& msg) {
        // 实现...
    }

private:
    Logger();
    ~Logger();
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
};

// 使用
Logger::getInstance().info("系统启动");
```

#### 详细讲解

**为什么使用单例？**

1. 日志系统 - 全局唯一的日志输出
2. 配置管理 - 全局共享配置
3. 数据库连接池 - 统一管理连接

**线程安全问题**:

```cpp
// ❌ 不安全的懒汉式
class UnsafeSingleton {
    static UnsafeSingleton* instance;
public:
    static UnsafeSingleton* getInstance() {
        if (!instance) {  // 线程不安全！
            instance = new UnsafeSingleton();
        }
        return instance;
    }
};

// ✅ C++11安全版本
static Singleton& getInstance() {
    static Singleton instance;  // 编译器保证线程安全初始化
    return instance;
}
```

**面试要点**:

- Q: 如何实现线程安全的单例？
- A: C++11 使用局部静态变量，编译器保证线程安全；C++11 之前使用双重检查锁定(DCL)

### 📌 工厂模式 (Factory)

#### 知识点

- 创建对象的接口
- 隐藏对象创建细节
- 便于扩展新类型

#### 项目中的例子

```cpp
// src/vision/detector/DetectorFactory.h
class DetectorFactory {
public:
    enum class DetectorType {
        YOLOV10,
        YOLOV8,
        PPYOLO
    };

    static std::unique_ptr<IDetector> create(DetectorType type) {

    }
```

#### 详细讲解

**工厂模式的优点**:

1. **解耦**: 客户端不需要知道具体类名
2. **扩展**: 添加新类型只需修改工厂
3. **统一管理**: 集中处理对象创建逻辑

```cpp
class IMqttMessageObserver {
public:
    virtual ~IMqttMessageObserver() = default;
    virtual void onMessageReceived(const std::string& topic,
                                   const std::string& message) = 0;

class MqttClient {
private:

            observer->onMessageReceived(topic, message);
        }
    }
};
```

### 📌 互斥锁 (Mutex)

#### 知识点

保护共享数据，避免数据竞争

#### 经典例子

```cpp
#include <mutex>

class ThreadSafeCounter {
private:
    int count_ = 0;
    mutable std::mutex mutex_;  // mutable允许在const函数中修改

public:
    void increment() {
        std::lock_guard<std::mutex> lock(mutex_);
        ++count_;  // 受保护的操作
    }

    int get() const {
        std::lock_guard<std::mutex> lock(mutex_);
        return count_;
    }
};
```

#### 项目中的例子

```cpp
// src/core/Logger.cpp
class Logger {
private:
    std::mutex mutex_;
    std::ofstream logFile_;

public:
    void log(const std::string& message) {
        std::lock_guard<std::mutex> lock(mutex_);  // RAII锁
        logFile_ << message << std::endl;
    }
};
```

#### 详细讲解

**lock_guard vs unique_lock**:

- `lock_guard`: 简单的 RAII 锁，不可解锁
- `unique_lock`: 更灵活，可以手动解锁和重新加锁

**面试要点**:

- Q: 什么是死锁？如何避免？
- A: 两个线程互相等待对方释放锁。避免方法：
  1. 固定加锁顺序
  2. 使用 std::lock 同时锁定多个锁
  3. 使用超时机制

## 6. STL 容器

### 📌 vector vs list vs deque

#### 知识点对比

| 容器   | 底层实现 | 随机访问 | 插入删除             | 使用场景         |
| ------ | -------- | -------- | -------------------- | ---------------- |
| vector | 动态数组 | O(1)     | 尾部 O(1), 中间 O(n) | 最常用，默认选择 |

## 8. CMake 构建系统

### 📌 CMake 基础 - 构建系统生成器

#### 知识点

CMake 是跨平台的构建系统生成器，它读取 CMakeLists.txt 配置文件，生成对应平台的构建文件（如 Makefile、VS 工程）。

**核心命令**:

```cmake
cmake_minimum_required(VERSION 3.15)  # 指定最低版本
project(MyProject CXX)                # 项目定义
add_executable(main main.cpp)         # 创建可执行文件
add_library(mylib STATIC lib.cpp)     # 创建静态库
target_link_libraries(main mylib)     # 链接库
```

#### 经典例子

```cmake
# 最简单的CMakeLists.txt
cmake_minimum_required(VERSION 3.15)
project(HelloWorld CXX)

# 设置C++标准
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 创建可执行文件
add_executable(hello main.cpp utils.cpp)

# 链接系统库
find_package(Threads REQUIRED)
target_link_libraries(hello Threads::Threads)
```

#### 项目中的例子

```cmake
# ESDK_On_Sophon/CMakeLists.txt（规划中）
cmake_minimum_required(VERSION 3.15)
project(ESDK_Sophon VERSION 1.0.0 LANGUAGES CXX)

# C++17标准
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# 输出目录
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)

# 添加源码目录
add_subdirectory(src)

# 主程序
add_executable(esdk_app
    src/main.cpp
    src/core/Logger.cpp
    src/mqtt/MqttClient.cpp
)

# 链接第三方库
find_package(Qt5 COMPONENTS Core REQUIRED)
target_link_libraries(esdk_app Qt5::Core)
```

#### 详细讲解

**1. CMake 工作流程**:

```
CMakeLists.txt → cmake命令 → Makefile/工程文件 → make/编译 → 可执行文件
```

**2. 重要目录变量**:

- `CMAKE_SOURCE_DIR`: 顶层 CMakeLists.txt 所在目录（源码根目录）
- `CMAKE_BINARY_DIR`: 构建目录（通常是 build/）
- `PROJECT_SOURCE_DIR`: 最近的 project()命令所在目录
- `CMAKE_CURRENT_SOURCE_DIR`: 当前 CMakeLists.txt 所在目录

**3. 构建类型**:

```cmake
# Debug: 调试版本，包含调试信息，无优化
cmake .. -DCMAKE_BUILD_TYPE=Debug

# Release: 发布版本，最高优化，无调试信息
cmake .. -DCMAKE_BUILD_TYPE=Release
```

#### 面试要点

**Q1: CMakeLists.txt 和 Makefile 的区别？**
A:

- CMakeLists.txt 是配置文件，描述项目如何构建，跨平台
- Makefile 是具体的构建脚本，由 CMake 根据平台生成
- CMakeLists.txt 写一次，可以在 Windows/Linux/Mac 上使用

**Q2: add_executable 和 add_library 的区别？**
A:

- `add_executable`: 创建可执行文件（.exe/.out）
- `add_library`: 创建库文件
  - STATIC: 静态库（.a/.lib），编译时链接
  - SHARED: 动态库（.so/.dll），运行时加载

**Q3: include_directories 和 target_include_directories 的区别？**
A:

- `include_directories`: 全局生效，之后所有目标都能看到这些路径
- `target_include_directories`: 只对指定目标生效，更精确（推荐使用）

#### 易错点

```cmake
# ❌ 错误：使用file(GLOB)自动查找文件
```

### 📌 target 命令 - 现代 CMake 核心

#### 知识点

现代 CMake 强调"target-based"方式，每个操作都针对特定目标，而不是全局生效。

**核心 target 命令**:

- `target_include_directories`: 设置头文件路径
- `target_link_libraries`: 链接库
- `target_compile_options`: 设置编译选项
- `target_compile_definitions`: 设置宏定义

#### 经典例子

```cmake
# 创建库
add_library(mylib STATIC
    src/utils.cpp
    src/logger.cpp
)

# 为库设置头文件路径
target_include_directories(mylib
    PUBLIC  include/   # 使用mylib的目标也能看到
    PRIVATE src/       # 只有mylib内部能看到
)

# 创建可执行文件并链接库
add_executable(myapp main.cpp)
target_link_libraries(myapp mylib)
# myapp自动继承mylib的PUBLIC头文件路径！
```

#### 项目中的例子

```cmake
# src/mqtt/CMakeLists.txt（规划中）
# 创建MQTT模块库
add_library(mqtt_module STATIC
    MqttClient.cpp
    MqttProcessor.cpp
)

# 设置头文件路径
target_include_directories(mqtt_module
    PUBLIC
        ${CMAKE_CURRENT_SOURCE_DIR}  # mqtt/目录，其他模块可见
    PRIVATE
        ${CMAKE_SOURCE_DIR}/src/core  # 依赖core模块
)

# 链接第三方MQTT库
target_link_libraries(mqtt_module
    PRIVATE
        paho-mqtt3c
        Qt5::Core
)

# 主程序中使用
add_executable(esdk_app main.cpp)
target_link_libraries(esdk_app mqtt_module)
# esdk_app自动获得mqtt_module的PUBLIC头文件路径
```

#### 详细讲解

**三种可见性修饰符**:

1. **PRIVATE（私有）**:

   - 只有当前目标能使用
   - 示例：内部实现细节

2. **PUBLIC（公开）**:

   - 当前目标和链接它的目标都能使用
   - 示例：库的公共接口

3. **INTERFACE（接口）**:
   - 当前目标不用，但链接它的目标能使用
   - 示例：header-only 库

**传递性示例**:

```cmake
# libA设置PUBLIC头文件
add_library(libA a.cpp)
target_include_directories(libA PUBLIC include/libA)

# libB链接libA
add_library(libB b.cpp)
target_link_libraries(libB PUBLIC libA)

# app链接libB
add_executable(app main.cpp)
target_link_libraries(app libB)

# 结果：app自动获得libA和libB的头文件路径（传递性）
```

#### 面试要点

**Q: PUBLIC、PRIVATE、INTERFACE 的区别？用什么场景？**
A:

- **PRIVATE**: 内部实现，不希望暴露给用户
  - 使用场景：源文件、内部头文件、实现依赖的库
- **PUBLIC**: 公共接口，用户也需要
  - 使用场景：API 头文件、用户代码也依赖的库
- **INTERFACE**: 纯接口，自己不用但用户需要
  - 使用场景：header-only 库、编译定义

**Q: 为什么推荐使用 target\_\*而不是全局命令？**
A:

1. **作用域清晰**: 只影响指定目标，不会意外影响其他目标
2. **传递性**: PUBLIC 属性可以自动传递给依赖者
3. **易于维护**: 修改一个目标不影响其他目标
4. **现代 CMake 标准**: 3.0+推荐的最佳实践

```cmake
# 问题：内部实现暴露给了所有用户
```

## 9. 配置管理与设计模式

### � 配置驱动设计 (Configuration-Driven Design)

#### 知识点

**配置驱动设计**是一种将程序的行为参数从代码中分离到配置文件的设计模式。核心思想是"**代码定义如何做，配置决定做什么**"，提高系统的灵活性和可维护性。

**核心特点**：

- 代码与配置分离：业务逻辑不依赖具体参数值
- 运行时可调整：无需重新编译即可修改行为
- 环境适配性：不同环境使用不同配置文件
- 可维护性：配置集中管理，易于查找和修改

#### 经典例子

```cpp
// ❌ 硬编码方式（不推荐）
class Logger {
public:
    void log(const std::string& msg) {
        // 硬编码路径、级别、大小限制
        std::ofstream file("/var/log/app.log");
        if (file.size() > 100 * 1024 * 1024) {  // 硬编码100MB
            rotateLog();
        }
        file << msg;
    }
};

// ✅ 配置驱动方式（推荐）
class Logger {
public:
    void initialize() {
        auto& config = Config::getInstance();
        logPath_ = config.getString("logger.path", "/var/log/app.log");
        maxSize_ = config.getInt("logger.max_size_mb", 100) * 1024 * 1024;
        level_ = config.getString("logger.level", "INFO");
    }

    void log(const std::string& msg) {
        std::ofstream file(logPath_);
        if (file.size() > maxSize_) {
            rotateLog();
        }
        file << msg;
    }

private:
    std::string logPath_;
    size_t maxSize_;
    std::string level_;
};

// config.json
{
    "logger": {
        "path": "/var/log/myapp.log",
        "max_size_mb": 200,
        "level": "DEBUG"
    }
}
```

**Q1: 配置驱动设计相比硬编码有什么优势？**

**A**:

1. **灵活性**: 无需重新编译即可修改程序行为，支持运行时热更新
2. **环境适配**: 同一份代码可通过不同配置适配开发/测试/生产环境
3. **可维护性**: 配置集中管理，参数修改无需翻阅代码
4. **安全性**: 敏感信息（密码、密钥）可独立存储，不提交到代码仓库
5. **测试性**: 快速切换配置进行不同场景测试
6. **部署性**: 发布时仅需替换配置文件，无需重新打包

**Q2: 如何设计一个健壮的配置管理系统？**

**A**:

1. **默认值机制**: 配置缺失时使用合理默认值（Fallback Pattern）
2. **类型安全**: 提供类型化的 getter 方法，避免类型转换错误
3. **嵌套路径**: 支持 `"logger.rotation.max_days"` 这样的层级访问
4. **异常处理**: 配置文件损坏、格式错误时要有明确的错误提示
5. **线程安全**: 多线程环境下要保证配置读取的线程安全性
6. **热更新**: 支持 reload()方法，无需重启程序即可重新加载配置
7. **验证机制**: 配置加载后进行合法性检查（如端口范围、路径存在性）

**Q3: 本项目中 Config 是如何实现嵌套路径访问的？**

**A**:

```cpp
// 实现原理：手动解析嵌套路径
std::string Config::Impl::getString(const std::string& key,
                                     const std::string& defaultValue) const {
    try {
        std::lock_guard<std::mutex> lock(mutex_);

        // 按"."分割路径：logger.rotation.max_days → ["logger", "rotation", "max_days"]
        std::vector<std::string> keys;
        std::stringstream ss(key);
        std::string token;
        while (std::getline(ss, token, '.')) {
            keys.push_back(token);
        }

        // 逐层访问JSON对象
        nlohmann::json currentNode = jsonData_;
        for (const auto& k : keys) {
            if (!currentNode.contains(k)) {
                return defaultValue;  // 路径不存在，返回默认值
            }
            currentNode = currentNode[k];
        }

        return currentNode.get<std::string>();

    } catch (...) {
        return defaultValue;
    }
}

// 为什么不用 json::pointer？
// nlohmann::json支持JSON Pointer (RFC 6901)，如 "/logger/rotation/max_days"
// 但某些版本不支持std::string构造json::pointer，会导致编译错误
// 手动解析更通用、可控，避免库版本兼容性问题
```

### 📌 降级方案模式 (Fallback Pattern)

#### 知识点

**降级方案模式**（Fallback Pattern）是一种容错设计模式，当主要方案失败时，自动切换到备用方案，确保系统**"优雅降级"**而不是直接崩溃。

**核心思想**：

- 主方案 + 备用方案的双重保障
- 失败时自动切换，用户无感知
- 保证系统的**可用性**优先于**最优性**

#### 经典例子

```cpp
// 场景：获取配置值
std::string getLogLevel() {
    // 1. 优先从配置文件读取
    try {
        return config.getString("logger.level");
    } catch (...) {
        // 2. 降级：从环境变量读取
        const char* envLevel = std::getenv("LOG_LEVEL");
        if (envLevel != nullptr) {
            return std::string(envLevel);
        }
        // 3. 最终降级：使用硬编码默认值
        return "INFO";
    }
}

// 场景：网络请求
Data fetchData() {
    // 1. 优先从远程API获取
    try {
        return httpClient.get("https://api.example.com/data");
    } catch (const NetworkException& e) {
        // 2. 降级：从缓存读取
        if (cache.has("data")) {
            logWarning("网络失败，使用缓存数据");
            return cache.get("data");
        }
        // 3. 最终降级：返回默认数据
        return Data::defaultValue();
    }
}
```

#### 详细讲解

**1. 降级方案的层次结构**

```cpp
// 单层降级（简单）
try {
    return primaryMethod();
} catch (...) {
    return fallbackValue;  // 直接降级到默认值
}

// 多层降级（推荐）
std::string getValue() {
    // 第1优先级：配置文件
    try {
        return config.get("key");
    } catch (...) {
        // 第2优先级：环境变量
        const char* env = std::getenv("KEY");
        if (env != nullptr) {
            return env;
        }
        // 第3优先级：用户目录配置
        std::string userConfig = readUserConfig();
        if (!userConfig.empty()) {
            return userConfig;
        }
        // 最终降级：硬编码默认值
        return DEFAULT_VALUE;
    }
}
```

**2. 降级方案 vs 异常处理**

| 特性         | 降级方案                     | 纯异常处理           |
| ------------ | ---------------------------- | -------------------- |
| **目标**     | 保证系统可用性               | 错误通知和清理       |
| **行为**     | 切换到备用方案               | 中断执行、抛出异常   |
| **用户体验** | 无感知（可能功能有限）       | 中断、错误提示       |
| **日志**     | 警告级别（系统仍可用）       | 错误级别（执行中断） |
| **适用场景** | 服务降级、配置缺失、网络失败 | 致命错误、数据损坏   |

**3. 何时使用降级方案？**

✅ **适合使用降级方案的场景**：

- 配置文件缺失或损坏
- 网络请求失败（可使用缓存）
- 外部服务不可用（可使用本地备份）
- 资源不足（可降低性能换取可用性）
- 非核心功能失败（可关闭该功能）

❌ **不适合降级的场景**：

- 数据库连接失败（核心功能无法继续）
- 文件权限不足（无法绕过）
- 内存分配失败（系统级问题）
- 核心算法错误（降级无意义）

**4. 降级方案的最佳实践**


#### 面试要点

**Q1: 什么是降级方案模式？为什么需要它？**

**A**:
降级方案模式是当主要方案失败时，自动切换到备用方案的容错机制。

**为什么需要**：

1. **高可用性**: 防止单点故障导致系统崩溃
2. **用户体验**: 部分功能失败仍能保证核心功能可用
3. **运维友好**: 配置错误不会导致生产环境崩溃
4. **渐进式故障**: 优雅降级而非直接宕机

**Q2: 本项目中 Logger 是如何实现降级方案的？**

**A**:

```cpp
// Logger的双层降级机制：

// 第1层：Config内部的降级（方法级别）
std::string Config::getString(const std::string& key, const std::string& defaultValue) {
    try {
        // 主方案：解析JSON获取值
        return jsonData_[key].get<std::string>();
    } catch (...) {
        // 降级1：返回用户提供的默认值
        return defaultValue;
    }
}

// 第2层：Logger的降级（类级别）
void Logger::loadConfigSettings() {
    try {
        // 主方案：从Config读取
        auto& config = Config::getInstance();
        logDir_ = config.getString("logger.dir", DEFAULT_LOG_DIR);
        // 如果config.json不存在，Config::getInstance()会抛异常
    } catch (...) {
        // 降级2：Config完全失败，使用硬编码常量
        logDir_ = DEFAULT_LOG_DIR;
        maxDays_ = DEFAULT_MAX_LOG_DAYS;
    }
}

// 这样设计的好处：
// 1. Config可独立工作，不依赖Logger
// 2. Logger可独立工作，不强制依赖Config
// 3. 任何一层失败都有降级方案，系统不会崩溃
```

**Q3: 降级方案和默认参数有什么区别？**

**A**:

```cpp
// 默认参数：编译时确定，函数调用时的语法糖
void log(std::string level = "INFO");  // 调用时可省略参数

// 降级方案：运行时决策，错误处理机制
std::string level = config.get("level", "INFO");  // 主方案失败才用默认值

// 区别：
// 1. 时机：默认参数是编译时，降级方案是运行时
// 2. 触发：默认参数是用户不传参，降级方案是主方案失败
// 3. 灵活性：降级方案可以有多层、可记录日志、可通知监控
// 4. 应用：默认参数是API便利性，降级方案是容错能力
```

```cpp
    // 2. 降级方案
    if (auto val = tryFallback()) return *val;
    // 3. 最终默认值
    return DEFAULT_VALUE;
```

### 📌 JSON 配置解析

#### 知识点

**JSON (JavaScript Object Notation)** 是一种轻量级的数据交换格式，广泛用于配置文件、API 通信、数据存储。C++中常用 **nlohmann/json** 库进行解析。

**JSON 基本类型**：

- **对象 (Object)**: `{"key": "value"}`
- **数组 (Array)**: `[1, 2, 3]`
- **字符串 (String)**: `"text"`
- **数字 (Number)**: `123`, `3.14`
- **布尔值 (Boolean)**: `true`, `false`
- **空值 (Null)**: `null`

#### 经典例子

```cpp
#include <nlohmann/json.hpp>
#include <fstream>
#include <iostream>

// 示例JSON文件: config.json
// {
//     "server": {
//         "host": "localhost",
//         "port": 8080
//     },
//     "users": ["Alice", "Bob"]
// }

void parseJSON() {
    // 1. 读取JSON文件
    std::ifstream file("config.json");
    nlohmann::json j;
    file >> j;

    // 2. 访问简单键值
    std::string host = j["server"]["host"];  // "localhost"
    int port = j["server"]["port"];          // 8080

    // 3. 遍历数组
    for (const auto& user : j["users"]) {
        std::cout << user.get<std::string>() << std::endl;
    }

    // 4. 检查键是否存在
    if (j.contains("debug")) {
        bool debug = j["debug"].get<bool>();
    }

    // 5. 类型安全的获取（带默认值）
    bool ssl = j.value("ssl", false);  // 如果不存在，返回false
}
```

#### 项目中的例子

```cpp
// Config类的JSON解析实现（Config.cpp）
class Config::Impl {
public:
    void load(const std::string& configPath) {
        std::ifstream file(configPath);
        if (!file.is_open()) {
            throw std::runtime_error("无法打开配置文件: " + configPath);
        }

        try {
            file >> jsonData_;  // nlohmann/json的operator>>
        } catch (const nlohmann::json::exception& e) {
            throw std::runtime_error("JSON解析失败: " + std::string(e.what()));
        }
    }

    // 嵌套路径访问: "logger.rotation.max_days"
    std::string getString(const std::string& key, const std::string& defaultValue) const {
        try {
            std::lock_guard<std::mutex> lock(mutex_);

            // 手动解析嵌套路径
            std::vector<std::string> keys;
            std::stringstream ss(key);
            std::string token;
            while (std::getline(ss, token, '.')) {
                keys.push_back(token);
            }

            // 逐层访问JSON对象
            nlohmann::json currentNode = jsonData_;
            for (const auto& k : keys) {
                if (!currentNode.contains(k)) {
                    return defaultValue;
                }
                currentNode = currentNode[k];
            }

            return currentNode.get<std::string>();
        } catch (...) {
            return defaultValue;
        }
    }

private:
    nlohmann::json jsonData_;
    mutable std::mutex mutex_;
};

// 配置文件示例（config/config.json）
{
    "logger": {
        "level": "DEBUG",
        "console_output": true,
        "log_directory": "logs",
        "rotation": {
            "enabled": true,
            "max_days": 15,
            "max_file_size_mb": 100
        }
    },
    "mqtt": {
        "broker": {
            "host": "localhost",
            "port": 1883
        }
    }
}
```

#### 详细讲解

**1. nlohmann/json 的核心特性**

```cpp
#include <nlohmann/json.hpp>
using json = nlohmann::json;

// 特性1: 直接从文件读取
std::ifstream file("config.json");
json j = json::parse(file);  // 或 file >> j;

// 特性2: 类型自动推断
json j = {
    {"name", "Alice"},
    {"age", 25},
    {"active", true}
};
std::string name = j["name"];  // 自动转换
int age = j["age"];
bool active = j["active"];

// 特性3: 数组操作
json arr = {1, 2, 3};
arr.push_back(4);
for (auto& elem : arr) {
    std::cout << elem << std::endl;
}

// 特性4: 异常处理
try {
    int value = j["nonexistent"];  // 抛出异常
} catch (json::exception& e) {
    std::cout << e.what() << std::endl;
}

// 特性5: 安全访问（不抛异常）
int value = j.value("key", 0);  // 不存在返回默认值0
```

**2. JSON 路径访问方式对比**

```cpp
// 方式1: 直接访问（简单但不支持动态路径）
std::string level = jsonData_["logger"]["rotation"]["max_days"];

// 方式2: JSON Pointer (RFC 6901标准)
// 路径格式: "/logger/rotation/max_days"
#include <nlohmann/json.hpp>
std::string level = jsonData_["/logger/rotation/max_days"_json_pointer];

// 方式3: 手动解析路径（本项目采用，兼容性最好）
std::string getByPath(const std::string& path) {
    std::vector<std::string> keys = split(path, '.');
    json node = jsonData_;
    for (const auto& key : keys) {
        node = node[key];
    }
    return node.get<std::string>();
}

// 对比：
// | 方式 | 优点 | 缺点 |
// | 直接访问 | 最快、类型安全 | 路径硬编码，不支持动态 |
// | JSON Pointer | 标准、简洁 | 某些版本不支持std::string构造 |
// | 手动解析 | 灵活、兼容性好 | 需要自己实现、稍慢 |
```

**3. JSON 异常处理**

```cpp
#include <nlohmann/json.hpp>

try {
    // 常见异常1: 文件不存在
    std::ifstream file("config.json");
    if (!file.is_open()) {
        throw std::runtime_error("文件不存在");
    }

    // 常见异常2: JSON格式错误
    nlohmann::json j;
    file >> j;  // 可能抛出 json::parse_error

    // 常见异常3: 类型转换错误
    int value = j["key"].get<int>();  // 如果value是字符串，抛出 json::type_error

    // 常见异常4: 键不存在
    std::string val = j["nonexistent"];  // 抛出 json::out_of_range

} catch (const nlohmann::json::parse_error& e) {
    std::cerr << "JSON解析错误: " << e.what() << std::endl;
} catch (const nlohmann::json::type_error& e) {
    std::cerr << "类型错误: " << e.what() << std::endl;
} catch (const nlohmann::json::out_of_range& e) {
    std::cerr << "键不存在: " << e.what() << std::endl;
} catch (const std::exception& e) {
    std::cerr << "其他错误: " << e.what() << std::endl;
}
```

#### 面试要点

**Q1: 为什么选择 JSON 作为配置文件格式？**

**A**:

1. **结构化**: 支持嵌套对象和数组，可表达复杂配置
2. **可读性**: 语法简单，人类可直接阅读和编辑
3. **跨语言**: 几乎所有语言都有 JSON 解析库
4. **生态丰富**: 工具、编辑器支持好（语法高亮、自动补全）
5. **轻量**: 相比 XML 更简洁，解析开销小

**缺点**:

- 不支持注释（可用`"_comment"`字段绕过）
- 不支持日期、二进制等特殊类型

**Q2: nlohmann/json 的优势是什么？**

**A**:

1. **Header-only**: 单头文件，无需编译，直接包含即可使用
2. **现代 C++**: 支持 C++11/14/17 特性，API 设计友好
3. **STL 兼容**: 与`std::vector`、`std::map`无缝转换
4. **异常安全**: 错误处理清晰，提供多种异常类型
5. **性能**: 解析速度接近 RapidJSON 等专业库

```cpp
// STL容器转JSON
std::vector<int> vec = {1, 2, 3};
json j = vec;  // 自动转换

std::map<std::string, int> map = {{"a", 1}, {"b", 2}};
json j2 = map;

// JSON转STL容器
std::vector<int> vec2 = j.get<std::vector<int>>();
```

**Q3: 如何避免 JSON 解析中的常见错误？**

**A**:

1. **键不存在**: 使用`contains()`检查或`value(key, default)`安全访问
2. **类型不匹配**: 使用`is_string()/is_number()`先检查类型
3. **空值处理**: 检查`is_null()`
4. **数组越界**: 用`size()`检查长度

```cpp
// ✅ 安全的访问方式
if (j.contains("key") && j["key"].is_string()) {
    std::string val = j["key"].get<std::string>();
}

// 或使用异常处理
try {
    std::string val = j["key"].get<std::string>();
} catch (const json::exception& e) {
    // 处理错误
}

// 或使用默认值
std::string val = j.value("key", "default");
```

#### 易错点

