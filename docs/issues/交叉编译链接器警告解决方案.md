## 🔍 问题分析

### 1. 什么是交叉编译?

**交叉编译** (Cross Compilation): 在一台机器(x86_64)上编译出另一台机器(aarch64)能运行的程序。

```
┌──────────────────┐           ┌──────────────────┐
│  编译环境         │           │  运行环境         │
│  Docker容器      │  生成可    │  SE7设备         │
│  stream_lzy      │  执行文件  │  (算能微服务器)   │
│  x86_64架构      │ ========> │  aarch64架构     │
│                  │           │                  │
│  ✅ 编译工具链    │           │  ✅ 运行时库      │
│  ✅ 头文件        │           │  ✅ 驱动程序      │
│  ❌ 运行时库      │           │  ✅ TPU固件       │
└──────────────────┘           └──────────────────┘
```

### 2. 为什么会报错?

#### 缺失的库清单

| 库文件                | 用途              | 提供者          |
| --------------------- | ----------------- | --------------- |
| `libbmrt.so.1.0`      | 算能 TPU 运行时库 | FastDeploy 依赖 |
| `libz.so.1`           | zlib 压缩库       | OpenCV 依赖     |
| `libtbb.so.2`         | Intel TBB 并行库  | OpenCV 依赖     |
| `libjpeg.so.8`        | JPEG 图像编解码   | OpenCV 依赖     |
| `libpng16.so.16`      | PNG 图像编解码    | OpenCV 依赖     |
| `libwebp.so.6`        | WebP 图像编解码   | OpenCV 依赖     |
| `libtiff.so.5`        | TIFF 图像编解码   | OpenCV 依赖     |
| `libgdal.so.26`       | 地理数据抽象库    | OpenCV 依赖     |
| `libIlmImf-2_3.so.24` | OpenEXR 图像格式  | OpenCV 依赖     |

#### 依赖关系链

```
test_detector (可执行文件)
  ├─> libdetector.so (我们的代码)
  │    ├─> libfastdeploy.so (FastDeploy)
  │    │    └─> libbmrt.so.1.0 ⚠️ 找不到!
  │    └─> libopencv_core.so (OpenCV)
  │         ├─> libz.so.1 ⚠️ 找不到!
  │         └─> libtbb.so.2 ⚠️ 找不到!
  └─> libopencv_imgcodecs.so (OpenCV图像IO)
       ├─> libjpeg.so.8 ⚠️ 找不到!
       ├─> libpng16.so.16 ⚠️ 找不到!
       └─> ...
```

### 3. 为什么 Docker 容器没有这些库?

**设计考虑**:

- Docker 容器只包含**编译所需**的工具和头文件
- 运行时库(`.so`文件)占用空间大,且只在设备上需要
- SE7 设备已经预装了这些库,无需重复携带

**类比理解**:

```
编译环境 = 工厂(生产产品)
  - 有图纸(头文件)
  - 有机器(编译器)
  - 没有成品零件(运行时库)

运行环境 = 用户家(使用产品)
  - 有配套设施(运行时库)
  - 有电源插座(驱动)
  - 有使用环境(操作系统)
```

## ✅ 解决方案

### 方案 1: 使用 `--allow-shlib-undefined` (推荐) ⭐

#### 原理

告诉链接器:"这些未定义的符号在运行时会被解析,链接时不要报错"。

#### 实现 (已应用到项目)

**修改文件**: `tests/CMakeLists.txt`

```cmake
# Detector模块测试程序
add_executable(test_detector test_detector.cpp)

# 链接所需库
target_link_libraries(test_detector
    PRIVATE
        detector
        core
        ThirdParty::OpenCV
        ThirdParty::FastDeploy
        pthread
)

# 🔧 交叉编译链接器配置
target_link_options(test_detector PRIVATE
    -Wl,-rpath-link,${CMAKE_SOURCE_DIR}/third_party/opencv4.2/lib
    -Wl,-rpath-link,${CMAKE_SOURCE_DIR}/third_party/fastdeploy/lib
    -Wl,--allow-shlib-undefined  # 关键选项!
)
```

#### 参数解释

| 参数                      | 作用                   | 为什么需要                     |
| ------------------------- | ---------------------- | ------------------------------ |
| `-Wl,`                    | 传递参数给链接器       | CMake 与链接器沟通的方式       |
| `-rpath-link,<path>`      | 链接时搜索库的路径     | 告诉链接器去哪里找依赖库的信息 |
| `--allow-shlib-undefined` | 允许共享库有未定义符号 | 交叉编译的核心:运行时才解析    |

#### 重新编译

```bash
cd /workspace/ESDK_On_Sophon/build
cmake ..
make test_detector
```

**预期结果**:

- ⚠️ 警告信息仍会出现(这是正常的)
- ✅ 可执行文件成功生成 `bin/tests/test_detector`
- ✅ 在 SE7 设备上可以正常运行

### 方案 2: 完全静态链接 (不推荐)

#### 原理

将所有库都静态链接进可执行文件,不依赖运行时库。

#### 缺点

- ❌ 可执行文件体积巨大(100MB+)
- ❌ TPU 驱动库(`libbmrt`)无法静态链接
- ❌ 违背嵌入式设备的设计原则

#### 实现(仅供参考,不要使用)

```cmake
target_link_options(test_detector PRIVATE
    -static-libgcc
    -static-libstdc++
    -Wl,-Bstatic -lz -ltbb -ljpeg -lpng -Wl,-Bdynamic
)
```

---

### 方案 3: 复制运行时库到 Docker (不推荐)

#### 原理

从 SE7 设备复制所有`.so`到 Docker 容器。

#### 缺点

- ❌ 需要频繁同步 SE7 设备和容器
- ❌ 占用 Docker 镜像空间
- ❌ 维护成本高

## 📚 知识扩展

### 1. 共享库 vs 静态库

| 特性         | 共享库 (`.so`)   | 静态库 (`.a`)    |
| ------------ | ---------------- | ---------------- |
| **链接时机** | 运行时(动态链接) | 编译时(静态链接) |
| **文件大小** | 小(代码共享)     | 大(代码拷贝)     |
| **更新方式** | 替换`.so`即可    | 需要重新编译     |
| **内存占用** | 多进程共享       | 每个进程独立     |
| **依赖性**   | 需要运行时库     | 自包含           |

#### 为什么嵌入式设备偏爱共享库?

```
假设10个程序都用OpenCV:

静态链接:
  程序1: 100MB (含OpenCV)
  程序2: 100MB (含OpenCV)
  ...
  程序10: 100MB (含OpenCV)
  总计: 1000MB

共享库:
  程序1-10: 各5MB
  OpenCV.so: 50MB (共享)
  总计: 100MB ✅ 节省900MB!
```

### 2. rpath vs rpath-link

| 参数          | 影响阶段 | 用途                       |
| ------------- | -------- | -------------------------- |
| `-rpath`      | 运行时   | 告诉程序去哪里找`.so`      |
| `-rpath-link` | 链接时   | 告诉链接器去哪里找依赖信息 |

```bash
# rpath (运行时搜索路径)
-Wl,-rpath,/opt/sophon/lib
# 生成的可执行文件会记住这个路径

# rpath-link (链接时搜索路径)
-Wl,-rpath-link,./third_party/lib
# 只在编译时生效,不影响运行时
```

### 3. 动态链接器工作原理

#### 运行时加载流程

```
1. 执行 ./test_detector
   ↓
2. 内核启动动态链接器 (ld-linux-aarch64.so)
   ↓
3. 读取ELF头,查找依赖库
   libdetector.so
   libopencv_core.so
   libfastdeploy.so
   ↓
4. 在标准路径搜索:
   /lib/aarch64-linux-gnu/
   /usr/lib/aarch64-linux-gnu/
   /opt/sophon/lib/
   $LD_LIBRARY_PATH
   ↓
5. 加载所有依赖库到内存
   ↓
6. 解析未定义符号 (bmrt_load_bmodel -> libbmrt.so)
   ↓
7. 执行main()函数
```

#### SE7 设备库路径配置

```bash
# 查看SE7设备上的库路径配置
cat /etc/ld.so.conf.d/sophon.conf

# 内容示例:
/opt/sophon/libsophon-current/lib
/opt/sophon/libsophon-current/lib/bmnn
/system/lib
```

## 📝 面试要点

### Q1: 什么是交叉编译?为什么需要?

**A**:

- **定义**: 在主机平台(x86_64)编译生成目标平台(aarch64)的可执行文件
- **原因**:
  1. 目标设备资源受限(算能 SE7 只有 4GB 内存)
  2. 编译速度慢(嵌入式 CPU 性能低)
  3. 开发效率(在 PC 上调试工具更丰富)

### Q2: 链接时的 undefined reference 和运行时的 symbol not found 有什么区别?

**A**:

- **链接时 undefined reference**:

  - 原因: 编译器找不到函数/变量的定义
  - 影响: 无法生成可执行文件
  - 解决: 添加链接库、检查函数签名

- **运行时 symbol not found**:
  - 原因: 动态链接器找不到共享库
  - 影响: 程序启动失败
  - 解决: 设置`LD_LIBRARY_PATH`、安装缺失库

### Q3: --allow-shlib-undefined 会带来什么风险?

**A**:

- **优点**: 允许交叉编译顺利进行
- **风险**:
  1. 运行时可能崩溃(如果 SE7 设备缺少库)
  2. 难以在编译阶段发现 API 不兼容
  3. 版本不匹配导致的诡异问题
- **最佳实践**:
  1. 编译后立即在目标设备测试
  2. 维护详细的依赖库版本清单
  3. 使用 CI/CD 自动化设备端测试

### Q4: 如何排查运行时找不到库的问题?

**A**:

```bash
# 1. 查看程序依赖
ldd ./test_detector

# 2. 查看库搜索路径
ldconfig -p | grep opencv

# 3. 临时添加库路径
export LD_LIBRARY_PATH=/opt/sophon/lib:$LD_LIBRARY_PATH

# 4. 永久配置
echo "/opt/sophon/lib" | sudo tee /etc/ld.so.conf.d/sophon.conf
sudo ldconfig

# 5. 验证库版本
strings /usr/lib/libopencv_core.so.4.2 | grep OPENCV
```

### Q5: 静态链接 vs 动态链接,如何选择?

**A**:

| 场景         | 推荐方式 | 原因                      |
| ------------ | -------- | ------------------------- |
| 嵌入式 Linux | 动态链接 | 节省存储和内存            |
| 单片机(MCU)  | 静态链接 | 没有操作系统,无动态链接器 |
| 桌面应用     | 动态链接 | 系统库共享,更新方便       |
| 一次性工具   | 静态链接 | 部署简单,无依赖           |
| 容器化应用   | 动态链接 | 分层镜像,减少重复         |
