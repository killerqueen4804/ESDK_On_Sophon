## 0. 一句话理解这个项目

这是一个运行在 **算能 SE7（ARM64 aarch64）** 上的边缘视觉系统：

- 从 DJI Edge-SDK 拿到 **实时 H.264 视频流/媒体文件**
- 用 **FastDeploy(BModel)** 推理（检测 YOLO/PP-YOLOE、分割 PaddleSeg/SAM2、追踪 ByteTrack）
- 通过 **MQTT** 与云端交互（收指令、回指令、上报事件）
- 可选：**RTMP 推流**

核心入口是 `src/main.cpp` → `esdk_sophon::Application::initialize()/run()/shutdown()`。

## 1. 你需要掌握的“最小闭环”

### 1.1 最重要的 4 件事（按优先级）

1. **编译是交叉编译**：在 Docker 容器 `stream_lzy` 里，用 `aarch64-linux-gnu-g++` 给 SE7 编出来。
2. **启动顺序不能乱**：`Edge-SDK` 必须最先 init，其次 Logger/Config，之后 MQTT，最后 TaskManager 和 MqttHandler。
   - 这在 `src/Application.cpp::initialize()` 写得很清楚。
3. **MQTT 指令是驱动系统的轮子**：云端下发 `thing/product/{device_sn}/services`，本地解析后启动/停止任务。
4. **配置文件是大脑**：`config/config.json` 决定 MQTT broker、模型路径、RTMP 地址、设备 SN 等。

### 1.2 一次端到端链路（你必须能讲清楚）

1. 云端向 Topic 发布指令：`thing/product/{device_sn}/services`

2. 本地 `mqtt::MqttClient` 收到消息 → 回调给 `mqtt::MqttHandler::onMessageReceived()`

3. `MqttHandler` 根据 `method` 路由到具体处理函数（如启动算法）

4. `TaskConfig::fromJson()` 解析指令 data → `TaskManager::startTask()`

5. 任务执行：

- LiveStream：解码 H.264 → detector/segment/tracker → 可视化 → 上报事件 → 可选 RTMP 推流
- MediaFile：扫描/读取媒体文件目录 → 同上

6. 上报事件：

- 事件 Topic（见 `config/config.json`）：`drone/{device_sn}/info/event`

补充：事件可靠性不是“直接 publish 就完事”，项目里有一层 **EventCache**（`include/esdk_sophon/core/EventCache.h`）用于处理 MQTT 断线时的缓存与重试：

- 正常：Task → TaskService → publish → MQTT
- 断线：Task/Service → EventCache 缓存（内存+文件）→ 等重连后自动 retry

## 2. 代码结构与模块职责（按“看代码顺序”）

### 2.1 程序入口

- `src/main.cpp`
  - 只做 3 件事：`initialize()` → `run()` → `shutdown()`
  - 这是一个典型 **Facade（外观模式）**：主函数不关心内部细节。

### 2.2 顶层协调器 Application（强烈建议先读）

- `src/Application.cpp`
  - `initialize()`：严格按顺序初始化
    1. Edge-SDK：`ESDKInit()`（定义在 Edge-SDK 示例源码中，被编译进主程序）
    2. Logger：`core::Logger`（单例）
    3. Config：`core::Config`（加载多个候选路径）
    4. MQTT：`mqtt::MqttClient::initialize()` + `connect()`
    5. TaskManager：`task::TaskManager::initialize()`（要求 MQTT 已连）
    6. MqttHandler：`mqtt::MqttHandler::initialize()` + `start()`（订阅 topics）
  - `run()`：主循环（目前是 sleep + 等信号）
  - `shutdown()`：逆序关闭：Handler → MQTT → Tasks → Edge-SDK

> 为什么要这样设计？
>
> - 好处 1：初始化/关闭顺序“写死”在一个地方，避免同事乱动导致隐性 bug。
> - 好处 2：main 极简，便于部署与守护进程化。
> - 好处 3：当你加新子系统（例如 Web API/本地 UI），只需要挂到 Application，不会污染 main。

### 2.3 任务系统 Task（系统的业务中枢）

- `include/esdk_sophon/task/TaskTypes.h`

  - `TaskType`：直播流检测 / 媒体文件检测 等
  - `TaskState`：IDLE/PENDING/RUNNING/PAUSED/COMPLETED/FAILED/CANCELLED
  - `TaskConfig`：任务配置（由 MQTT JSON 解析而来）
    - 关键点：**任务配置解析集中在 `TaskConfig::fromJson()`**，后续协议变更优先改这里。

- `include/esdk_sophon/task/TaskManager.h`
  - 单例 + 工厂：根据 `TaskType` 创建 `LiveStreamTask` / `MediaFileTask`
  - `startTask(config)` 是常用入口：create + start
  - 线程安全：对外接口都加锁，允许在 MQTT 回调线程调用

> 交接建议：你要对同事强调“任务系统是状态机思想”，**一切处理围绕 Task 生命周期**。

### 2.4 业务编排层 TaskService（把“做什么”与“怎么做”隔离）

文件：`include/esdk_sophon/task/TaskService.h`

它是典型的 **Service Layer（业务编排层）**：

- Task（LiveStreamTask/MediaFileTask）只负责：取数据、线程控制、节流、何时调用 service
- TaskService 负责：
  - `processFrame()`：一帧的完整业务流程（检测 → 过滤 → 构建事件 → 发布）
  - `buildEvent()` / `buildSegmentationEvent()`：把推理结果封装成平台需要的事件 JSON
  - `publishEvent()` / `publishMqttMessage()`：统一出口上报

为什么要这样分层？

- 好处 1：Task 的职责更纯粹（“调度器”），更容易写对线程/状态机
- 好处 2：以后加新的任务类型（比如录像分析/多路输入）时复用 service，不会复制粘贴业务逻辑
- 好处 3：协议变化集中在“构建事件”的位置，不会散落满地

### 2.5 MQTT 通信层（云端交互的入口）

- `include/esdk_sophon/mqtt/MqttHandler.h`
  - 角色：桥接 `MqttClient`（通信）与 `TaskManager`（业务）
  - 关键点：
    - `start()` 会订阅 `thing/product/{device_sn}/services`
    - `onMessageReceived()` 解析 JSON，根据 `method` 路由
    - `publishEvent(eventJson)` 上报事件到 `drone/{device_sn}/info/event`

> 注意：从头文件可以看到新旧演进：
>
> - `types::DetectionResult` 已被废弃（现在统一走 eventJson / EventCache 思路）
> - 这说明项目在“输出格式”上经历过重构，后续再改协议请优先维持这个方向：**用 JSON 事件作为边界**。

## 3. 构建、部署与运行（按你真实会做的流程写）

### 3.1 编译方式总览

本项目的顶层 `CMakeLists.txt` 明确配置了交叉编译：

- 目标系统：Linux
- 目标架构：aarch64
- 编译器：`/usr/bin/aarch64-linux-gnu-gcc/g++`

并且把输出固定到：

- 可执行文件：`build/bin/ESDK_Sophon`
- 库：`build/lib/*.a`

另外 `src/CMakeLists.txt` 会把模块按层组织：

`core → mqtt/vision/video/storage/utils/rtmp/task → device → ESDK_Sophon`

并且把 Edge-SDK 示例源码 `pre_init.cc/key_store_default.cc` **一起编进主程序**（这点很关键）。

### 3.2 Docker 交叉编译（推荐给新人用脚本）

脚本：`scripts/build_in_docker.sh`

它会做：

1. 检查你是不是在容器内、是不是在 `/workspace`、工具链文件是否存在 2)（可选）检查第三方库架构 3)（可选）清理 build
2. cmake 配置（指定 toolchain）
3. 编译
4. 验证 `bin/ESDK_Sophon` 是否为 ARM64

如果你要“一键编译+部署到 SE7”，可以参考 `scripts/build_and_test.sh`。

> 交接提示：`build_and_test.sh` 里写了 SE7 的固定 SSH 信息（host/port/user/target_dir）。
> 新同事接手后，第一件事就是确认这些是否仍可用。

### 3.4 Windows 开发机上的“你能做什么/不能做什么”

你当前看到的仓库在 Windows 上打开没问题（写代码/看日志/改配置/改 CMake 都可以），但**最终产物必须是 ARM64**，所以：

- ✅ 推荐：在 Windows 上编辑代码 → 进 Docker 容器交叉编译 → scp 到 SE7 运行
- ⚠️ 不推荐：在 Windows 上直接本地编译运行（除非你额外搭了完整 aarch64 交叉环境，并且 third_party 也匹配）

### 3.3 SE7 上运行目录约定

从脚本可以看出默认路径：

- 可执行文件目录：`/data/Edge-SDK/build/bin`
- 日志目录（通过 config 控制，相对路径时通常在运行目录下）：`logs/`
- 模型目录（绝对路径）：`/data/Edge-SDK/models/...`

## 4. 配置文件说明（超详细，建议照着改）

### 4.1 配置系统如何读取？

入口：`core::Config`（`include/esdk_sophon/core/Config.h`）

- `Application::initialize()` 会尝试这些路径：
  1. `config/config.json`
  2. `../config/config.json`
  3. `/workspace/config/config.json`

这意味着：

- 你在 SE7 的运行目录里放一个 `config/config.json` 最稳。
- 在 Docker 容器里，通常用 `/workspace/config/config.json`。

### 4.2 `config/config.json` 字段解释（抓“接手必改”的）

#### logger

- `logger.level`：INFO/DEBUG...
- `logger.log_directory`：日志目录（相对路径会相对运行目录）
- `logger.rotation.*`：轮转策略

#### mqtt

- `mqtt.broker`：如 `tcp://jiaoyujidi.work:1883`
- `mqtt.client_id`：客户端 ID（通常跟设备 SN 相关）
- `mqtt.topics.*`：Topic 模板，包含 `{device_sn}` 占位符

#### device

- `device.analysis_sn`：**分析端设备 SN**（很关键，影响 topic 替换与身份）
- `device.gateway_sn`：机场网关 SN（Cloud API 相关）
- `device.aircraft.sn`：飞行器 SN（订阅 OSD 等）
- camera/gimbal：采集与云台参数

#### detector / segmentation / tracker

- 模型路径基本都是绝对路径 `/data/Edge-SDK/models/...`
- `confidence_threshold` / `nms_threshold` / `input_size` 是最常调的

#### video.rtmp

- `video.rtmp.enabled`：开关
- `video.rtmp.url`：推流地址（常变）
- `width/height/fps/bitrate`：推流参数

> 新人改配置的典型顺序：
>
> 1. 先改 `device.analysis_sn`、`mqtt.client_id`（保证 Topic 里替换正确）
> 2. 再改 `mqtt.broker`（确保能连云端）
> 3. 再改模型目录（如果设备上目录不同）
> 4. 最后改 RTMP 推流（可选）

### 4.3 单独的 `config/logger.json`

`config/logger.json` 提供了更细粒度的日志配置项（文件名 pattern 等）。

> 经验：当日志文件乱码或编码不对，优先看 `scripts/fix_log_encoding.sh` 与 `scripts/setup_utf8_system.sh`（仓库里已有相关脚本）。

## 5. 新人最容易踩的坑（以及正确排查思路）

### 5.1 “能编译但在 SE7 跑不起来”

常见原因：

- 可执行文件架构不对（编成了 x86-64）
  - 用 `scripts/build_in_docker.sh` 的 `file bin/ESDK_Sophon` 检查
- 第三方库架构混了
  - 用 `scripts/check_lib_arch.sh` 排查

### 5.2 “MQTT 连不上”

检查顺序：

1. `config/config.json` 的 `mqtt.broker` 是否可达
2. `client_id` 是否冲突（同一个 broker 上 client_id 重复会导致互踢）
3. 设备 SN 是否正确（topic 替换后是否符合云端约定）

定位手段：

- 看日志：`logs/` 下按日期滚动
- 重点关注：Application 初始化阶段 `[4/5] 连接MQTT服务器...`

（可选）如果你需要快速验证云端 Topic 是否能通：

- 先用 `tests/test_mqtt`（如果该测试覆盖了连接与发布）
- 再看 `MqttHandler::onMessageReceived()` 是否有命令到达日志

### 5.3 “云端发了指令，但是本地没反应”

常见原因：

- 没成功订阅 topic（`MqttHandler::start()` 失败）
- Topic 模板不对（`thing/product/{device_sn}/services` 的 device_sn 没替换成真实值）
- method 字段不匹配（云端升级协议后 method 名变了）

正确排查：

1. 确认 `Application` 初始化日志显示 `MqttHandler启动成功`
2. 在 `MqttHandler` 里找到 `initCommandHandlers()` 注册的 method 列表
3. 查 `TaskConfig::fromJson()` 的字段解析是否与云端一致

### 5.4 “推理没结果/结果很慢”

常见原因：

- 模型路径不对（绝对路径不存在）
- 输入尺寸与模型不匹配
- device_id 不对（多卡场景）

建议做法：

- 先跑 `tests/` 里的相关测试（比如 detector、tracker、h264 decoder）确认基础 OK

## 7. “你要改什么，去哪里改”（按需求分流）

### 7.1 云端协议字段变了

优先改：

- `TaskConfig::fromJson()`（`include/esdk_sophon/task/TaskTypes.h`）
- `mqtt::MqttHandler` 的 method 路由（`initCommandHandlers()`/`handleServiceCommand()`）

### 7.2 想新增一种任务类型

步骤：

1. 在 `TaskType` 加枚举
2. 新增一个实现 `ITask` 的任务类（参考 LiveStream/MediaFile）
3. 在 `TaskManager::createTask()` 工厂里加分支
4. 若需云端下发：在 `TaskConfig::fromJson()` 里能解析出对应 type

### 7.3 想新增一个算法（比如新检测器/分割器）

建议思路：

- 不要把算法细节塞到 TaskManager/MqttHandler
- 算法应在 `vision/` 模块内抽象统一接口
- Task 只负责“调度 + 数据流”，算法负责“处理一帧”

## 9. 你接手后的“第一周路线图”（带原因）

1. **读一遍 `src/Application.cpp`**：理解生命周期顺序，避免后续改坏初始化。
2. **读 `MqttHandler` + `TaskConfig::fromJson()`**：这是云端协议适配层。
3. **把 SE7 上的 `config/config.json` 路径与模型路径理顺**：这会消灭 70% 的运行问题。
4. **跑一遍 tests**：建立“改动 → 验证”的习惯。
5. **最后再深入 vision/video/rtmp**：这些模块最容易因环境差异踩坑。
